22.1 CLR, JIT & memory basics Added

The CLR runs your code: C# compiles to IL, the JIT turns IL into machine code at run time, and the runtime manages memory, types and threads for you.

OptionWhat it doesTrade-off
Tiered compilationQuick JIT first, optimised JIT for hot code. On by defaultCode is slower for the first seconds (warm-up)
Dynamic PGOUses live profile data to optimise Tier 1 code. Default since .NET 8None for most apps; just keep tiering on
ReadyToRunPre-compiles IL to native code at publish; still JITs hot paths laterFaster startup, bigger files
Native AOTWhole app compiled to native code, no JIT at all (see 22.9)Fastest startup; limits reflection

Stack vs heap, value vs reference

Stack

  • One per thread. Holds locals and call frames.
  • Freed automatically when the method returns. Very cheap.
  • Value-type locals and references (pointers) live here.

Managed heap

  • Shared by all threads. Holds objects created with new for classes, arrays, strings and boxed values.
  • Freed later by the garbage collector (22.2).
  • More objects = more GC work.

📦 Boxing

Putting a value type into an object or interface variable copies it into a new heap object. Unboxing copies it back.

🕵️ Hidden boxing

Non-generic collections (ArrayList), object parameters, and casting a struct to an interface.

✅ Avoid it

Use generics (List<int>), generic constraints (where T : IComparable<T>) and typed APIs.

  • "Structs live on the stack" is only half true. A value type lives wherever its container lives: a struct field inside a class is on the heap.
  • Value types copy on assignment. Big or mutable structs cause bugs and slow copies; keep them small and readonly.
  • Warm-up is real: the first requests run Tier 0 code. Use ReadyToRun or warm-up requests if cold starts matter.

22.2 Garbage collection Added

The garbage collector frees objects that nothing references any more. It splits the heap into generations because most objects die young.

ModeHow it worksDefault for
WorkstationOne heap, GC runs on the thread that triggered itConsole, desktop and most client apps
ServerOne heap and GC thread per core; built for throughputASP.NET Core apps
DATASServer GC that grows and shrinks the number of heaps with load, keeping the heap close to the live data sizeOn by default with Server GC since .NET 9
Background GCGen 2 collections run mostly alongside your threadsOn by default
POHPinned object heap for buffers that must not move (native I/O)GC.AllocateArray(…, pinned: true)

DATAS trades a few percent of peak throughput for a much smaller heap. That's good in containers. On a dedicated machine that needs every request per second, you can turn it off with GarbageCollectionAdaptationMode=0.

🔥 GC pressure causes

String concatenation in loops, LINQ and closures on hot paths, boxing, big temporary arrays (LOH), and caches that grow without limit.

🧹 Finalizers

Objects with a finalizer survive at least one extra GC and are cleaned up later on one finalizer thread.

🔑 IDisposable

Releases sockets, file handles and connections now, deterministically. Call it with using or await using.

🛡️ SafeHandle

Wraps an unmanaged handle and owns the finalizer for you. You almost never need to write your own finalizer.

22.3 async/await internals Added

async/await lets a thread start I/O, go back to the pool while it waits, and carry on later. The compiler rewrites your method into a state machine to make that work.

  • The compiler turns an async method into a struct with a MoveNext() method. Each await is a numbered state.
  • If the awaited task is already complete, the method just keeps going on the same thread. No allocation, no thread switch.
  • If not, locals are saved, the method returns an incomplete Task, and a continuation is registered.
  • While the I/O is in flight, no thread is waiting. That's why one server can handle thousands of concurrent requests.
TypeUse whenRules
Task / Task<T>The default for any async methodCan be awaited many times, cached, passed to WhenAll
ValueTask<T>Hot paths that usually finish synchronously (cache hit, buffered read)Await it once. Never await twice or call .Result before it completes
IAsyncEnumerable<T>Streaming results as they arrive (DB rows, paged APIs)Consume with await foreach; pass a token with WithCancellation

SynchronizationContext and ConfigureAwait(false)

WPF, WinForms, MAUIYes, the UI threadNot in code that touches the UI after the await
Old ASP.NET (System.Web)Yes, the request contextYes; .Result here can deadlock

💥 async void

The caller can't await it, and an exception crashes the process. Only use it for UI event handlers.

🔒 Sync over async

.Result, .Wait(), GetAwaiter().GetResult() block a thread. With a context they deadlock; without one they starve the thread pool (22.4).

🚀 Fire and forget

An un-awaited task loses its exceptions. Put background work on a queue or Channel read by a BackgroundService.

🛑 Cancellation

Accept a CancellationToken and pass it to every call. ASP.NET Core binds HttpContext.RequestAborted to it when the client disconnects.

  • Async is about not blocking threads during I/O. It doesn't make one call faster, and it doesn't help CPU-bound work.
  • Go "async all the way". One .Result in the middle of the call chain undoes the benefit.
  • Use ConfigureAwait(false) in libraries. In ASP.NET Core app code it's optional.

What actually happens at an await? 🧵

⚙️ The compiler turns your method into a state machine

⏸️ If the task isn't done, it saves your locals and returns to the caller

🏊 The thread goes back to the pool. While the DB works, no thread is waiting

▶️ When the I/O completes, any pool thread resumes the method where it left off

🚫 .Result and async void break the deal

Async isn't faster, it's more scalable. Did you know ConfigureAwait(false) does nothing useful in ASP.NET Core app code?

22.4 Threading & the thread pool Added

The thread pool is a shared set of worker threads. Blocking them starves everything else, and the fix is almost always to stop blocking, not to add threads.

Threads vs processes, concurrency vs parallelism and race conditions are covered on page 01: 1.2 Concurrency vs Parallelism. This section is about the .NET specifics.

  • The pool starts with a minimum number of threads (by default, the number of CPU cores) and hands out work instantly up to that level.
  • Above the minimum it adds threads gradually, using a hill-climbing algorithm and starvation detection. A burst of blocking calls therefore means seconds of queueing.
  • Async I/O completions and continuations run on the same pool, so blocked threads also delay the code that would unblock them.

Symptoms

  • Latency climbs while CPU stays low.
  • Thread count creeps up steadily.
  • Thread-pool queue length keeps growing.
  • Health checks time out under load.

Diagnosis

  • dotnet-counters monitor -n MyApi --counters System.Runtime
  • Watch dotnet.thread_pool.queue.length and dotnet.thread_pool.thread.count (.NET 9+ names).
  • dotnet-stack report -p <pid> shows where threads are stuck.
  • Fix the blocking call; SetMinThreads only hides it.

lock + System.Threading.LockShort critical sections in sync codeNew Lock type in .NET 9+; no await inside
SemaphoreSlimAsync mutual exclusion; capping concurrent callsWaitAsync + release in finally
InterlockedAtomic counters, compare-and-swapLock-free, very cheap
Concurrent collectionsShared dictionaries, queues, bagsGetOrAdd's factory can run more than once

  • Never hold a lock across an await. Use SemaphoreSlim.WaitAsync for async code.
  • Bound every queue. An unbounded channel just moves the out-of-memory error somewhere else.

22.7 HttpClient & outbound calls Added

HttpClient is meant to be reused. Create one per call and you run out of sockets; keep one forever and you miss DNS changes. IHttpClientFactory or a pooled connection lifetime solves both.

🏷️ Typed clients

A class that takes HttpClient in its constructor and wraps one API. Config, base address and resilience live in one registration.

🛡️ Resilience handler

AddStandardResilienceHandler() adds rate limiting, total and per-attempt timeouts, retries and a circuit breaker. See 3.6 Resilience patterns.

🪤 Typed client in a singleton

Typed clients are transient. Capture one in a singleton and its handler never rotates: stale DNS again.

  • Disposing HttpClient is the bug, not the fix. Reuse the handler, not just the client.
  • Every outbound call needs a timeout. The default HttpClient.Timeout is 100 seconds, which is far too long for a request path.
  • Only retry idempotent calls, or calls that carry an idempotency key (payments!).

22.8 EF Core performance & pitfalls Added

EF Core turns LINQ into SQL. Most performance problems come from loading too much, too often: N+1 queries, tracking you don't need, and whole entities when you only need three columns.

PitfallSymptomFix
N+1 queriesHundreds of tiny queries per requestInclude, or better a Select projection
Cartesian explosionIncluding 2+ collections returns huge result setsAsSplitQuery()
Tracking read-only dataHigh memory and CPU on readsAsNoTracking()
Whole entitiesWide rows over the wireProject into a DTO with Select
Load, modify, save in bulkOne UPDATE per rowExecuteUpdateAsync / ExecuteDeleteAsync
ToList() too earlyFiltering and paging done in memoryKeep it IQueryable until the end
Hot query re-translationCPU spent compiling the same LINQCompiled queries (EF.CompileAsyncQuery)

DbContext lifetime

  • A unit of work: scoped, one per request.
  • Not thread-safe. Two parallel queries on one context throw "A second operation was started".
  • AddDbContextPool reuses context instances for high-throughput APIs.
  • Background jobs and Blazor: IDbContextFactory<T>, one context per operation.

Migrations in production

  • Avoid Database.Migrate() at app startup in production: the app then needs schema-change rights, and a failed migration takes every instance down.
  • Generate an idempotent SQL script or a migration bundle and run it as a pipeline step.
  • Review the SQL; prefer additive, backward-compatible changes (expand/contract).
  • Log the generated SQL in development (LogTo or the EF Core logging category). You can't fix queries you never look at.
  • FromSql($"... {value}") sends value as a parameter. FromSqlRaw with string concatenation is SQL injection.
  • EF 10 sends parameterised collections (ids.Contains(x.Id)) as one parameter per value by default, which helps the query planner.

22.10 Actor model with Orleans Added

Orleans is Microsoft's virtual actor framework. You write small, single-threaded objects (grains) with an identity, and the runtime places, activates and recovers them across a cluster of servers (silos).

🧱 Grain

An actor with a key (e.g. account ID), its own state and async methods. Processes one request at a time by default.

🖥️ Silo

A host process running grains. Silos form a cluster with membership stored in Azure Table, SQL, Kubernetes and others.

👻 Virtual actor

A grain always "exists". It's activated when called and deactivated when idle. You never create or destroy it.

💾 State, timers, reminders

Pluggable persistence, in-memory timers and durable reminders that survive restarts.

Good fit

  • Many independent entities with their own state: accounts, devices, carts, game sessions.
  • Hot in-memory state with low latency, and a cluster that scales out.
  • Avoiding distributed locks: each entity is single-threaded by design.

Poor fit

  • Simple CRUD over a database: a plain API is easier.
  • Big set-based queries across all entities ("all accounts over $10k").
  • Teams without the appetite to run a stateful cluster.
  • Virtual actor = location transparency plus automatic lifecycle. The caller only knows the grain's interface and key.
  • Single-threaded grains remove locks, but a hot grain (one very busy account) becomes a bottleneck. Design keys so load spreads.
  • Grains calling each other in a cycle (A → B → A) can deadlock unless you allow reentrancy.

// ✅ correlation ID + timing: a convention-based middleware
public sealed class CorrelationMiddleware(RequestDelegate next, ILogger<CorrelationMiddleware> log)
{
    const string Header = "X-Correlation-ID";

    // scoped services go here, not in the constructor (the class lives for the whole app)
    public async Task InvokeAsync(HttpContext ctx, IRequestContext requestContext)
    {
        var id = ctx.Request.Headers[Header].FirstOrDefault() is { Length: > 0 and <= 64 } h ? h : ctx.TraceIdentifier;
        requestContext.CorrelationId = id;
        ctx.Response.OnStarting(() => { ctx.Response.Headers[Header] = id; return Task.CompletedTask; });

        var start = Stopwatch.GetTimestamp();
        using (log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
        {
            try { await next(ctx); }                                    // in ... endpoint ... out
            finally
            {
                log.LogInformation("{Method} {Path} {Status} in {Ms:0} ms", ctx.Request.Method,
                    ctx.Request.Path, ctx.Response.StatusCode, Stopwatch.GetElapsedTime(start).TotalMilliseconds);
            }
        }
    }
}

22.15 Authentication and authorisation in ASP.NET Core Added

Authentication proves who the caller is and builds HttpContext.User (a ClaimsPrincipal). Authorisation decides what that user may do, ideally through named policies, not role checks scattered through the code.

How it works

  • A scheme is a name plus a handler (Cookies, Bearer, OpenIdConnect). The handler can authenticate, challenge (401 or a login redirect) and forbid (403).
  • AddAuthentication registers schemes. UseAuthentication sets User. UseAuthorization checks the endpoint's metadata. Order: routing, then authentication, then authorisation (see 22.6).
  • Validate every token: signature key, issuer, audience, lifetime. ClockSkew defaults to 5 minutes; shorten it.
SchemeFitsWatch
CookieServer-rendered apps; the BFF for a SPAHttpOnly, Secure, SameSite, anti-forgery
JWT bearerAPIs called by apps and servicesStateless, so hard to revoke: keep lifetimes short
OpenID ConnectSign-in through an IdP (Entra ID, Okta)Code flow + PKCE, then a cookie session

Roles and claims

[Authorize(Roles = "Admin")] is fine for coarse checks. Roles alone soon explode into "Admin-NSW-ReadOnly".

Policies

A named set of requirements, each checked by an AuthorizationHandler. Endpoints name the policy, not the rule.

Resource-based

When the answer depends on the record ("is this your account?"), load it, then call IAuthorizationService.AuthorizeAsync(user, resource, policy).

Identity vs IdP

ASP.NET Core Identity stores users and passwords. .NET 8 added MapIdentityApi endpoints; .NET 10 adds passkeys. In an enterprise, prefer Entra ID through Microsoft.Identity.Web.

22.18 WCF and migrating off it Added

WCF is .NET Framework's SOAP and RPC stack. Its server side isn't part of modern .NET, so you either lift it to CoreWCF or move each contract to gRPC, REST or messaging.

🔤 What WCF gave you

SOAP and WS-* (WS-Security, reliable messaging, transactions), duplex callbacks, many transports. Very config-heavy.

🚫 Status

WCF server isn't in modern .NET. It stays on .NET Framework 4.8.x, supported but frozen.

🔁 CoreWCF

Open-source, community-driven port of the server side (.NET Foundation). Microsoft publishes a support policy: 1.9 is supported on .NET 10.

📞 WCF client

Still available on .NET 10: System.ServiceModel.* packages plus dotnet-svcutil to generate proxies from WSDL.

⚡ Quick-fire Q&A

When would you use a struct instead of a class?

For small, short-lived, immutable values without identity, such as money, coordinates or IDs. Roughly 16 bytes or less, and ideally a readonly record struct. Use a class when the object has identity, is large, or is shared and changed in place.

What's the difference between IDisposable and a finalizer?

Dispose releases resources deterministically, when you call it (via using). A finalizer is a safety net the GC runs at some unknown later time, on one thread, and it makes the object survive an extra GC. Implement IDisposable, wrap native handles in SafeHandle, and almost never write a finalizer yourself.

Task vs ValueTask?

Use Task by default. ValueTask avoids an allocation when a method usually completes synchronously (a cache hit, for example). But it may only be awaited once, and never consumed with .Result before it completes. Only use it on measured hot paths.

Why can calling .Result on a task deadlock or slow everything down?

It blocks the current thread until the task finishes. If there's a SynchronizationContext (UI, old ASP.NET), the continuation needs that same blocked thread: deadlock. In ASP.NET Core there's no context, but each blocked call takes a pool thread. Under load the pool starves and latency climbs while CPU stays low.

When does ConfigureAwait(false) matter?

In library code that might be called from a UI app or old ASP.NET, where it avoids resuming on the captured context (and possible deadlocks). ASP.NET Core has no SynchronizationContext, so in app code it makes no real difference. In UI code, don't use it before touching UI controls.

What is a captive dependency, and how do you catch it?

A longer-lived service holding a shorter-lived one, typically a singleton that injects a scoped DbContext. The scoped instance then lives forever and is shared across requests. Turn on ValidateScopes and ValidateOnBuild (on by default in Development), and use IServiceScopeFactory inside singletons.

Why not create a new HttpClient for each request?

Disposing it closes the connection, and the socket stays in TIME_WAIT. Under load you run out of ports. A single static client fixes that but never refreshes DNS. Use IHttpClientFactory with typed clients, or one static client with SocketsHttpHandler.PooledConnectionLifetime.

How would you find a memory leak in a production .NET service?

Confirm the trend with dotnet-counters (GC heap size and gen 2 size keep growing). Take two heap snapshots with dotnet-gcdump and compare which types grow. Then use dotnet-dump analyze with gcroot to see what keeps them alive. Common causes: event handlers, static caches, timers and captured closures.

Is .NET Framework end-of-life?

No. .NET Framework 4.8.x is supported as part of Windows and gets security fixes, but no new features. New work should target modern .NET (.NET 10 LTS); migrate existing apps by business value, not all at once.

What's the difference between LTS and STS releases?

Even-numbered releases are LTS with 3 years of support; odd-numbered are STS with 24 months (extended from 18, starting with .NET 9). Quality is the same; only the support length differs. .NET 8 and .NET 9 both end on 10 November 2026.

How do you inject a scoped service such as a DbContext into middleware?

Convention-based middleware is created once per app, so add the scoped service as a parameter of InvokeAsync, not the constructor. Or implement IMiddleware and register the class in DI, which resolves it per request.

What's the difference between Map and UseWhen?

Map (and MapWhen) fork the pipeline and the branch never rejoins, so it usually ends in Run. UseWhen runs extra middleware for matching requests and then rejoins the main pipeline.

How does validation work in minimal APIs in .NET 10?

Call builder.Services.AddValidation(). A source generator finds the handler parameter types, and an endpoint filter checks their DataAnnotations (and IValidatableObject). Invalid input gets a 400 ProblemDetails response before your handler runs.

Why shouldn't you use route constraints for validation?

A failed constraint means no route matches, so the client gets a 404 instead of a 400 with a useful error. Constraints like {id:guid} are for choosing between routes; validate the values with binding and validation.

In what order do MVC filters run?

Authorization, then resource filters (before model binding), then model binding, action filters around the action, exception filters if something threw, and result filters around the result. On the way out, result and then resource filters finish. Within a type, global wraps controller wraps action unless Order is set.

What are Blazor's render modes in .NET 8 and later?

Static Server (static SSR, the default), Interactive Server (events over a SignalR circuit), Interactive WebAssembly (runs in the browser) and Interactive Auto (server first, then WebAssembly once the bundle is cached). Apply them with @rendermode.

How would you secure a SPA that calls your ASP.NET Core API?

Use a BFF. The server signs in with OpenID Connect (code flow + PKCE), keeps the tokens and gives the browser an HttpOnly, Secure, SameSite cookie. The BFF calls the API with a bearer token. No tokens in localStorage, where any XSS can read them.

When do you need resource-based authorisation instead of a policy attribute?

When the decision depends on the data, such as "only the owner can edit this account". An attribute runs before the record is loaded, so load it, then call IAuthorizationService.AuthorizeAsync(user, resource, "Policy") with an AuthorizationHandler<TRequirement, TResource>, and return 403 if it fails.

How does EF Core know what to UPDATE when you call SaveChanges?

The change tracker keeps a snapshot of each tracked entity. SaveChanges runs DetectChanges, compares current values with the snapshot, marks entities Added, Modified or Deleted, and sends INSERT, UPDATE (changed columns only) or DELETE statements in one transaction. Untracked (Detached) entities are ignored.

How do you implement soft delete and multi-tenancy in EF Core?

Global query filters: HasQueryFilter(e => !e.IsDeleted) and a tenant filter that reads the current tenant id from the context. EF 10 lets you name each filter and switch one off with IgnoreQueryFilters(["SoftDelete"]). Set IsDeleted in a SaveChangesInterceptor instead of deleting the row.

How do you use a scoped DbContext from a BackgroundService?

A hosted service is a singleton, so don't inject the DbContext. Inject IServiceScopeFactory, call CreateAsyncScope() for each unit of work (each message or timer tick), resolve the DbContext from that scope and dispose the scope when done.

IOptions, IOptionsSnapshot or IOptionsMonitor: which one and why?

IOptions is a singleton read once, for settings that never change. IOptionsSnapshot is scoped and re-read per request, for controllers and scoped services. IOptionsMonitor is a singleton with CurrentValue and OnChange, for singletons and background services that must see reloaded values.

Can you run WCF services on .NET 10?

Not with WCF itself: the server side stayed on .NET Framework. CoreWCF, an open-source port, hosts the same contracts and bindings on ASP.NET Core, and Microsoft publishes a support policy for it. The WCF client (System.ServiceModel.*) works on .NET 10.

CoreWCF, gRPC or REST when leaving WCF?

CoreWCF when many SOAP clients can't change. gRPC for internal, high-throughput or streaming service-to-service calls (browsers need gRPC-Web or JSON transcoding). REST for partners, web and mobile. Decide per contract and per consumer.

What does the C# 14 field keyword do?

It refers to the compiler-generated backing field inside a property accessor, so you can add logic (trim, validate, raise PropertyChanged) without declaring a private field: public string Name { get; set => field = value.Trim(); }.

What is HybridCache and when did it ship?

A caching library (Microsoft.Extensions.Caching.Hybrid) that combines an in-memory cache with an optional distributed cache such as Redis behind one GetOrCreateAsync call, with stampede protection and tag invalidation. It was built for .NET 9 and went GA in March 2025 (9.3.0).

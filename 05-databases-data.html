5.1 SQL vs NoSQL Added

SQL: tables, fixed schema, joins, strong transactions. NoSQL: flexible models built for scale and specific access patterns.

Relational (SQL)

SQL Server, PostgreSQL, Oracle, Azure SQL

Transactions, ledgers, complex queries

Key-value

Redis, DynamoDB

Sessions, cache, lookups by key

Document

MongoDB, Cosmos DB

JSON aggregates, catalogues, profiles

Wide-column

Cassandra, HBase

Massive writes, time-ordered data

Graph

Neo4j, Cosmos Gremlin

Relationships, fraud rings, recommendations

Time-series / Vector / Search

InfluxDB · pgvector, Pinecone · Elasticsearch

Metrics · AI similarity · full-text

  • Model NoSQL around access patterns (queries first). Model SQL around entities (normalise first).
  • "Polyglot persistence": use the right store per service, but every new store adds operational cost.
  • Default to relational unless scale, schema flexibility or the access pattern clearly says otherwise.

5.2 ACID vs BASE & isolation levels Added

ACID (relational)

  • Atomicity: all or nothing
  • Consistency: constraints always hold
  • Isolation: concurrent transactions don't interfere
  • Durability: committed = survives a crash

BASE (many NoSQL)

  • Basically Available
  • Soft state: may change without input as copies sync
  • Eventually consistent
Isolation levelDirty readNon-repeatable readPhantom read
Read uncommitted❌ possible❌❌
Read committed (common default)✅ prevented❌❌
Repeatable read✅✅❌
Serializable✅✅✅
  • Higher isolation = more correct, but more locking and lower throughput. Snapshot isolation (MVCC) is a popular middle ground.

public class Account
{
    public int Id { get; set; }
    public decimal Balance { get; set; }
    [Timestamp] public byte[] RowVersion { get; set; } = [];   // optimistic concurrency
}

// Transfer: both updates commit together, or neither does
await using var tx = await db.Database.BeginTransactionAsync(IsolationLevel.Snapshot, ct);
var from = await db.Accounts.SingleAsync(a => a.Id == fromId, ct);
var to   = await db.Accounts.SingleAsync(a => a.Id == toId, ct);
from.Balance -= amount;
to.Balance   += amount;
await db.SaveChangesAsync(ct);   // throws DbUpdateConcurrencyException if someone else changed a row
await tx.CommitAsync(ct);

Snapshot needs ALLOW_SNAPSHOT_ISOLATION ON in SQL Server (Azure SQL has it on). With EnableRetryOnFailure, wrap manual transactions in db.Database.CreateExecutionStrategy().ExecuteAsync(…).

5.3 Indexing Added

An index is like a book's index: it finds rows without scanning the whole table. Reads get faster, writes get slower.

  • B-tree (default): equality and range queries, sorting.
  • Hash: equality only.
  • Clustered: the table is physically sorted by this key (one per table). Non-clustered: a separate structure pointing to rows.
  • Composite (customer_id, created_at): follows the leftmost-prefix rule. It helps a filter on customer_id, but not a filter on created_at alone.
  • Covering index: contains every column the query needs, so the table is never touched.
  • Index columns used in WHERE, JOIN and ORDER BY. Check the execution plan. Too many indexes slow down inserts and updates.
.NET 10 How to implement it
Index typeEF Core API
Single / compositeHasIndex(p => new { p.CustomerId, p.CreatedAt }), with IsDescending() per column if needed
Unique.IsUnique(), also your last line of defence for idempotency keys and business keys
Covering.IncludeProperties(…) (SQL Server and Npgsql providers)
Filtered / partial.HasFilter("[Status] = 'Pending'")
Clustered / methodSQL Server: .IsClustered(). PostgreSQL (Npgsql): .HasMethod("hash") / "gin"
Check the planquery.ToQueryString() to get the SQL, then look at the execution plan; LogTo / OpenTelemetry for slow queries
modelBuilder.Entity<Payment>(b =>
{
    // Composite: helps WHERE CustomerId = @c ORDER BY CreatedAt (leftmost-prefix rule)
    b.HasIndex(p => new { p.CustomerId, p.CreatedAt })
     .IncludeProperties(p => new { p.Amount, p.Status });       // covering: no key lookups

    b.HasIndex(p => p.Reference).IsUnique();
    b.HasIndex(p => p.Status).HasFilter("[Status] = 'Pending'"); // small, targeted index
});
// then: dotnet ef migrations add AddPaymentIndexes

Cosmos DB indexes every property by default. Tune it with IndexingPolicy on the container (Microsoft.Azure.Cosmos) to exclude paths you never query and cut write RU cost.

5.4 Database scaling

Climb the ladder: try the cheap, simple steps first, and only move to sharding when you must.

The scaling ladder (bottom = do first)
8. Polyglot / CQRS / NewSQL (Spanner, CockroachDB, Cosmos DB)
7. Sharding: split rows across many databases
6. Partitioning: split a big table inside one database
5. Federation: split by function (users DB, orders DB)
4. Read replicas: send reads to copies
3. Caching: Redis in front of the DB
2. Vertical scale + connection pooling
1. Optimise queries, indexes, schema

Replication

  • Leader–follower: one writer, many readers. Simple. Watch for replication lag (read-your-own-writes issues).
  • Multi-leader: writes in several regions. Needs conflict resolution.
  • Leaderless (Dynamo-style): quorum reads and writes.

Partitioning vs sharding

Sharding strategyHow➕➖
RangeBy value range (date, A–H)Range queries are easyHotspots (all new data on the last shard)

  • A good shard key has high cardinality, spreads load evenly and matches your main query.
  • Sharding pain: cross-shard joins and transactions, rebalancing, global unique IDs (use Snowflake-style IDs or UUIDv7), more operations work.
  • Connection pooling (PgBouncer, built-in pools) is often the quickest win when many app instances overwhelm the DB.
  • Denormalisation trades storage and write complexity for faster reads.

var cs = builder.Configuration.GetConnectionString("sql");

// Writes go to the primary
builder.Services.AddDbContextPool<AppDbContext>(o => o.UseSqlServer(cs));

// Reads go to a readable secondary, with no change tracking
builder.Services.AddDbContextPool<ReadDbContext>(o => o
    .UseSqlServer(cs + ";ApplicationIntent=ReadOnly")
    .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking));

Replicas lag. After a write, read your own data from the primary (or cache it) to avoid "my update disappeared" bugs.

Don't shard your database on day one 🙅

The scaling ladder: 1) fix queries and indexes → 2) bigger box + connection pooling → 3) cache → 4) read replicas → 5) split by function → 6) partition → 7) shard.

Every rung adds complexity. Climb only when the metrics tell you to.

5.5 Database backup strategies

Backups are insurance against deletion, corruption, ransomware and disasters. A backup only counts if you've tested the restore.

Full: every backup = everything. Incremental: Δ since the LAST backup of any type. Differential: Δ since the LAST FULL, so it grows every day.

TypeBackup timeStorageRestore speed
FullSlowestMostFastest (one set)
IncrementalFastestLeastSlowest (whole chain)
DifferentialMedium (grows)MediumMedium (full + latest diff)

📜 Transaction log backups → PITR

Log backups every few minutes let you restore to any point in time, like "just before the bad DELETE at 10:42".

📸 Snapshots

Storage- or volume-level copies, near-instant. Make sure they're application-consistent.

🔤 Logical vs physical

Logical = SQL dump (portable, slow). Physical = data files (fast, same engine).

🔥 Hot vs cold

Hot = DB online during backup. Cold = DB offline (consistent, but downtime).

🌏 Geo-redundant

Copy to another region (GRS) for disaster recovery.

🔒 Immutable / air-gapped

WORM storage that can't be deleted or encrypted by ransomware.

  • 3-2-1 rule: 3 copies of data, on 2 different media, 1 offsite. Modern version: 3-2-1-1-0 = plus 1 immutable or air-gapped copy, and 0 errors after restore verification.
  • Retention: GFS (Grandfather-Father-Son), e.g. daily for 30 days, monthly for 12 months, yearly for 7 years (compliance).
  • Encrypt backups. Protect and back up the keys separately.
  • Backup frequency sets your RPO. Restore speed sets your RTO.
.NET 10 How to implement it
Library / APIPackageUse it for
Azure SQL PITR + LTRAzure.ResourceManager.SqlBackups are automatic. Use the SDK to set short-term retention and long-term (GFS) retention policies, and to script point-in-time restores for drills
SQL Server backup / restoreMicrosoft.SqlServer.SqlManagementObjects (SMO Backup / Restore)Full, differential and log backups from code. Or run BACKUP DATABASE … TO URL through Microsoft.Data.SqlClient

The "0 errors" part needs a scheduled restore test: restore to a scratch database in a pipeline, then run row counts and checksums against it.

Your backup strategy is only as good as your last successful restore 🔁

✅ 3 copies ✅ 2 media ✅ 1 offsite ✅ 1 immutable ✅ 0 errors on restore test

That's the 3-2-1-1-0 rule. Ransomware goes after your backups first. Make one copy it can't touch.

5.6 Data migration strategies

Moving data from a source to a target system without losing it, corrupting it, or stopping the business.

Lifecycle

1. Assess & profilevolume, quality
→
2. Map & designsource → target rules
→
3. Extract & transformcleanse
→
4. Loadtrial runs / mocks
→
5. Validate & reconcilecounts, checksums
→
6. Cutovergo / no-go
→
7. Decommission

💥 Big bang

Move everything in one cutover window (e.g. a weekend).

  • ➕ Simple. No dual running.
  • ➖ High risk, downtime, hard to roll back.

💧 Trickle / phased

Migrate in waves (by product, region or customer segment) while old and new run side by side.

  • ➕ Low risk, learn as you go.
  • ➖ Longer, needs sync between systems.

🔄 CDC replication

Bulk-load history, then stream ongoing changes (CDC) until cutover. Near-zero downtime.

🪞 Parallel run

Run old and new together and compare outputs before switching. Common in banking.

✍️ Dual write

The app writes to both systems. Risky (partial failures). Prefer CDC or outbox.

🧩 Expand → migrate → contract

For schema changes: add the new column, backfill, switch reads, then drop the old one. Zero downtime.

Cloud migration: the 7 Rs

Rehost (lift & shift) · Relocate · Replatform (lift & reshape) · Refactor (re-architect) · Repurchase (move to SaaS) · Retire · Retain

  • Data quality issues show up during migration. Profile early and agree on cleansing rules with the business.
  • Reconcile: row counts, sums of amounts, hash totals, sample record checks.
  • Always have a rollback plan and a rehearsed cutover runbook.

ETL vs ELT: the only difference is where the "T" lives 🔤

ETL: clean the vegetables before putting them in the fridge.

ELT: put everything in a huge fridge (cloud warehouse) and prep when you cook.

Cheap cloud compute made ELT popular. Data governance keeps ETL alive.

5.8 Change Data Capture (CDC) Added

Capture every insert, update and delete from a database and stream it to other systems in near real time.

Source DBtransaction log
→
CDC connectorDebezium / GoldenGate / SQL CDC
→
Kafka / Event Hubs
→
Consumerscache, search, lake, microservices
  • Log-based (best): reads the DB transaction log. Low impact, captures deletes.
  • Trigger-based: DB triggers write to a change table. Adds write overhead.
  • Query / timestamp-based: polls WHERE updated_at > last_run. Misses deletes, adds load.
  • CDC is a key enabler for near-real-time integration, strangler migrations and cache invalidation, without touching legacy app code.

    .GetChangeFeedProcessorBuilder<Order>("order-projector", HandleChangesAsync)
    .WithInstanceName(Environment.MachineName)
    .WithLeaseContainer(leasesContainer)
    .Build();

async Task HandleChangesAsync(ChangeFeedProcessorContext context,
    IReadOnlyCollection<Order> changes, CancellationToken ct)
{
    foreach (var order in changes)
        await cache.RemoveAsync($"order:{order.Id}", ct);
}

The default change feed mode doesn't show deletes. Use a soft-delete flag plus TTL, or the newer "all versions and deletes" mode where your account supports it.

⚡ Quick-fire Q&A

Read replicas or sharding?

Replicas scale reads, and they're simple. Sharding scales writes and storage, and it's complex. Most systems are read-heavy, so start with replicas and caching.

How do you achieve near-zero-downtime migration?

Bulk-copy history, keep it in sync with CDC, validate continuously, then do a short cutover (switch the connection or DNS) with a rollback path.

Incremental vs differential restore?

Incremental needs the full backup plus every incremental since. Differential needs the full backup plus only the latest differential.

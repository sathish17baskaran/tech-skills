13.2 Source control, branching & code review Added

How a team shares one codebase: where changes live, how they get reviewed, and how they get back into main quickly and safely.

Three branching models

🏷️ GitFlow

Long-lived main and develop, plus feature, release and hotfix branches. Fits versioned products with several supported releases (SDKs, installed software). Heavy for web services: its author added a 2020 note recommending simpler flows for continuously delivered apps.

🔀 GitHub flow

main is always deployable. Short branch → pull request → review and checks → merge → deploy. A simple, good default for most teams.

🌳 Trunk-based

Everyone integrates into trunk at least daily, directly or through branches that live hours, at most a day or two. Unfinished work hides behind feature flags. This is the model CI/CD assumes.

ModelLong-lived branchesBranch lifeRelease fromBest for
GitFlowmain, develop (+ release, hotfix)Days to weeksRelease branch, tagged on mainProducts with several supported versions
GitHub flowmain onlyHours to a few daysmain, after each mergeWeb apps and APIs with one live version
Trunk-basedtrunk onlyHours (1–2 days max)Trunk, or a short release branch cut from itCI/CD and frequent deploys

Why trunk-based + feature flags suits CI/CD: "continuous integration" means merging with everyone else's code at least daily. A branch that lives two weeks isn't integrated, so conflicts and surprises pile up at the end. Flags split deploy from release, so unfinished code can merge safely. DORA lists trunk-based development as a capability linked to better delivery performance.

Pull requests & code review

🔍 What reviewers look for

  • Correctness: edge cases, error paths, concurrency
  • Design: does it fit? Is there a simpler way?
  • Tests that prove the behaviour, not just coverage
  • Security: input validation, authorisation, no secrets
  • Operability: logs, metrics, flags, safe DB migrations
  • Readability: names, comments that explain why

🤝 Etiquette

  • Review the code, not the person. Ask questions, don't command
  • Label optional comments as nit: so blockers stand out
  • Approve when it improves the codebase, not when it's perfect
  • Author: small PR, a clear description (why, how tested), self-review first
  • Respond within one business day at most (Google's guidance)

📏 PR size

Small PRs get faster, better reviews. Google's guide: ~100 lines is usually reasonable, 1,000 is usually too large. Split refactoring from behaviour changes.

⏱️ Review SLA

Agree a first-response target (hours, not days). Waiting for review is often the biggest part of lead time (13.15).

👥 Pairing & mob

Review happens while the code is written. It can replace async PR review where policy allows. Regulated teams may still need a recorded second approver.

🤖 Automate the boring bits

Formatting, linting, tests and security scans run as required checks. Humans review logic and design.

Commits, protected branches & ownership

13.3 Testing strategy Added

Many fast, cheap tests at the bottom, a few slow, realistic ones at the top, and some checks that only make sense in production.

🔺 Test pyramid

Lots of unit tests, fewer integration tests, very few end-to-end tests. Fast feedback, cheap to run.

🏆 Testing trophy

Kent C. Dodds' version: static analysis at the base, some unit tests, the most integration tests, a few E2E. Integration tests give the most confidence per minute.

Both shapes say the same thing: buy the most confidence for the least test time. The anti-pattern is the "ice-cream cone": mostly manual and E2E tests.

Contract testing (consumer-driven)

  • Each consumer states what it actually uses. The provider proves it still meets every contract before it deploys.
  • It replaces most slow, flaky cross-team E2E tests between microservices.

Performance testing: four different questions

TypeQuestion it answersBanking example
LoadDo we meet our SLOs at the expected peak?Lunchtime card traffic
StressWhere does it break, how does it fail, and does it recover?2× the busiest day on record
SpikeCan we survive a sudden surge? Does autoscaling react fast enough?Payday at midnight, a viral sale
Soak (endurance)Does it degrade over hours? Memory leaks, connection pools, full disksA 12-hour run before a major release

Chaos engineering

🧪 Hypothesis first

"If one zone fails, p99 latency stays under 500 ms and no payment is lost." Then inject the failure and measure.

💥 Small blast radius

Start with one instance, in staging, or 1% of traffic. Always have an abort switch.

🎮 Game days

Planned team exercises that break things on purpose, and practise the incident response too.

🛠️ Tools

Azure Chaos Studio, Chaos Mesh (Kubernetes), AWS Fault Injection Service, Gremlin. In code: Polly chaos strategies.

🧬 Test data management

  • Synthetic data generated to look real (fake names, valid account formats)
  • Masked production copies: irreversible masking of personal data
  • Never raw production customer data in test (privacy law)
  • Each test creates and cleans up its own data

⬅️ Shift left · Shift right ➡️

  • Left: unit tests, analyzers and contract tests on every PR, ephemeral test environments
  • Right: synthetic monitoring (scripted journeys every few minutes in prod)
  • Right: automated canary analysis (compare canary vs baseline metrics, roll back on regression)
  • Aim for fast feedback and real confidence, not a coverage percentage.
  • For microservices, contract tests replace most cross-team E2E tests.
  • Performance-test against your SLOs, with production-like data volumes.
  • Chaos without a hypothesis and an abort button is just an outage.

13.4 Versioning & release management Added

A version number is a promise about compatibility. Release management decides how a tested artifact gets that number, its release notes, and its path to production.

Semantic Versioning (SemVer 2.0.0)

PartChange it whenExample
MAJORConsumers could break (removed member, changed contract)1.4.2 → 2.0.0
MINORNew feature, backward compatible1.4.2 → 1.5.0
PATCHBug fix, backward compatible1.4.2 → 1.4.3
Pre-releaseNot stable yet. Sorts before the final release2.0.0-beta.1
Build metadataInformation only. Ignored when comparing versions2.0.0+5114f85

📦 Libraries & NuGet packages

  • NuGet fully supports SemVer 2.0 (pre-release labels, build metadata).
  • NuGet picks the lowest version that satisfies a range, so bump honestly.
  • 0.y.z means "no stability promise yet".
  • Catch accidental breaking changes in the build with package validation (below).

🌐 HTTP APIs

  • Usually expose only the MAJOR: /v1, /v2 (styles in 8.2).
  • Within a major, changes must be additive: new optional fields, new endpoints.
  • Publish a deprecation date and use the Sunset header before removing a version.
  • Contract tests catch breaking changes before release (13.3).

Release trains vs continuous delivery

🚂 Release train

A fixed cadence (fortnightly, monthly, quarterly). Whatever is ready catches the train. ✅ Predictable for the business, change boards, app stores and multi-team releases. ❌ Big batches, waiting, more risk per release.

🔁 Continuous delivery

Every merged change can go to production on its own, often behind a flag. ✅ Small risk per change, fast feedback. ❌ Needs strong test automation, observability and rollback.

Many banks run both: continuous delivery for internal services and APIs, and a train for mobile app releases and core banking changes.

  • Artifact immutability: a published version never changes. Never rebuild or overwrite 1.8.0; ship 1.8.1. nuget.org won't accept the same version twice (you can only unlist).
  • Deploy containers by digest (@sha256:…), not a moving tag like latest.
  • Environment promotion moves the artifact you tested, never a fresh build. Config and secrets come from each environment (13.1).
  • Keep provenance: who built it, from which commit, signed and with an SBOM (12.10).

Changelogs & release notes

📜 Changelog (for developers)

Every notable change per version, grouped as Added, Changed, Deprecated, Removed, Fixed, Security ("Keep a Changelog" style). Lives in the repo.

📣 Release notes (for users)

What changed for them: new features, migration steps for breaking changes, known issues. Written for the audience, not a list of commits.

Automate it: Conventional Commits (13.2) let tools such as release-please or semantic-release work out the next version, write the changelog and create the release. In .NET, MinVer, Nerdbank.GitVersioning or GitVersion stamp the version into the build.

  • A breaking change means a new MAJOR. No exceptions, even for "tiny" ones.
  • Published artifacts are immutable. Promote the same one, by digest, through every environment.
  • Derive versions and changelogs from git (tags, commit messages), not by hand.
  • Release trains trade speed for predictability. Continuous delivery trades process for automation.

13.5 Deployment strategies

Ways to release a new version that trade off downtime, risk, cost and rollback speed.

1. Recreate (big bang)

Stop all, start the new version. ➕ Simple, cheap. ➖ Downtime, risky.

2. Rolling

Replace instances in batches. ➕ No downtime, no extra cost. ➖ Mixed versions run during rollout, slow rollback.

3. Blue-Green

Two full environments, flip the switch. ➕ Instant switch and rollback. ➖ 2× cost. DB schema must work with both versions.

4. Canary

Expose to a small slice first. ➕ Real-traffic validation, small blast radius. ➖ Needs good monitoring and traffic splitting.

5. A/B testing

Like canary, but for business experiments, not technical safety.

6. Shadow / dark launch

Test v2 with real production traffic and no user impact. ➖ Watch out for side effects (don't double-charge!).

  • Database changes are the hard part. Use expand → migrate → contract so old and new code both work with the schema.
  • Define automatic rollback triggers (error rate, p99 latency) for canary and blue-green.
  • Ring-based deployment: internal users → early adopters → region → everyone (used by Microsoft).
  • Roll back vs roll forward: rolling back is safest if it's fast. Roll forward when a fix is small and well understood.

13.8 Containers & Kubernetes Added

A container packages an app with its dependencies. Kubernetes runs many containers across many machines: it schedules, heals, scales and connects them.

VM vs container

VM = [App][Libs][Guest OS] on a hypervisor. Container = [App][Libs] on the shared host OS kernel → lighter, starts in seconds.

Kubernetes at a glance

Deployment → ReplicaSet → Pods (1+ containers). Service = stable IP/DNS for pods · Ingress = L7 routing in · ConfigMap / Secret = config · HPA = auto-scale pods. Control plane: API server · scheduler · controller manager · etcd (state). Worker nodes: kubelet + container runtime.

  • Probes: liveness (restart if dead), readiness (send traffic only when ready), startup.
  • StatefulSet for stateful apps, DaemonSet for one pod per node (agents).
  • Managed offerings: AKS, EKS, GKE. Simpler PaaS option: Azure Container Apps.

13.9 Observability Added

Monitoring tells you that something is wrong. Observability lets you ask why, from the telemetry the system emits.

📜 Logs

Timestamped events. Make them structured (JSON) and include a correlation ID. Never log secrets or PII.

📈 Metrics

Numbers over time: request rate, error %, latency, CPU. Cheap to keep, good for alerts.

🧵 Traces

The path of one request across services (spans with timings). Shows where the time went.

The W3C traceparent header is propagated on every call, so all these spans share one trace ID (4bf9…). Child spans (└) sit inside their parent's time. Here the SQL INSERT is the bottleneck.

Four golden signals (Google SRE)

Latency · Traffic · Errors · Saturation

RED (services) & USE (resources)

Rate, Errors, Duration · Utilisation, Saturation, Errors

  • OpenTelemetry is the vendor-neutral standard for emitting logs, metrics and traces.
  • Alert on symptoms users feel (SLO burn rate), not on every CPU spike.

A log is a timestamped record of something that happened. Logs explain why something went wrong, and they're only useful if you can search and correlate them.

Log levels: use them consistently

LevelWhenExample
FATAL / CRITICALThe app can't continueCan't connect to DB at startup

WARNUnexpected, but handledRetry 1/3 to fraud service, circuit half-open

Structured vs unstructured

✗ Unstructured  "Payment failed for cust 42 amount 800 because timeout"
✓ Structured    {"ts":"2026-10-16T01:02:03Z","level":"ERROR","service":"payments","env":"prod",
                 "traceId":"4bf92f…","correlationId":"c-91a…","event":"PaymentFailed",
                 "paymentId":"7f3a","reason":"FraudServiceTimeout","durationMs":2004}
→ query it: where event=="PaymentFailed" | summarize count() by reason, bin(ts, 5m)

🧵 Correlation

Put traceId / correlationId on every log line and pass it across services (W3C traceparent), so you can follow one request end to end.

🏷 Context fields

service, version, environment, region, instance, operation, user or tenant ID (pseudonymised).

🔒 Never log

Passwords, tokens, secrets, full card numbers (PAN), CVV, full PII. Mask them (****1234) or tokenise.

💰 Volume & cost

Sample noisy DEBUG and success logs, set retention tiers (hot 30 d → archive 1–7 yrs), and drop health-check spam.

📜 Audit logs ≠ app logs

Audit logs record who did what, and when. Keep them immutable and tamper-evident, with longer retention, for compliance.

⏱ Async & non-blocking

Logging must never slow down or crash the request. Use buffered, async sinks.

  • Log events and decisions, not every line of code. Ask: "Would this help someone at 3 a.m.?"
  • Log an error once, at the boundary where it's handled. Logging it at every layer creates duplicate noise.
  • Use UTC timestamps in ISO 8601 format.
  • Make the log level changeable at runtime, so you can turn on DEBUG briefly during an incident.

13.11 Metrics Added

Metrics are numbers measured over time. They're cheap to store, fast to query, and ideal for dashboards, trends and alerts. They tell you that something is wrong.

Metric types

➕ Counter

Only goes up (resets on restart). Requests, errors, payments processed. Look at its rate: requests/s.

🌡 Gauge

Goes up and down. CPU %, memory, queue depth, active connections.

📊 Histogram

Counts values in buckets, so you can calculate percentiles (p50, p95, p99). Latency, payload size.

📐 Summary

Percentiles calculated on the client. Can't be combined across instances, so prefer histograms.

What to measure

LayerFrameworkExample metrics
User-facing service / APIRED: Rate, Errors, Durationreq/s, 5xx %, p95/p99 latency per endpoint
Infrastructure resourceUSE: Utilisation, Saturation, ErrorsCPU %, memory, disk I/O wait, thread-pool queue, DB DTU %
Whole systemGolden signals: Latency, Traffic, Errors, SaturationA combination of the above
MessagingFlow healthQueue depth, message age, consumer lag (Kafka), DLQ count
Business (KPIs)OutcomesPayments/min, success %, onboarding drop-off, $ value processed
GenAI / LLMAI opsTokens in/out, cost per request, time to first token, groundedness score, 429s

100 requests: 95 take 100 ms and 5 take 3,000 ms. The average (245 ms) looks fine and hides the slow tail. p95 = 100 ms, but p99 = 3,000 ms: 1 in 20 users waits 3 s.

  • Cardinality kills metric systems. Never use userId, paymentId or full URLs as labels. Use bounded values: endpoint template, status class, region.
  • Track business metrics next to technical ones. "CPU fine, but payments/min dropped 40%" is the alert that matters.
  • Tools: Prometheus + Grafana, Azure Monitor metrics, App Insights, Datadog, Dynatrace, CloudWatch. Emit them through OpenTelemetry.

13.12 Alerting Added

An alert should page a human only when something needs action now. Every page should be urgent, actionable and tied to user impact.

Types of alert rules

📏 Static threshold

"5xx rate > 2% for 5 min." Simple and predictable. Can be noisy if traffic varies.

📈 Dynamic / anomaly

Baseline learned by ML. Flags unusual patterns (e.g. payments/min far below the normal Monday 9 a.m. level).

🔥 SLO burn rate ⭐

Alert when the error budget is being used up too fast. Ties alerts directly to user impact.

💓 Heartbeat / absence

"No batch file processed by 06:00" or "no logs from service X for 10 min". Catches silent failures.

🔍 Log-based

Count of a specific event/error ("FraudServiceTimeout" > 50 in 5 min).

🧪 Synthetic

Scripted probes call key journeys (login, pay) from outside every minute.

SLO burn-rate alerting (multi-window)

SLO 99.9% → error budget 0.1% per 30 days (≈ 43 min). Burn rate = actual error rate ÷ allowed error rate. 1× uses the budget up in exactly 30 days.

Each PAGE rule needs a long AND a short window to both be over the threshold. The short window confirms it's still happening → fewer false alarms.

Severity & routing

SeverityMeaningResponseChannel
Sev 1 / P1Major customer impact (payments down)Immediate, 24×7, incident bridgePage + phone
Sev 2 / P2Degraded, or a key feature downWithin ~30 minPage
Sev 3 / P3Minor or at risk (disk 80%, cert expires in 14 d)Business hoursTicket / Teams
Sev 4 / InfoFor awarenessNo actionDashboard only

✅ A good alert

  • Based on a symptom users feel (errors, latency, failed journeys)
  • Has a clear title: what, where, how bad
  • Links to a runbook and dashboard
  • Has an owner and routes to the right team
  • Auto-resolves when the condition clears

❌ Alert fatigue causes

  • Paging on causes ("CPU 85%") with no user impact
  • Flapping thresholds, no duration window
  • Duplicate alerts for one incident (no grouping)
  • Alerts nobody acts on. Delete them or turn them into tickets
  • Everything is "critical"
  • Alert on symptoms, use dashboards for causes.
  • Group and deduplicate related alerts. Suppress them during planned maintenance.
  • Review alerts after every incident: did one fire? Too late? Too noisy? Tune them.
  • Don't forget "silent" failures: missing heartbeats, DLQ growth, certificate expiry, batch job SLAs.
  • Tools: Azure Monitor alerts + Action Groups, Grafana Alerting / Alertmanager, PagerDuty, Opsgenie, ServiceNow.

13.14 SRE practices Added

Site Reliability Engineering runs operations as a software problem: agree how reliable a service must be, spend the leftover risk on purpose, and automate the repetitive work away.

SLI vs SLO vs SLA and the error-budget maths are in 3.10. Burn-rate alerts are in 13.12. This section covers the team practices around them.

Error budget policy

A written agreement, signed off by product and engineering before anything goes wrong, saying what happens as the budget runs down.

  • Define thresholds and actions, who decides, and the exceptions (security patches, legal deadlines).
  • Name an escalation path for disagreements (e.g. head of engineering).
  • If the budget is always untouched, the SLO may be too loose, or you could take more risk. If it's always gone, renegotiate the SLO or invest in reliability.

Toil and the 50% rule

🔁 What toil is

Manual, repetitive, automatable work with no lasting value that grows with the service. E.g. restarting a stuck job, renewing certificates by hand, re-running failed batches.

⚖️ The 50% cap

Google SRE caps operational work at 50% of each engineer's time. The rest goes to engineering that removes toil or improves reliability. Over the cap? Hand work back to the dev team.

🛠️ Reduce it

Measure it (tickets, pages, hours). Automate the most frequent task first, offer self-service, fix the root cause, delete useless alerts.

On-call health

PracticeWhy
Big enough rotationGoogle SRE: at least 8 people for a single-site 24×7 primary + secondary rota, or 6 per site with follow-the-sun
Page only on symptomsUsers hurting or the SLO burning (13.12). Causes go to dashboards and tickets
Runbook on every pageThe responder knows the first steps at 3 a.m.
Cap the loadGoogle aims for at most 2 incidents per 12-hour shift. More means fix the system, not hire heroes
Written handoverAt each rotation change: open incidents, silenced alerts, risky changes in flight
Recovery & reviewTime off after a bad night. Review pages per week and false positives every month

Blameless postmortems

  • Blameless: assume people acted sensibly with what they knew. Fix the system, not the person. Blame makes people hide information.
  • Triggers: any Sev 1/2, data loss, a big error-budget burn, or an incident that monitoring missed.
  • Share postmortems widely and review open action items regularly. An unfinished action item is a repeat incident waiting to happen.

Production readiness review (PRR)

A checklist a service passes before it goes live or before SRE takes on its pager.

📈 Observability

SLIs and SLOs defined, dashboards, alerts with runbooks, distributed tracing.

🛡️ Resilience

Timeouts, retries, circuit breakers (3.6), load tested, DR tested (3.13).

🚀 Deploy & rollback

Safe deployment strategy, flags, a tested rollback, backward-compatible DB migrations.

🔐 Security & capacity

Threat model, secrets in a vault, capacity plan with headroom.

📟 Ownership

On-call rota, escalation contacts, support docs, dependencies listed.

Game days

Planned exercises that inject a real failure (zone outage, slow dependency, expired certificate) while the on-call team responds as if it were live. They test runbooks, alerts and people, not just code. Chaos principles and tools are in 13.3.

  • SLOs and error budgets turn "features vs reliability" into an agreed, data-driven rule.
  • Agree the error budget policy in advance, not in the middle of an incident.
  • Keep toil under 50%. Automate the most frequent manual task first.
  • Page on symptoms with a runbook. Write blameless postmortems with owned action items.

13.15 DORA metrics & engineering effectiveness Added

DORA's research-backed metrics measure software delivery outcomes, how fast and how safely changes reach production, so teams can see whether their improvements work.

The five metrics (DORA, 2024 onwards)

🚀 Throughput

  • Change lead time: from commit to running in production.
  • Deployment frequency: how often you deploy to production.
  • Failed deployment recovery time: how long to recover from a deployment that needed immediate intervention. It replaced MTTR in 2023.

💥 Instability

  • Change fail rate: % of deployments that need immediate intervention (rollback or hotfix).
  • Deployment rework rate (added 2024): % of deployments that are unplanned, made to fix a production incident.

These are the original "four keys" plus rework rate. DORA keeps finding that speed and stability aren't a trade-off: top performers do well on all of them. The lever behind all five is small batches.

Forsgren, Storey and others (2021): developer productivity can't be one number. Pick metrics from at least three of these dimensions, mixing surveys and system data.

😊 Satisfaction & well-being

Fulfilment, burnout, tooling happiness (surveys).

🎯 Performance

Outcomes: quality, reliability, customer impact.

📊 Activity

Counts of PRs, builds, deploys. Never use them alone.

💬 Communication & collaboration

Review turnaround, knowledge sharing, onboarding time.

🌊 Efficiency & flow

Uninterrupted focus time, handoffs, waiting time.

Anti-patterns

❌ Don't

  • Rank or compare teams, or use the metrics in individual performance reviews
  • Set them as targets from above (Goodhart's law: they get gamed)
  • Game them: split deploys, skip logging incidents, redefine "failure"
  • Track speed without stability, or count lines of code and commits

✅ Do

  • Let the team own its metrics and discuss them in retros
  • Compare a team with its own past, not with other teams
  • Pair them with SLOs (13.14) and well-being signals
  • Pick one improvement (smaller PRs, faster reviews) and watch the trend
  • Five metrics: lead time, deployment frequency, recovery time (throughput); change fail rate, rework rate (instability).
  • Speed and stability move together. Small batches improve both.
  • Use them for team learning, never to rank teams or people.
  • 2025: no more elite ladder. Per-metric benchmarks plus seven team archetypes.

⚡ Quick-fire Q&A

Blue-green vs canary?

Blue-green switches all traffic at once between two full environments, with instant rollback and double cost. Canary shifts traffic gradually and validates on real users with a smaller blast radius, but needs strong monitoring.

How do you deploy a DB schema change with zero downtime?

Expand/contract: add the new column or table (backward compatible), deploy code that writes both, backfill, switch reads, then remove the old structure in a later release.

Test pyramid vs testing trophy?

The pyramid says: many unit tests, fewer integration tests, very few E2E. The trophy (Kent C. Dodds) adds static analysis at the base and puts the most weight on integration tests, because they give the most confidence per minute. Both reject the "ice-cream cone" of mostly manual and E2E tests.

What is consumer-driven contract testing?

Each consumer writes a test that records exactly what it needs from a provider API (a pact). The provider runs those pacts in its own pipeline and can only deploy if every consumer's contract still passes. It catches breaking API changes without a shared, flaky end-to-end environment.

Logs vs metrics vs traces?

Metrics tell you something is wrong (error rate is up). Traces show where (which hop is slow). Logs explain why (the exception details).

What should you alert on?

User-facing symptoms: error rate, latency against the SLO (burn rate), failed synthetic journeys, missing heartbeats, and business KPIs dropping. Show causes like CPU or memory on dashboards, and ticket them rather than paging.

Why are high-cardinality metric labels a problem?

Each unique label combination is a separate time series. Labels like userId or paymentId create millions of series, which blow up memory, cost and query time. Put those IDs in logs and traces instead.

How do you reduce alert fatigue?

Page only on actionable symptoms, add duration windows, use multi-window burn-rate alerts, group and deduplicate, attach runbooks, and delete or downgrade alerts nobody acts on.

Trunk-based development vs GitFlow?

GitFlow keeps long-lived develop and release branches. It suits versioned products with several supported releases, but merges arrive late and big. Trunk-based development merges small changes into trunk at least daily and hides unfinished work behind feature flags, which is what CI/CD needs. Most web teams use trunk-based or GitHub flow.

What makes a good pull request and code review?

A small PR (around a few hundred lines at most) with a clear description of why and how it was tested. Automated checks cover style, tests and security, so reviewers focus on correctness, design, tests, security and operability. Reviews are kind, label nits as optional, and get a response within a business day.

How do you version a NuGet library or an API?

SemVer: MAJOR for breaking changes, MINOR for backward-compatible features, PATCH for fixes. Derive the version from git (MinVer, Nerdbank.GitVersioning or GitVersion), turn on package validation to catch accidental breaks, and never overwrite a published version. HTTP APIs usually expose only the major (/v2) and keep changes within it additive.

Why build once and promote the same artifact?

What reaches production is exactly what was tested. Rebuilding per environment can pull different dependencies or compiler output. Promote one immutable, signed artifact (by image digest) and only change config per environment.

What is an error budget policy?

A pre-agreed rule between product and engineering about what happens as the error budget (100% − SLO) is used: ship normally while there's budget, slow down as it burns, freeze features and fix reliability when it's gone. Exceptions and escalation are written down in advance.

What goes into a blameless postmortem?

Summary, impact, a timestamped timeline, contributing factors (not a person to blame), what went well, badly and where we got lucky, and action items with owners and due dates. The goal is to fix the system so the same failure can't recur.

What are the DORA metrics today?

Five since 2024: change lead time, deployment frequency and failed deployment recovery time (throughput), plus change fail rate and deployment rework rate (instability). The 2025 report replaced the elite/high/medium/low clusters with per-metric benchmarks and seven team archetypes.

How can DORA metrics be misused?

By ranking teams, tying them to individual performance reviews, or setting them as top-down targets. Teams then game them, for example by splitting deploys or not recording incidents. Use them for a team's own improvement over time, together with SLOs and well-being signals (SPACE).

19.1 URL shortener Added

"Design a service like bit.ly that turns a long URL into a short code and redirects anyone who opens it." A read-heavy key-value lookup with one hard part: making unique short keys.

1. Requirements

  • F: create a short link (optional custom alias and expiry), redirect, see click counts
  • NFR: 100M new links/month, 100:1 read:write, redirect p99 < 50 ms, 99.99% available, links never collide, codes not easy to guess
  • Out of scope: user accounts UI, link previews

2. Estimates

  • Writes: 100M ÷ (30 × 86,400 s ≈ 2.6M s) ≈ 40/s
  • Reads: 40 × 100 = 4,000/s average, ~10,000/s at peak
  • Storage: 100M × 12 × 5 years = 6B links × 500 B ≈ 3 TB
  • Key length: 626 ≈ 57B, 627 ≈ 3.5 trillion, so 7 base62 characters is plenty
  • Bandwidth: 4,000 × 500 B ≈ 2 MB/s (tiny). Cache the hot 20% of links: a few GB to tens of GB

3. API

4. Data model

One lookup by key, no joins. A key-value or NoSQL store (Cosmos DB, DynamoDB, Cassandra) fits; SQL is also fine at 3 TB if you shard by code.

6. Deep dives

Key generationHowGoodWatch out
Hash the URLMD5/SHA-256 of the long URL, take the first 7 base62 charsSame URL gives the same code; no coordinationCollisions: check and retry with a salt. Extra DB read on every write
Counter + base62Unique number (DB sequence or Snowflake-style ID), encode in base62No collisions, short codesSequential codes are guessable; one counter is a hotspot. Shuffle or encrypt the number first

301 or 302?

  • 301 (permanent): browsers cache it and skip you next time. Less load, but you lose click analytics and can't change or expire the link.
  • 302 (or 307, temporary): every click reaches you. Use it when analytics, expiry or abuse blocking matter. Use a CDN cache with a short TTL to take the load.

Read-heavy caching and async analytics

  • Cache-aside in Redis with LRU eviction. A small in-process L1 cache for the hottest links (05 strategies).
  • Cache "not found" for a short time too, so bots scanning random codes don't hit the DB.
  • Emit a click event to a queue or stream. A consumer aggregates counts per day. The redirect never waits on analytics.

7. Bottlenecks & scaling

  • DB reads: cache hit rate is the main lever. Add read replicas; shard by hash(code) with consistent hashing.
  • Viral link (hot key): L1 in-process cache plus CDN in front of GET /{code}.
  • Abuse: rate limit link creation per user/IP, and scan long URLs against malware and phishing lists before saving.
  • Expiry: a TTL in the store (or a nightly clean-up job) removes expired links; return 410 Gone.
  • Do the key-space maths first: 7 base62 characters ≈ 3.5 trillion codes.
  • Name the three key options (hash, counter + base62, KGS) and pick one with a reason.
  • 302 when you need analytics or expiry; 301 when you only want to save load.
  • Analytics are async. The redirect path does one cache lookup and nothing else.

const string Alphabet = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz";

static string ToBase62(long n)                   // 125 => "21" (2×62 + 1)
{
    if (n == 0) return "0";
    Span<char> buf = stackalloc char[11];        // long.MaxValue fits in 11 chars
    int i = buf.Length;
    while (n > 0) { buf[--i] = Alphabet[(int)(n % 62)]; n /= 62; }
    return new string(buf[i..]);
}

19.2 Distributed rate limiter Added

"Design a rate limiter that every API gateway node shares, so a client gets the same limit no matter which node it hits." The algorithms are in 08.6 Rate limit algorithms; this is the system around them.

1. Requirements

  • F: limit per API key, user, IP or tenant; different limits per plan and endpoint; tell clients their remaining quota
  • NFR: 1M requests/s at peak across all gateways, adds < 2 ms p99, accurate within a few %, keeps working if the limiter store fails
  • Out of scope: monthly billing quotas (a separate, slower counter)

2. Estimates

  • Checks: 1 check per request = 1M Redis calls/s
  • Redis: one shard handles roughly 100k simple ops/s, so ~10 shards, ~20 with headroom
  • Memory: 10M active keys × ~100 B per bucket ≈ 1 GB (fits easily)
  • Bandwidth: 1M × ~200 B ≈ 200 MB/s between gateways and Redis: keep them in the same zone

3. API

  • Mostly an internal call: Check(key, policy, cost=1) → {allowed, remaining, retryAfter}
  • Admin: PUT /policies/{plan} {limit, window, burst}
  • Response headers to clients (IETF draft, not yet an RFC):
HTTP/1.1 429 Too Many Requests
Retry-After: 1
RateLimit-Policy: "default";q=100;w=10
RateLimit: "default";r=0;t=1

4. Data model

WhereKeyValue
Redis hashrl:{policy}:{clientId}tokens, last_refill_ts; TTL ≈ 2 × refill time
Policy tableplan + routecapacity, refill rate, cost; cached in every gateway

5. High-level design

6. Deep dives

Algorithm choice

  • Token bucket for APIs: allows short bursts, two numbers to tune.
  • Sliding window counter when you need even limits per minute with little memory.
  • Avoid fixed windows for strict limits (2× burst at the edges).

Atomic check with Lua

  • "Read tokens, then write tokens" from two gateways is a race: both see 1 token, both allow.
  • A Lua script runs inside Redis as one atomic step: refill, take, save, return.
  • Use Redis server time (TIME) so gateway clock skew doesn't matter.

Per-key partitioning

  • Redis Cluster shards by key hash, so load spreads across shards automatically.
  • One bucket = one key, so the script never needs keys from two shards.
  • Hot key (one huge tenant)? Split its quota into N sub-buckets, or give it a local limiter.

Multi-region

  • Per-region limits (limit ÷ regions): simple, no cross-region calls. Most common.
  • Global: active-active Redis with CRDT counters replicates async, so it can overshoot briefly.
  • Never do a synchronous cross-region call per request (adds 50–200 ms).

Fail-open or fail-closed?

  • Fail-open (allow if Redis is down): protects availability. Right for most APIs, with a local in-memory limiter as a safety net.
  • Fail-closed (deny): for login, OTP and payment-initiation endpoints where abuse costs more than downtime.
  • Short timeout (~5 ms) on the Redis call either way.

Where it lives

  • Edge (WAF/CDN) for IP floods, gateway (APIM, YARP) for keys and plans, service for business limits.
  • Limit only after authentication, so attackers can't invent keys to get new buckets.

const string TokenBucketLua = """
    local cap, rate = tonumber(ARGV[1]), tonumber(ARGV[2])          -- capacity, tokens/sec
    local t = redis.call('TIME'); local now = t[1] + t[2] / 1000000  -- Redis clock, not ours
    local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
    local tokens = math.min(cap, (tonumber(b[1]) or cap) + (now - (tonumber(b[2]) or now)) * rate)
    local ok = 0
    if tokens >= 1 then tokens = tokens - 1; ok = 1 end
    redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
    redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) * 2)
    return { ok, math.floor(tokens) }
    """;

app.Use(async (ctx, next) =>
{
    var client = ctx.User.FindFirst("client_id")?.Value ?? $"ip:{ctx.Connection.RemoteIpAddress}";
    RedisResult[] r;
    try { r = (RedisResult[])(await redis.ScriptEvaluateAsync(TokenBucketLua, [new RedisKey($"rl:default:{client}")], [100, 10]))!; }
    catch (Exception e) when (e is RedisException or TimeoutException) { await next(ctx); return; } // fail open

    ctx.Response.Headers["RateLimit-Policy"] = "\"default\";q=100;w=10";
    ctx.Response.Headers["RateLimit"] = $"\"default\";r={(int)r[1]}";
    if ((int)r[0] == 0) { ctx.Response.StatusCode = 429; ctx.Response.Headers.RetryAfter = "1"; return; }
    await next(ctx);
});

The RateLimit / RateLimit-Policy headers are an IETF draft (draft-ietf-httpapi-ratelimit-headers), not an RFC yet. Many APIs still send the older RateLimit-Limit/Remaining/Reset or X-RateLimit-* names. Retry-After is the standard one.

Your rate limiter works on one server. Then you scale to 10 nodes and every client gets 10× the limit. 😬

🪣 Token bucket per client, stored in Redis, shared by all nodes

⚛️ Check + update in ONE Lua script, or two nodes both spend the last token

🕐 Use Redis server time, not each node's clock

🌏 Multi-region: split the limit per region, don't call across regions

🔓 Redis down? Fail open for normal APIs, fail closed for login and OTP

And always return 429 + Retry-After so clients can back off politely.

19.3 Chat / messaging app Added

"Design WhatsApp or Teams chat: 1:1 and group messages, online status, delivered and read ticks, and nothing lost when you're offline."

1. Requirements

  • F: 1:1 and group chat (up to 500 members), presence, delivered/read receipts, history on any device, push when offline
  • NFR: 50M daily users, 10M connected at once, delivery p99 < 500 ms when online, messages never lost, ordered within a conversation
  • Out of scope: voice/video calls, end-to-end encryption details (mention it)

2. Estimates

  • Messages: 50M × 40/day = 2B/day ÷ 86,400 ≈ 23k/s, ~70k/s at peak
  • Storage: 2B × 200 B ≈ 400 GB/day ≈ 146 TB/year before replication
  • Connections: 10M ÷ ~50k per gateway server ≈ 200 servers (plus headroom)
  • Bandwidth: 23k × 200 B ≈ 5 MB/s in; out is higher because groups fan out

3. API

5. High-level design

6. Deep dives

Connections

  • WebSockets: one long-lived, two-way connection per device (02 real-time).
  • Gateways hold connections only; chat logic sits behind them, so gateways can restart safely.
  • Clients reconnect with backoff and call /sync for anything missed.

Ordering per conversation

  • A per-conversation sequence number (Redis INCR, or one partition per conversation in Kafka).
  • Global order is not needed and doesn't scale. Order within a chat is enough.
  • Clients sort by seq and spot gaps, then fetch the missing range.

Group delivery

  • Small groups: fan out on write, one send per online member's gateway.
  • Big channels (thousands): store once, notify "new message in X", clients pull.
  • Gateways subscribe to a pub/sub backplane (Redis, Azure SignalR) to reach each other.

Storage: wide-column

  • Write-heavy, read by "conversation, newest first": a perfect fit for Cassandra/ScyllaDB or Cosmos DB.
  • Bucket by month so one busy chat doesn't create a huge partition.
  • Discord publicly described storing trillions of messages this way (Cassandra, later ScyllaDB).

Presence, offline, receipts

  • Presence: heartbeat every ~30 s sets a Redis key with a TTL. No heartbeat, key expires, user is offline.
  • Only push presence to people who have the chat open, or it floods the system.
  • Receipts store "read up to seq N" per member, not a flag on every message.

Never lose, never duplicate

  • Persist before you ack. The sender's single tick means "stored".
  • The client resends until acked, so dedupe on clientMsgId.
  • Push (APNs/FCM) is a wake-up hint only; the app then syncs from the server.

Hot conversation partitionTime buckets in the partition key; cache recent messages in Redis
  • Store first, then ack, then deliver. Push notifications only wake the app.
  • Order per conversation with a sequence number; never promise global order.
  • Presence = heartbeat + TTL. Receipts = "read up to N".

public sealed class ChatHub(IConnectionMultiplexer redis, IMessageStore store) : Hub
{
    public async Task<long> Send(string convId, Guid clientMsgId, string body)
    {
        // TODO: check the caller is a member of convId
        var db = redis.GetDatabase();
        long seq = await db.StringIncrementAsync($"seq:{convId}");          // order within the chat
        await store.AppendAsync(new ChatMessage(convId, seq, Context.UserIdentifier!, clientMsgId, body));
        await Clients.OthersInGroup(convId).SendAsync("message", convId, seq, body);
        return seq;                                                         // the ack: one tick
    }

    public Task Join(string convId) => Groups.AddToGroupAsync(Context.ConnectionId, convId);
}

builder.Services.AddSignalR().AddAzureSignalR();   // or .AddStackExchangeRedis(connString)

AppendAsync should be idempotent on clientMsgId (a resend after a lost ack must not create a second message). If INCR succeeds but the store fails, you get a gap in seq; clients must tolerate gaps.

How does a chat app show ✓ then ✓✓ then blue ticks? 💬

🔌 Each phone keeps one WebSocket open to a gateway

💾 The server stores the message BEFORE it says "got it" (✓)

🔢 Each conversation has its own sequence number, so order is per chat

📬 Bob's phone confirms delivery (✓✓) and later "read up to #1042"

😴 Offline? A push wakes the app, and it syncs from the server

Store first, ack second, deliver third. That one rule removes most chat bugs.

19.4 Notification service (multi-channel platform) Added

"Design a shared platform that any team can call to send email, SMS, push and in-app messages, respecting user preferences." Unlike the 18 payment-alert example (one event source, one use case), this is the generic engine behind many products.

1. Requirements

  • F: one API for all channels; templates with variables and languages; user preferences and quiet hours; scheduling; delivery status
  • NFR: 10M users, 100M notifications/day; OTPs and security alerts in < 5 s, marketing within hours; no duplicates; survive provider outages
  • Out of scope: the campaign-design UI

2. Estimates

  • Average: 100M ÷ 86,400 ≈ 1,200/s
  • Peak: a campaign to all 10M users in 15 min ≈ 11k/s on top
  • Storage: 100M × 1 KB ≈ 100 GB/day; keep 30 days hot ≈ 3 TB
  • Provider limits: if an SMS account allows e.g. 100 msg/s, 1M SMS takes ~2.8 hours. Queues absorb it

5. High-level design

6. Deep dives

Priority

  • Separate queues and worker pools per priority. Don't rely on "priority" fields inside one queue.
  • Reserve provider capacity for high priority (e.g. 30% of the SMS rate).
  • Time-sensitive items get a TTL: an OTP that is 10 minutes late is useless, so drop it.

Retries, DLQ, idempotency

  • Retry transient errors (timeouts, 429, 5xx) with exponential backoff + jitter. Don't retry hard bounces.
  • DLQ after max attempts; replay after the fix.
  • Dedupe at two levels: the API's Idempotency-Key, and (notificationId, channel) before calling the provider.

Provider rate limits and failover

  • A token bucket per provider account in each worker (or a shared Redis bucket).
  • Circuit breaker per provider; on open, switch SMS to the backup provider.
  • Respect the provider's 429 and Retry-After.

Templates and preferences

  • Versioned templates per channel and locale; render in the router, not in the caller.
  • Categories: transactional/security (can't fully opt out) vs marketing (opt-in, must honour unsubscribe under spam laws such as Australia's Spam Act 2003).
  • Quiet hours use the user's time zone.

Why did my OTP arrive 40 minutes late? Because it was stuck behind a marketing campaign. 📵

A good notification platform avoids that:

🚦 Separate queues per channel AND per priority

🪣 Rate-limit yourself to each provider's limit (they will throttle you anyway)

One platform, many teams, zero "sorry for the spam" emails.

  • v1: reverse time order.
  • v2: score = f(recency, affinity with author, engagement, content type).
  • Rank a candidate set (a few hundred) at read time, then cache the ranked page briefly.

Caching in Redis

  • Feed = sorted set of post IDs only; post bodies are cached separately and shared by everyone.
  • Trim to the newest ~800 entries; older pages fall back to pull.
  • Inactive users get no fan-out; rebuild their feed on first visit.

Cursor pagination

  • Cursor = last seen (score, post_id), encoded opaque.
  • Offsets break when new posts arrive (you see duplicates or skip items).
  • Same idea as continuation tokens in Cosmos DB.

7. Bottlenecks & scaling

  • Fan-out volume: async workers on a partitioned stream (Kafka / Event Hubs keyed by author); batch Redis writes with pipelining.
  • Celebrity problem: the hybrid threshold; also skip followers inactive for 30+ days.
  • Hot posts: post bodies and counts in a replicated cache; like counters aggregated async.
  • Unfollow / delete: filter at read time (cheap) and clean up feeds lazily.
  • Say push vs pull vs hybrid, then the celebrity threshold. That's the core of the answer.
  • Feeds store IDs; posts are hydrated from a shared cache.
  • Cursor pagination, never offsets, for a feed that changes while you scroll.

public async Task FanOutAsync(Post post, CancellationToken ct)
{
    if (await users.GetFollowerCountAsync(post.AuthorId, ct) > CelebrityThreshold)
        return;                                         // celebrities: readers pull instead

    double score = post.CreatedAt.ToUnixTimeMilliseconds();
    await foreach (long[] followers in follows.GetActiveFollowerPagesAsync(post.AuthorId, pageSize: 1_000, ct))
    {
        var batch = redis.CreateBatch();                // one round trip per 1,000 followers
        var writes = new List<Task>(followers.Length * 2);
        foreach (var f in followers)
        {
            writes.Add(batch.SortedSetAddAsync($"feed:{f}", post.Id, score));
            writes.Add(batch.SortedSetRemoveRangeByRankAsync($"feed:{f}", 0, -801));  // keep newest 800
        }
        batch.Execute();
        await Task.WhenAll(writes);
    }
}

Why can't you just "push every post to every follower"? Because of one person with 50 million followers. ⭐

📥 Fan-out on read: cheap writes, but slow feeds

🔀 Hybrid: push for normal users, pull for celebrities, merge at read time

🧠 Store only post IDs in Redis, hydrate the posts from a shared cache

👉 Use cursors, not page numbers, or users see duplicates as new posts arrive

19.6 Video streaming platform (YouTube / Netflix-style) Added

"Design YouTube or Netflix: creators upload videos, and millions watch them on any device without buffering." The work is a one-off processing pipeline per upload, then a huge read path that the CDN must carry.

1. Requirements

  • F: upload large files (resumable), process into streamable formats, watch on phone/TV/web at the right quality, search, view counts, live streams
  • NFR: 100M daily viewers, 500k uploads/day (avg 6 min); playback starts < 2 s; rebuffering < 1% of watch time; new uploads playable within minutes; 99.95% playback availability, worldwide
  • Out of scope: ads, comments, creator payouts; recommendations in one line

2. Estimates

  • Uploads: 500k ÷ 86,400 ≈ 6/s; 500k × 6 min = 3M minutes/day (≈ 35 hours of video every minute)
  • Ladder size: 5 rungs (0.4 + 0.8 + 1.4 + 2.8 + 5 Mbps) ≈ 10.5 Mbps × 60 s ÷ 8 ≈ 80 MB per video minute
  • Storage: 3M × 80 MB = 240 TB/day ≈ 88 PB/year, plus the originals. Storage tiers are not optional
  • Encoding: 3M min × 5 rungs = 15M rung-minutes/day. If one vCPU does ~1 min per min (very rough), ÷ 1,440 ≈ 10,000 vCPUs busy all day
  • Egress at peak: 5M watching at once × 3 Mbps = 15 Tbps. At a 95% CDN hit ratio the origin still serves 750 Gbps; each 1% of misses = 150 Gbps
  • Read:write: 100M × 40 min watched vs 3M min uploaded ≈ 1,300 : 1

5. High-level design

6. Deep dives

Resumable direct upload

  • Never stream gigabytes through your API servers. Hand out a short-lived, write-only URL for one blob.
  • Block blobs: upload blocks in parallel, then commit the list. After a drop, ask which blocks arrived and send the rest.
  • Treat the upload as untrusted until probed and scanned.

Transcoding pipeline

  • Split at keyframes, encode each segment × rung in parallel, then stitch. A 10-min video = 150 segments × 5 rungs = 750 small jobs: minutes, not an hour.
  • Same GOP length on every rung, so the player can switch at any segment boundary.
  • Jobs are idempotent per (video, segment, rung), so retries and Spot evictions are safe.

Adaptive bitrate (ABR)

  • HLS (.m3u8, Apple) and MPEG-DASH (.mpd): a manifest plus small segments over plain HTTP.
  • CMAF (fragmented MP4): one set of segments serves both, so you store and cache them once.
  • The player, not the server, picks the rung for each next segment from measured throughput and buffer level.

CDN and cache hit ratio

  • Segments never change: cache them with a long max-age. Live manifests get a TTL of a second or two.
  • Hit ratio is the key metric: at 15 Tbps, each 1% of misses is 150 Gbps on the origin.
  • Origin shield (tiered cache) collapses misses; pre-warm before a big premiere.

Protecting content

  • Tokenised URLs: the play API signs a manifest URL that expires in minutes. Stops hotlinking.
  • Premium content adds DRM: encrypt once (CENC), then a licence per device: Widevine (Chrome, Android), FairPlay (Apple), PlayReady (Windows, many TVs).
  • The licence server checks the entitlement, not the CDN.

Metadata, search, views

  • Metadata in SQL / Cosmos DB; a search index fed from change events. Captions make speech searchable.
  • Views: INCR in Redis, flush to the DB every minute; unique viewers with HyperLogLog (05 probabilistic). Counts lag a little by design.
  • Recommendations: offline candidate generation + online ranking on watch history.

Live streaming (short version)

  • Ingest: the broadcaster pushes RTMP or SRT to the nearest ingest point.
  • Transcode in real time: you can't split the future, so each live channel needs reserved encoder capacity.
  • Low-latency HLS: small partial segments (a few hundred ms), blocking playlist reload, preload hints.
  • Latency: classic HLS with 6 s segments is often 10–30 s behind; LL-HLS gets to a few seconds. Sub-second (auctions, calls) needs WebRTC, which costs more to fan out.
  • Record the stream and publish it as VOD afterwards.

Cost: where the money goes

  • Egress is the big bill. Hit ratio, better codecs for devices that support them, and CDN contracts matter more than compute.
  • Storage tiers: hot for new and popular videos, cool / cold for the long tail, archive for originals (180-day minimum, hours to rehydrate).
  • Per-title encoding: build the ladder per video. Netflix (2015) streamed a simple cartoon at 1080p for 1,540 kbps, where its fixed ladder gave 480p at 1,750 kbps.
  • Encode the top rungs lazily, once a video actually gets views.

[Function(nameof(TranscodeVideo))]
public static async Task<string> TranscodeVideo(
    [OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var videoId = ctx.GetInput<string>()!;
    var segments = await ctx.CallActivityAsync<string[]>(nameof(Split), videoId);

    string[] ladder = ["1080p", "720p", "480p", "360p", "240p"];
    var encodes = from s in segments
                  from r in ladder
                  select ctx.CallActivityAsync<string>(nameof(Encode), new Job(s, r));
    string[] outputs = await Task.WhenAll(encodes);  // fan in: 10 min = 750 tasks

    return await ctx.CallActivityAsync<string>(nameof(Package), outputs);
}

[Function(nameof(Encode))]
public static async Task<string> Encode([ActivityTrigger] Job job)
{
    var output = Path.ChangeExtension(job.Segment, $".{job.Rung}.mp4");
    await FFMpegArguments.FromFileInput(job.Segment)
        .OutputToFile(output, true, o => o
            .WithVideoCodec(VideoCodec.LibX264)
            .WithVideoBitrate(Ladder.Kbps[job.Rung])
            .WithCustomArgument($"-vf scale=-2:{Ladder.Height[job.Rung]}"))
        .ProcessAsynchronously();
    return output;               // real code: download from / upload to Blob Storage
}

19.7 Payment ledger service Added

"Design the ledger that records every money movement for a digital wallet or bank account product." Here correctness beats speed: every cent must balance, and nothing is ever edited or lost.

1. Requirements

  • F: post transfers between accounts, show balances and statements, reverse a posting, reconcile with external settlement files
  • NFR: 10M accounts, 50M transactions/day; strong consistency; no overdraw; exactly-once effect for retries; full audit trail; multi-year retention
  • Out of scope: card authorisation, FX, the payment scheme connections themselves

2. Estimates

  • Transactions: 50M ÷ 86,400 ≈ 580/s, ~5k/s at peak (payday, sale events)
  • Entries: at least 2 per transaction = 100M/day × 200 B ≈ 20 GB/day ≈ 7 TB/year
  • Reads: balance checks ~10× writes. Read "available" from the primary (never a stale cache); serve statements from replicas

5. High-level design

6. Deep dives

Double-entry, append-only

  • Every transaction has entries that sum to zero, so money is never created or lost.
  • Never UPDATE or DELETE an entry. Fix mistakes with a reversal (new opposite entries).
  • Store amounts as integers in minor units (cents), never floating point.

Balances: stored or derived?

  • Derived (sum of entries): always correct, slow for busy accounts.
  • Stored balance updated in the same transaction: fast reads and a cheap overdraw check.
  • Common answer: store it, and a nightly job proves it equals the sum of entries.

Concurrency and idempotency

  • Conditional update WHERE available >= amount (or optimistic version check) stops two withdrawals racing.
  • Lock / update accounts in a fixed order (by ID) to avoid deadlocks.
  • Unique index on the idempotency key makes client retries safe (08 idempotency).

Across services

  • Outbox in the same transaction, then events: no "DB saved but event lost".
  • Multi-step flows (debit here, credit at another bank) use a saga with a holding/suspense account and compensations.
  • Tamper evidence: SQL ledger tables or hash-chained entries for auditors.

A duplicate idempotency key fails SaveChangesAsync with a unique-index violation: catch it and return the original result. Update the two accounts in ID order, not from/to order, to avoid deadlocks between opposite transfers.

A ledger is the one system where "eventually correct" is not good enough. 🏦

📒 Double-entry: every transaction's entries add up to zero

🚫 Append-only: never edit an entry, post a reversal instead

🔢 Integers in cents, never floats

🔑 Idempotency key + "WHERE balance >= amount" = no double charge, no overdraw

📤 Outbox row in the same transaction, so events are never lost

🧮 Reconcile daily against the outside world

Boring by design. That's the point.

⚡ Quick-fire Q&A

How do you start any design case study in an interview?

Clarify 2–3 core features and the key numbers (users, read:write ratio, latency, availability), do a quick estimate, then sketch the API and data model before drawing boxes. The estimate tells you whether you need caching, sharding or queues.

URL shortener: how do you avoid two links getting the same code?

Don't rely on random luck. Either encode a unique counter in base62, or hand each server a block of pre-generated keys from a key service. If you hash the URL, check for a collision and retry with a salt.

Rate limiter: what happens if Redis goes down?

Decide per endpoint. Most APIs fail open with a local in-memory limiter as a safety net. Login, OTP and payment initiation fail closed, because abuse costs more than a short outage.

Chat: how do you keep messages in order?

Give each conversation its own sequence number (Redis INCR or one stream partition per conversation). Clients sort by it and fetch any gaps. Global ordering isn't needed.

Feed: what is the celebrity problem?

With fan-out on write, one post by an account with millions of followers means millions of feed writes. The hybrid fix: push posts from normal accounts, and pull celebrity posts at read time and merge them in.

Video: why cut a video into segments at several bitrates?

Segments let you encode in parallel (minutes, not hours) and let the player switch quality at every segment boundary. The bitrate ladder gives every network a rung it can play without stalling, and small immutable segments cache well on the CDN.

Video: what is the biggest cost, and how do you cut it?

Egress (CDN bandwidth), not storage or compute. Keep the cache hit ratio high, use per-title encoding and newer codecs where devices support them, and move the long tail of rarely watched videos to cooler storage tiers.

Ledger: why store a balance if you can sum the entries?

Summing is slow for busy accounts and makes the overdraw check expensive. Store the balance, update it in the same transaction as the entries, and run a nightly check that it still equals the sum.

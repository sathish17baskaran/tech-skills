                                PaymentsDb db, CancellationToken ct) =>
{
    if (await db.Payments.AnyAsync(p => p.IdempotencyKey == key, ct))
        return Results.Ok();                                    // retry: same result, no double charge

    var payment = Payment.Create(req, key);
    db.Payments.Add(payment);
    db.Outbox.Add(OutboxMessage.From(new PaymentCompleted(payment.Id)));  // same transaction
    await db.SaveChangesAsync(ct);                              // unique index backs up the check
    return Results.Created($"/payments/{payment.Id}", payment.Id);
})
.RequireAuthorization("payments.write")
.RequireRateLimiting("per-user");

What happens when you tap "Pay" in a banking app? 💳 (a system design tour)

DNS → WAF/CDN → API gateway (JWT, rate limit) → load balancer → stateless service → cache + DB (ACID + idempotency key) → outbox → event bus → notifications, ledger, analytics.

Every arrow is a design decision: sync or async, consistency or availability, retry or fail fast.

15.2 System design interview framework Added

A repeatable 7-step structure for a 45–60 minute design discussion. Structure beats brilliance.

1. Clarify~5 min
→
2. Estimate~3 min
→
3. API~5 min
→
4. Data model~5 min
→
5. High-level design~10 min
→
6. Deep dives~15 min
→
7. Wrap-up~5 min

1. Clarify requirements

  • Functional: core use cases (pick 2–3)
  • Non-functional: scale, latency, availability, consistency, security, compliance
  • Constraints: cloud, existing systems, budget, timeline
  • Out of scope

2. Back-of-the-envelope

  • Users → requests/s (average and peak)
  • Read:write ratio
  • Storage per year, bandwidth
  • This drives the design choices

3. API design

  • Main endpoints or events
  • Request and response shapes
  • Auth, idempotency, pagination

4. Data model

  • Entities and relationships
  • SQL or NoSQL, and why
  • Partition or shard key, indexes

5. High-level design

  • Draw the boxes: client → edge → gateway → services → data → async
  • Walk through 1–2 key flows end to end

6. Deep dives

  • Bottlenecks and scaling (cache, replicas, sharding, queues)
  • Failure modes (what if X dies?)
  • Consistency, security, observability

7. Wrap-up

  • Summarise key trade-offs
  • Risks and what you'd do next
  • How you'd evolve it (v2)
  • Think aloud. Interviewers score your reasoning, not just the final picture.
  • Say the trade-off every time: "I chose X because…, at the cost of…".
  • Start simple, then scale. Don't open with Kafka + Kubernetes + 12 microservices.

Example: "Queue vs Event? A queue hands a command to one consumer. An event broadcasts a fact to many. Queues give load levelling and reliable hand-off. Events give decoupling and fan-out. I'd use a queue for 'process this payment' and an event for 'payment completed'. At my last project we used Service Bus queues for… and topics for…"

15.5 Worked example: real-time payment notification platform Added

"Design a service that notifies customers (push, SMS, email) within 5 seconds of any card or account transaction."

1. Requirements

  • F: subscribe to preferences, receive notifications, view history
  • NFR: 5M customers, p95 delivery < 5 s, 99.95% availability, at-least-once delivery with no duplicate pushes, PII protected

2. Estimates

  • 20M transactions/day ≈ 230/s average, ~1,000/s peak
  • History: 20M × 1 KB ≈ 20 GB/day → keep 90 days hot (~1.8 TB)

3. API / events

  • Consumes TransactionPosted events (from core banking via CDC)
  • PUT /customers/{id}/notification-preferences
  • GET /customers/{id}/notifications?cursor=

4. Data

  • Preferences: SQL (small, relational) + Redis cache
  • Notification history: NoSQL (Cosmos/Cassandra), partition key = customerId

5. Design

6. Deep dives

  • Duplicates: dedupe key = transactionId + channel in Redis (TTL 24 h). Consumers are idempotent.
  • Ordering: partition by accountId so a customer's events are processed in order.
  • Spikes: queues level the load. Workers auto-scale on queue depth.
  • Provider outage: circuit breaker per provider, failover SMS provider, DLQ + replay.
  • Security: mask PII in payloads (last 4 digits only), managed identities, encryption at rest and in transit.
  • Observability: trace from transactionId → delivered. SLO = % delivered within 5 s.

7. Trade-offs

Near-real-time events instead of synchronous calls from core banking (decoupled, but eventually consistent). At-least-once delivery + dedupe instead of costly exactly-once. NoSQL for history (scale) instead of SQL (ad-hoc queries go to the lakehouse instead).

processor.ProcessMessageAsync += async args =>
{
    var evt = args.Message.Body.ToObjectFromJson<TransactionPosted>()!;
    foreach (var channel in await prefs.GetChannelsAsync(evt.CustomerId, args.CancellationToken))
    {
        // Claim (transaction, channel) once for 24 h; a redelivery finds the key and skips
        bool first = await redis.StringSetAsync($"notif:{evt.TransactionId}:{channel}", 1,
                                                TimeSpan.FromHours(24), When.NotExists);
        if (first) await senders[channel].SendAsync(evt, args.CancellationToken);
    }
    await args.CompleteMessageAsync(args.Message);
};

If a send fails after the key is set, that channel is skipped on retry. Delete the key in a catch before rethrowing, or set it only after a successful send.

15.6 Design review checklist Added

Questions to run through before you present or approve a design.

Scale & performance

  • Peak load known?
  • Stateless tier?
  • Caching plan?
  • DB scaling path?

Reliability

  • SPOFs removed?
  • Timeouts, retries, circuit breakers?
  • RPO/RTO met and tested?

Security

  • AuthN/AuthZ on every call?
  • Secrets in a vault?
  • Data classified and encrypted?
  • Threat model done?

Integration

  • Right style (RT / NRT / batch)?
  • Idempotency and DLQs?
  • Contracts versioned?

Operations

  • SLOs and alerts?
  • Tracing end to end?
  • Runbooks and SOPs?
  • Safe deployment strategy?

Governance

  • ADRs for key decisions?
  • NFRs measurable?
  • Cost estimated?
  • Compliance (APRA, Privacy, PCI)?

Section 05

Caching: strategies, expiration & pitfalls

A cache keeps a copy of data somewhere faster, so you don't repeat expensive work. It's the cheapest performance win, and the easiest way to serve stale or wrong data.

5.1 Caching basics: where can you cache? Added

Cache as close to the user as you can, for as long as the data can safely be stale.

✅ Good to cache

  • Read-heavy, rarely changing data (reference data, product catalogue, config)
  • Expensive results (aggregations, third-party API calls)
  • Session data, tokens, rate-limit counters

❌ Be careful

  • Balances, stock levels, anything that must be exactly right
  • Per-user sensitive data in shared caches (PII, auth)
  • Data that changes on almost every write
  • Hit ratio = hits ÷ (hits + misses). Aim high (often >80–90%) or the cache isn't paying for itself.
  • "There are only two hard things in computer science: cache invalidation and naming things." (Phil Karlton)

5.2 Caching strategies (read & write patterns)

They answer two questions: who loads the cache on a read, and what happens to the cache on a write?

1. Cache-aside (lazy loading) ⭐ most common

  • The app manages the cache. Data is loaded only when someone asks for it.
  • ➕ Cache failure isn't fatal. Only hot data gets cached.
  • ➖ First request is slow (miss). Data can go stale.

2. Read-through

  • The cache library or provider fetches from the DB on a miss.

  • ➖ Needs a cache that supports loaders. Same first-miss cost.

3. Write-through

  • Every write goes to the cache and the DB at the same time.
  • ➕ Cache is always fresh. Reads are fast.
  • ➖ Slower writes. Caches data nobody may read.

  • ➕ Very fast writes. Absorbs spikes.

public sealed class ProductService(HybridCache cache, AppDbContext db)
{
    // Cache-aside: on a miss, the factory runs once and the result is cached
    public ValueTask<Product?> GetAsync(int id, CancellationToken ct) =>
        cache.GetOrCreateAsync($"product:{id}",
            async token => await db.Products.FindAsync([id], token),
            cancellationToken: ct);

    public async Task UpdateAsync(Product product, CancellationToken ct)
    {
        db.Products.Update(product);
        await db.SaveChangesAsync(ct);                       // 1. write the DB
        await cache.RemoveAsync($"product:{product.Id}", ct); // 2. then delete the key
    }
}

6 caching strategies every engineer should know 🧠

1️⃣ Cache-aside: app checks the cache, loads from the DB on a miss

2️⃣ Read-through: cache loads from the DB for you

3️⃣ Write-through: write cache + DB together

4️⃣ Write-behind: write cache now, DB later (fast but risky)

5️⃣ Write-around: writes skip the cache

6️⃣ Refresh-ahead: refresh hot keys before they expire

5.3 Cache expiration strategies

Expiration decides when an entry stops being valid. (Eviction decides what to throw out when memory is full.)

⏳ Absolute TTL

Expires X seconds after it's written. Simple and predictable. Example: FX rates, TTL 60 s.

🔄 Sliding expiration

The timer resets on each access. Good for sessions ("log out after 15 min idle"). Hot data may never refresh, so add an absolute cap.

🎯 Explicit / event-based invalidation

Delete or update the key when the source changes, triggered by the write path, an event or CDC. Freshest, but more moving parts.

🏷 Versioned keys

product:42:v7. Bump the version on change and old keys age out. Great for CDN assets (app.3f9a.js).

🌓 Stale-while-revalidate

Serve the stale value right away and refresh in the background. Users never wait.

🎲 TTL with jitter

TTL = 300 s ± random 30 s, so many keys don't expire at the same moment (prevents an avalanche).

  • Invalidating across instances: use pub/sub (Redis keyspace notifications) or events to clear L1 caches.

RemoveAsync / RemoveByTagAsync invalidate this server's L1 and the shared L2, but not the in-memory L1 on other servers. Keep LocalCacheExpiration short, so stale L1 copies age out quickly.

Implementation: HashMap + doubly linked list gives O(1) get and put. The map finds the entry, and the list keeps the usage order (move to front on access, drop from the tail when full). A classic interview question.

  • Redis policies: noeviction, allkeys-lru, volatile-lru, allkeys-lfu, volatile-lfu, allkeys-random, volatile-ttl. "volatile" = only keys that have a TTL.

Interview version: an O(1) LRU in C# with Dictionary + LinkedList (not thread-safe; wrap it in a Lock if it's shared):

public sealed class LruCache<TKey, TValue>(int capacity) where TKey : notnull
{
    private readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map = new();
    private readonly LinkedList<(TKey Key, TValue Value)> _list = new();

    public bool TryGet(TKey key, out TValue value)
    {
        if (_map.TryGetValue(key, out var node))
        {
            _list.Remove(node); _list.AddFirst(node);      // now most recently used
            value = node.Value.Value; return true;
        }
        value = default!; return false;
    }

    public void Put(TKey key, TValue value)
    {
        if (_map.TryGetValue(key, out var existing)) _list.Remove(existing);
        else if (_map.Count == capacity)
        {
            var lru = _list.Last!;                          // least recently used
            _list.RemoveLast(); _map.Remove(lru.Value.Key);
        }
        _map[key] = _list.AddFirst((key, value));
    }
}

5.5 Cache problems & fixes Added

The classic ways caches fail in production, and the standard fix for each.

🐘 Cache stampede (thundering herd)

A hot key expires and 10,000 requests hit the DB at once.

  • Lock or request coalescing (only one request rebuilds)
  • Stale-while-revalidate, refresh-ahead
  • Probabilistic early expiry

🕳 Cache penetration

Requests for keys that don't exist always miss and hit the DB (often an attack).

  • Cache "null" results with a short TTL
  • Bloom filter of valid keys (see 5.8)
  • Input validation, rate limiting

🏔 Cache avalanche

Many keys expire together, or the cache cluster goes down, and the DB is flooded.

  • TTL jitter
  • Highly available cache cluster, multi-level cache
  • Circuit breaker and rate limiting on the DB

🔥 Hot key

One key (a celebrity or a promotion) overloads a single cache node.

  • Local L1 cache in front
  • Replicate the key (key#1..#N)

🔀 Inconsistency

Cache and DB disagree after a race or a failed invalidation.

  • Update the DB, then delete the key
  • Delayed double delete
  • CDC-driven invalidation (Debezium → delete key)

🧳 Big keys

Huge values block a single-threaded Redis and saturate the network.

  • Split values, compress, use hashes

5.6 CDN (Content Delivery Network) Added

A worldwide network of edge servers that cache content close to users, cutting latency and load on your origin.

  • Pull CDN: the edge fetches from the origin on the first request (most common). Push CDN: you upload content ahead of time.
  • Cache static assets (JS, CSS, images, video) and public GET APIs. Dynamic or personalised content gets "acceleration" (optimised routing) but isn't cached.

5.8 Probabilistic data structures: Bloom filter, HyperLogLog, Count-Min Sketch Added

Tiny, fast structures that give an approximate answer ("probably yes", "about 1.2 million", "roughly 340 times") using a fraction of the memory an exact answer needs.

🌸 Bloom filter

"Have we seen this before?"

  • Answers "definitely not" or "probably yes"
  • No false negatives. False positives are tunable (1% needs about 10 bits per item)
  • Can't delete items

🐦 Cuckoo filter

Same question as a Bloom filter, but it supports delete and is often smaller at low error rates.

🔢 HyperLogLog (HLL)

"How many unique items?"

  • Count distinct with a fixed, tiny memory
  • Redis: 12 KB per key, about 0.81% standard error, for counts into the billions
  • Can merge (daily → monthly uniques)

📊 Count-Min Sketch

"How often has X appeared?"

  • Frequency per item in a fixed grid of counters
  • May over-count, never under-counts

🏆 Top-K

"What are the K most frequent items?" Heavy hitters in a stream: top merchants, hottest cache keys, noisiest API clients.

How a Bloom filter works

  • Start with an array of m bits, all 0, and k hash functions.
  • Add: hash the item k times and set those k bits to 1.
  • Check: hash it again. Any bit is 0? Definitely not added. All bits are 1? Probably added (other items may have set those bits).
  • More bits per item = fewer false positives. The filter fills up as you add items, so size it for the expected count.

// In memory: a small Bloom filter with double hashing
public sealed class BloomFilter(int bits, int hashes)
{
    private readonly BitArray _bits = new(bits);

    public void Add(string item) { foreach (var i in Positions(item)) _bits[i] = true; }

    public bool MightContain(string item)          // false = definitely not added
    {
        foreach (var i in Positions(item)) if (!_bits[i]) return false;
        return true;
    }

    private IEnumerable<int> Positions(string item)
    {
        ulong h = XxHash3.HashToUInt64(Encoding.UTF8.GetBytes(item));
        ulong h1 = (uint)h, h2 = h >> 32;
        for (ulong k = 0; k < (ulong)hashes; k++) yield return (int)((h1 + k * h2) % (ulong)bits);
    }
}

Size a Bloom filter for the number of items you expect. Overfill it and the false-positive rate climbs fast. Rebuild it (or use Redis's scaling filters) when the data grows.

Your cache doesn't need to know everything. Sometimes "probably" is enough 🎯

🌸 Bloom filter: "Have we seen this ID?" A "no" is always right. A "yes" means "go and check".

🔢 HyperLogLog: count unique users in 12 KB with under 1% error.

📊 Count-Min Sketch: "how often?" for millions of keys in fixed memory.

🏆 Top-K: the heavy hitters in a stream, live.

Exact answers need memory that grows with your data. These need a fixed, tiny amount. Where would a 1% error be fine in your system?

⚡ Quick-fire Q&A

Expiration vs eviction?

Expiration is time or validity based (TTL). Eviction is space based (LRU/LFU when memory is full).

Why delete instead of update the cache on write?

Two concurrent writers can update the cache in the opposite order to the DB and leave stale data. Deleting forces the next read to load the true value.

Would you cache an account balance?

Generally no, or only with a very short TTL, clearly labelled "as at" time, and never for authorising transactions. Correctness beats speed.

Can a Bloom filter give a false negative?

No. If an item was added, all its bits are 1, so the filter always says "probably yes". It can give false positives, because other items may have set the same bits. That's why a "yes" is followed by a real lookup.

How would you count unique daily users across 50 million events cheaply?

A HyperLogLog per day (Redis PFADD / PFCOUNT): 12 KB per key, about 0.81% error. Merge the daily keys (PFMERGE) for weekly or monthly uniques. Use an exact set only if the number must be exact.

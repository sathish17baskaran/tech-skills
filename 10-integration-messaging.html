Real-time, near-real-time or batch? Three questions decide it ⏱

1️⃣ Who is waiting? A human → real-time API

2️⃣ Must others react soon? → events / CDC (near-real-time)

3️⃣ Is it big, periodic, and fine by tomorrow? → batch

Most good architectures use all three for the same business process.

10.2 Integration styles & architecture approaches Added

Hohpe & Woolf's four styles (file transfer, shared DB, RPC, messaging), and how enterprises organise integration at scale.

📁 File transfer

Systems exchange files. Simple, batch, loosely coupled.

🗄 Shared database

Systems read and write the same DB. Tight coupling. Avoid it.

📞 Remote procedure call

Sync APIs (REST, SOAP, gRPC).

✉️ Messaging

Async through a broker. Decoupled and reliable.

🍝 Point-to-point

Every system connects directly to every other. n systems ⇒ up to n(n−1)/2 links. Becomes spaghetti.

🎡 Hub-and-spoke / ESB

A central bus does routing and transformation. Fewer links, but the bus can become a bottleneck and a monolith.

🧱 API-led connectivity

Three layers: System APIs (unlock core systems) → Process APIs (business logic) → Experience APIs (per channel). Built for reuse.

⚡ Event-driven / event mesh

Producers publish events. Any consumer subscribes. Most decoupled.

☁️ iPaaS

Cloud integration platform with connectors: MuleSoft, Boomi, Azure Integration Services (Logic Apps + APIM + Service Bus + Event Grid + Functions).

Command

"CreateAccount": tells one handler to act. Can be rejected.

Event

"AccountCreated": a past fact, broadcast. Can't be rejected.

Event notification vs event-carried state

A thin event says "id 42 changed, call back for details". A fat event carries all the data, so no callback is needed.

  • Queues give load levelling: the producer can burst while consumers process at their own pace.
  • Events invert dependencies: the producer doesn't know or care who listens. Add consumers without changing the producer.
  • Version event schemas carefully. Use a schema registry and backward-compatible changes.
  • Event-driven systems are eventually consistent and harder to debug, so invest in correlation IDs and tracing.

Queue vs Event: the difference in one line 📬📢

Queue = a to-do list. Each task is done by ONE worker. ("Process payment #42")

Event = a public announcement. EVERYONE interested hears it. ("Payment #42 completed")

Streaming (Kafka) = announcements recorded on tape, so you can replay them later.

10.4 Delivery guarantees & ordering Added

The three delivery guarantees, the ordering options, and what happens to messages that keep failing.

At-most-once

Fire and forget. May lose messages, never duplicates. Fine for metrics.

At-least-once ⭐ default

Retries until acknowledged. No loss, but duplicates are possible, so consumers must be idempotent.

Exactly-once

Hard end to end. In practice it's "effectively once" = at-least-once + idempotent consumer (or Kafka transactions inside Kafka).

  • Ordering: global order kills scale. Order per key instead (Kafka partition key, Service Bus sessions), e.g. per account ID.
  • Dead-letter queue (DLQ): messages that fail N times move aside for investigation and replay, so they don't block the queue.
  • Poison message: a message that always fails. Detect it with a delivery count and move it to the DLQ.
  • Peek-lock / ack: the message is only removed after successful processing.

{
    AutoCompleteMessages = false,   // peek-lock: we settle each message ourselves
    MaxConcurrentCalls = 8
});

{
    var msg = args.Message;
    var payment = msg.Body.ToObjectFromJson<PaymentDto>();
    if (payment is null)            // poison message: never retry it
    {
        await args.DeadLetterMessageAsync(msg, "InvalidBody", "Could not parse payment");
        return;
    }
    await using var scope = scopes.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    if (!await db.ProcessedMessages.AnyAsync(p => p.Id == msg.MessageId))
    {
        db.ProcessedMessages.Add(new ProcessedMessage(msg.MessageId)); // unique key
        db.Payments.Add(Payment.From(payment));
        await db.SaveChangesAsync(args.CancellationToken);  // one transaction
    }
    await args.CompleteMessageAsync(msg);  // ack only after the DB commit
};
processor.ProcessErrorAsync += args => Task.CompletedTask; // log args.Exception
await processor.StartProcessingAsync();

10.5 Back-pressure & flow control Added

When a consumer can't keep up, it pushes back on the producer. Work slows down, or is shed on purpose, instead of piling up until something falls over.

Strategies

🪣 Buffer, with a bound

A queue soaks up bursts. Always set a maximum size or age, then decide what happens when it's full.

🚦 Throttle the producer

Rate limit at the edge. Return 429 or 503 with Retry-After. Callers back off with jitter.

🗑️ Drop / shed load

Drop the oldest or newest items, sample, or reject low-priority work first. Fine for telemetry. Never for payments.

📥 Pull, don't push

The consumer asks for the next batch when it's ready (Kafka poll, prefetch count). It sets its own pace.

🎟️ Credit-based flow

The receiver grants "credits" for how much it can take: AMQP link credit, TCP and HTTP/2 flow-control windows, Reactive Streams request(n).

📈 Scale the consumers

Add competing consumers when lag grows. KEDA scales pods on queue length or Kafka lag, even down to zero.

✅ Queue-based load levelling

  • A bounded queue between a spiky producer and a steady consumer
  • The consumer runs at a safe, fixed rate
  • Alerts and autoscaling on lag

❌ Unbounded queue

  • Hides the problem until memory or storage runs out
  • Latency grows silently: messages are hours old
  • Fails later and bigger
  • Consumer lag is the key signal: Kafka offset lag, Service Bus active message count, and the age of the oldest message.
  • 429 Too Many Requests = this caller is over its limit. 503 Service Unavailable = the server is overloaded. Both can carry Retry-After.
  • Back-pressure must travel end to end. If the API keeps saying 202 Accepted while the queue explodes, you've only moved the problem.
  • Every buffer needs a bound and a "when full" rule: block, drop or reject.
  • Choose per message type: block or reject for payments (never drop), drop or sample for metrics and logs.
  • Alert and autoscale on the age of the oldest message, not just the count.

// Bounded channel: when 100 items are waiting, the producer has to wait
var channel = Channel.CreateBounded<Payment>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait,   // back-pressure, nothing is dropped
    SingleWriter = true
});

// Producer: WriteAsync only completes when there is room
async Task ProduceAsync(IAsyncEnumerable<Payment> incoming, CancellationToken ct)
{
    await foreach (var p in incoming.WithCancellation(ct))
        await channel.Writer.WriteAsync(p, ct);  // slows to the consumers' pace
    channel.Writer.Complete();
}

// Consumers: 4 workers drain the channel at their own pace
var workers = Enumerable.Range(0, 4).Select(_ => Task.Run(async () =>
{
    await foreach (var p in channel.Reader.ReadAllAsync(ct))
        await ProcessAsync(p, ct);
}));
await Task.WhenAll(workers);

A channel lives in memory, so it's lost on restart. Use it to protect one process. Business messages that must survive belong in a durable broker (Service Bus, Kafka).

A queue doesn't fix a slow consumer. It just delays the outage 🧯

🪣 Bound every buffer. "Unbounded" means it fails later, and bigger.

🚦 Push back: block the writer, or return 429/503 with Retry-After.

🗑️ Shed what's cheap to lose (telemetry). Never shed payments.

📥 Let consumers pull at their own pace (prefetch, credits).

📈 Watch consumer lag and the age of the oldest message, and autoscale on them.

Back-pressure isn't a failure. It's your system being honest about its capacity.

10.6 Messaging & Enterprise Integration Patterns Added

A shared vocabulary for designing message flows (from Enterprise Integration Patterns, Hohpe & Woolf).

Competing consumers

Many workers read one queue to scale processing.

Request-reply

Send on a request queue, reply on a reply queue, matched by correlation ID.

Content-based router

Route by message content (e.g. AU vs NZ payments).

Message filter

Drop messages a consumer doesn't care about.

Splitter / Aggregator

Split a batch into items. Aggregate results back together.

Scatter-gather

Ask many (e.g. FX quotes), collect and pick the best.

Message translator / canonical model

Map to a shared format so N systems don't need N² mappings.

Claim check

Store the big payload in blob storage and send only a reference.

Idempotent receiver

Deduplicate by message ID.

Transactional outbox ⭐

Write business data + an "outbox" row in one DB transaction. A relay publishes the outbox to the broker. No lost or phantom events.

Queue-based load levelling

A queue between a spiky producer and a steady consumer.

Priority queue

Urgent messages get processed first.

// 2. Relay: publish unsent rows to the broker, then mark them sent
public sealed class OutboxRelay(IServiceScopeFactory scopes, ServiceBusSender sender)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(2));
        while (await timer.WaitForNextTickAsync(ct))
        {
            await using var scope = scopes.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var batch = await db.Outbox.Where(m => m.SentAt == null)
                .OrderBy(m => m.CreatedAt).Take(100).ToListAsync(ct);
            foreach (var m in batch)
            {
                await sender.SendMessageAsync(new ServiceBusMessage(m.Payload)
                    { MessageId = m.Id.ToString(), Subject = m.Type }, ct);
                m.SentAt = DateTime.UtcNow;
            }
            await db.SaveChangesAsync(ct);
        }
    }
}

The relay can crash after sending but before saving SentAt, so a message may go out twice. Reuse the outbox id as the MessageId and keep consumers idempotent.

⚡ Quick-fire Q&A

Service Bus or Event Hubs?

Service Bus for enterprise messaging (commands, transactions, sessions, DLQ, ordered workflows). Event Hubs for high-throughput event streaming and telemetry with replay.

How do you guarantee an event is published when the DB commits?

Transactional outbox, or CDC on the outbox table. Never "write the DB, then publish" as two separate steps.

How do you handle duplicates with at-least-once delivery?

Idempotent consumers: deduplicate by message ID or business key, use upserts, and use version checks.

What is back-pressure, and how do you apply it?

The consumer signals that it is full, so the producer slows down instead of overwhelming it. Use bounded queues with a clear "when full" rule (block, drop or reject), rate limits that return 429/503 with Retry-After, pull-based or credit-based consumption, and autoscaling on consumer lag.

Why is an unbounded queue dangerous?

It hides overload. The queue grows until memory or storage runs out, and latency climbs silently because messages wait for hours. A bound turns a hidden, late failure into an early, visible signal you can act on.

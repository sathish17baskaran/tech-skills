2.2 TCP vs UDP Added

TCP is a reliable, ordered phone call. UDP is fire-and-forget postcards: fast, but some may get lost.

TCPUDP
ConnectionHandshake firstNone
ReliabilityRetransmits lost packets, keeps orderNo guarantee
Speed / overheadHigherLower
Used byHTTP/1.1, HTTP/2, DB connections, SFTP, AMQPDNS, video/voice, gaming, QUIC (HTTP/3)
  • TCP head-of-line blocking: one lost packet holds up everything behind it.
  • QUIC builds reliability on top of UDP, per stream, so one lost packet doesn't block the other streams.
.NET 10 How to implement it
Library / APIPackageUse it for
TcpListener / TcpClientbuilt-in System.Net.SocketsReliable, ordered byte streams (custom protocols, legacy host links)
UdpClientbuilt-in System.Net.SocketsFire-and-forget datagrams (metrics, discovery, streaming)
Socketbuilt-in System.Net.SocketsLow-level control when the helpers above are not enough
QuicListener / QuicConnectionbuilt-in System.Net.QuicQUIC: reliable streams over UDP, the base of HTTP/3. Needs msquic (built into Windows 11 / Server 2022; a package on Linux)
Pipelinesbuilt-in System.IO.PipelinesParse a TCP stream into messages without buffer juggling
// TCP: connect first, then a reliable ordered stream
using var tcp = new TcpClient();
await tcp.ConnectAsync("core-banking.internal", 9000, ct);
await using var stream = tcp.GetStream();
await stream.WriteAsync("PING\n"u8.ToArray(), ct);

// UDP: no connection, no delivery guarantee
using var udp = new UdpClient();
await udp.SendAsync("payments.count:1|c"u8.ToArray(), "statsd.internal", 8125, ct);

TCP is a stream, not messages: one ReadAsync can return half a message or two. Add framing (length prefix or delimiter), or let System.IO.Pipelines help.

2.3 HTTP/1.1 vs HTTP/2 vs HTTP/3 Added

Same HTTP meaning (methods, status codes, headers), faster ways of sending it.

HTTP/1.1 (1997)

  • Text-based
  • Keep-alive connections
  • One request at a time per connection, so browsers open about 6 connections
  • Head-of-line blocking

HTTP/2 (2015)

  • Binary framing
  • Multiplexing: many streams on one TCP connection
  • Header compression (HPACK)
  • gRPC runs on it
  • Still blocks at the TCP level

HTTP/3 (2022)

  • Runs on QUIC over UDP
  • TLS 1.3 built in, faster setup (1-RTT, 0-RTT on resume)
  • No TCP head-of-line blocking
  • Connection survives a network change (Wi-Fi → 4G)
  • HTTPS = HTTP + TLS. In production, always use TLS 1.2 or later (prefer 1.3).
  • CDNs and gateways often speak HTTP/2 or 3 to clients and HTTP/1.1 to backends.
.NET 10 How to implement it
Library / APIPackageUse it for
Kestrelbuilt-in HttpProtocols.Http1AndHttp2AndHttp3Serve HTTP/1.1, 2 and 3 on one endpoint (HTTP/3 needs TLS)
HttpClientbuilt-in DefaultRequestVersion / DefaultVersionPolicyAsk for HTTP/2 or 3 and choose whether to fall back
IHttpClientFactoryMicrosoft.Extensions.Http (included in ASP.NET Core)Named/typed clients with pooled, recycled handlers. The standard way to call HTTP APIs
SocketsHttpHandlerbuilt-in System.Net.HttpConnection pooling settings: PooledConnectionLifetime, MaxConnectionsPerServer, EnableMultipleHttp2Connections
builder.WebHost.ConfigureKestrel(k =>
    k.ListenAnyIP(5001, listen =>
    {
        listen.Protocols = HttpProtocols.Http1AndHttp2AndHttp3;
        listen.UseHttps();                      // HTTP/2 and HTTP/3 in browsers need TLS
    }));

builder.Services.AddHttpClient("payments", c =>
{
    c.BaseAddress = new Uri("https://payments.internal/");
    c.DefaultRequestVersion = HttpVersion.Version30;
    c.DefaultVersionPolicy = HttpVersionPolicy.RequestVersionOrLower; // fall back to 2 or 1.1
});

2.4 DNS Added

The internet's phone book: it turns api.bank.com into an IP address.

Record types

  • A / AAAA: name → IPv4 / IPv6
  • CNAME: alias to another name
  • MX: mail server
  • TXT: verification, SPF/DKIM
  • NS: which servers are authoritative

Points to remember

  • TTL controls caching. Lower it before a migration or cutover.
  • DNS can load balance and route by geography (Azure Traffic Manager, Route 53).
  • DNS failover is slow because clients cache old answers.
  • Private DNS zones resolve private endpoints inside a VNet.

var lookup = new LookupClient();                      // DnsClient
var result = await lookup.QueryAsync("bank.com", QueryType.MX);
foreach (var mx in result.Answers.MxRecords())
    Console.WriteLine($"{mx.Preference} {mx.Exchange}");

// A singleton HttpClient that still follows DNS changes
var http = new HttpClient(new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2)
});

A static HttpClient without PooledConnectionLifetime keeps its old connections and never sees a DNS change. IHttpClientFactory avoids this by recycling handlers.

REST, gRPC, GraphQL, WebSocket, SSE, Webhooks, AMQP, Kafka, SFTP… which one? 🤔

Ask one question: what interaction do I need?

✅ Answer now → REST / gRPC ✅ Live push → WebSocket / SSE ✅ "Something happened" → Webhook / Event ✅ Decouple → Queue ✅ Bulk → File

The protocol follows the interaction, not the hype.

2.6 Short polling vs Long polling vs SSE vs WebSocket vs Webhook Added

Five ways to get updates from a server, from "keep asking" to "the server calls you".

  • Webhooks need HMAC signature checks, retries with backoff, idempotent handlers and fast 2xx replies (do the work async).
  • WebSockets and SSE need sticky connections or a pub/sub backplane (for example Redis or Azure SignalR) to scale out.
  • SSE reconnects automatically, which makes it great for streaming LLM tokens.
.NET 10 How to implement it
TechniqueLibrary / APINotes
Pollingbuilt-in minimal API endpoint + ETag / 304Plain GET. Return 304 when nothing changed
SSE (server)built-in TypedResults.ServerSentEvents (new in ASP.NET Core 10)Stream any IAsyncEnumerable<T> as text/event-stream
SSE (client)System.Net.ServerSentEvents (SseParser)Read an SSE stream from .NET (e.g. LLM token streams)
WebSocketbuilt-in app.UseWebSockets(), ClientWebSocketRaw two-way messages; you handle reconnects and scale-out
SignalRbuilt-in ASP.NET Core SignalR; scale-out: Microsoft.Azure.SignalR or Microsoft.AspNetCore.SignalR.StackExchangeRedisPicks WebSocket / SSE / long polling for you, adds groups and reconnects
Webhookbuilt-in HMACSHA256 + CryptographicOperations.FixedTimeEqualsVerify the signature before trusting the payload
// SSE: push price updates to the browser
app.MapGet("/prices", (PriceFeed feed, CancellationToken ct) =>
    TypedResults.ServerSentEvents(feed.StreamAsync(ct), eventType: "price"));

// Webhook: verify the HMAC signature, reply 2xx fast, process later
app.MapPost("/webhooks/payments", async (HttpRequest req, IConfiguration cfg, Channel<byte[]> inbox) =>
{
    using var ms = new MemoryStream();
    await req.Body.CopyToAsync(ms);
    var body = ms.ToArray();
    var expected = HMACSHA256.HashData(Encoding.UTF8.GetBytes(cfg["Webhook:Secret"]!), body);
    var given = Convert.FromHexString(req.Headers["X-Signature"].ToString());
    if (!CryptographicOperations.FixedTimeEquals(expected, given))
        return Results.Unauthorized();
    await inbox.Writer.WriteAsync(body);         // a worker does the real work
    return Results.Ok();
});

Compare signatures with FixedTimeEquals, never == or SequenceEqual, which leak timing. Also check a timestamp header to block replays.

⚡ Quick-fire Q&A

Why is gRPC faster than REST/JSON?

Binary Protobuf payloads, HTTP/2 multiplexing, persistent connections and generated client stubs.

WebSocket or SSE for a live dashboard?

SSE if data only flows server → client (simpler, plain HTTP, auto-reconnect). WebSocket if the client also sends frequent messages.

How do you secure webhooks?

HTTPS only, an HMAC signature with a shared secret (or mTLS), timestamps to block replays, an allowlist, idempotent processing and a quick 2xx acknowledgement.

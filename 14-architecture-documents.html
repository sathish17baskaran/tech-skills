Section 14

Architecture documents & governance

What each document is for, when it's written, who reads it and what goes in it: ACD, AIA, SO, HLD, LLD, ADR, SOP, plus NFRs, C4, threat models and runbooks.

Acronyms like ACD, AIA and SO mean different things in different organisations. The expansions below are the common ones. Check your organisation's templates and adjust the names, keeping the purpose.

14.2 ACD: Architecture Concept / Context Document

The earliest architecture artefact. It frames the problem, the business context and the target concept before detailed design begins.

Typical contents

  • Problem statement and business drivers
  • Scope (in / out), stakeholders
  • Current state (as-is) context diagram
  • Target state concept (to-be), capabilities affected
  • Options considered (at a high level), recommended direction
  • Key assumptions, constraints, dependencies, risks
  • Alignment with enterprise strategy and principles
  • Keep it short and visual. Its job is to get agreement on direction.
  • One context diagram is worth pages of text (C4 level 1).
  • Capture options early so later reviews don't reopen them.

14.3 AIA: Architecture Impact Assessment

Assesses how a change affects existing systems, data, integrations, security, operations and cost, and decides how much governance it needs.

Typical contents

  • Change summary and classification (minor / major / strategic)
  • Impacted applications, interfaces, data stores
  • Data impact: classification, PII, residency, retention
  • Security and privacy impact, regulatory obligations
  • Infrastructure, operational and support impact
  • Technology standards compliance, technical debt created or removed
  • Risk rating → governance path (fast-track vs full review board)
  • In AI programmes, "AIA" can also mean AI Impact Assessment: fairness, transparency, data use, human oversight, model risk.
  • Be honest about impacts. Surprises found later cost much more.

14.4 SO: Solution Outline / Solution Overview

A high-level description of the proposed solution: its components, integrations, key decisions and how it meets requirements. The bridge between concept and detailed design.

Typical contents

  • Requirements summary: functional + non-functional
  • Solution architecture diagram (C4 level 2: containers)
  • Components and responsibilities, build vs buy
  • Integration overview: interfaces, patterns (sync/async/batch), protocols
  • Data flows and data model overview
  • Security architecture (IAM, encryption, network zones)
  • Deployment and environments, HA/DR approach
  • Options analysis, key decisions (link ADRs), risks, costs
  • Explain how each NFR is met (availability target → zone redundancy + DR region).
  • Show trade-offs. Reviewers trust designs that admit their weaknesses.

14.5 HLD: High-Level Design Added

The system-level design: major components, interactions, technology choices and deployment topology. In many organisations, the SO and HLD are one document.

  • Architecture diagrams (logical + physical), component interactions, sequence diagrams for key flows
  • Technology stack, hosting, networking, environments
  • Cross-cutting concerns: logging, monitoring, security, resilience

14.6 LLD: Low-Level Design

The developer-ready blueprint. It describes each component in enough detail to build and test without guessing.

Typical contents

  • Component internals: modules, classes, responsibilities
  • API contracts (OpenAPI), message schemas, event definitions
  • Database schema: tables, keys, indexes, partitioning
  • Detailed sequence diagrams, including error paths
  • Validation rules, mappings and transformations, business rules
  • Error handling, retries, idempotency, timeouts
  • Configuration, feature flags, secrets references
  • Logging and metrics events, alert definitions
  • Infrastructure specifics: SKUs, network rules, IaC modules
  • Test approach: unit, integration, performance
  • Keep it close to the code (in the repo, as Markdown + diagrams-as-code) so it doesn't drift.
  • Generated artefacts (OpenAPI, schema DDL) are better than hand-copied tables.

14.7 ADR: Architecture Decision Record

A short, immutable note recording one significant decision: its context, the options, the choice and the consequences. Your future self will thank you.

ADR-017: Use Azure Service Bus for payment event integration
Status:   Accepted (2026-03-04)   [Proposed | Accepted | Deprecated | Superseded by ADR-0xx]
Context:  Payment service must notify 4 downstream systems; needs ordering per account,
          DLQ, at-least-once delivery, enterprise support; volumes ~200 msg/s peak.
Options:  1) Service Bus topics  2) Event Hubs/Kafka  3) Direct REST calls
Decision: Service Bus topics with sessions (session = account ID) + transactional outbox.
Consequences:
   + ordering per account, DLQ, managed service, fits volumes
   − not built for replaying history (use Event Hubs later if analytics streaming needed)
   − consumers must be idempotent
  • Write ADRs for decisions that are hard to reverse or often questioned.
  • Never edit an accepted ADR. Supersede it with a new one, so the history is kept.
  • Store them in the repo (/docs/adr). Tools: adr-tools, Log4brains.
  • Formats: Michael Nygard's (above), MADR.

"Why on earth did we choose this?" 🤔 Every team, 18 months later.

Fix: Architecture Decision Records. One page per big decision: Context → Options → Decision → Consequences.

Never edit an old one, supersede it. Your architecture gets a memory.

14.8 SOP: Standard Operating Procedure

Step-by-step instructions for a routine operational task, so it's done the same way every time, by anyone trained.

Typical structure

  1. Purpose and scope
  2. Roles and responsibilities (RACI)
  3. Prerequisites, access and tools needed
  4. Numbered steps with expected results (and screenshots or commands)
  5. Verification / success criteria
  6. Rollback or exception handling
  7. Escalation contacts
  8. Version, owner, review date

Examples

  • Certificate renewal and rotation
  • Monthly DR failover test
  • Onboarding a new API consumer in APIM
  • Replaying messages from a DLQ
  • Patching and release deployment

14.9 Non-Functional Requirements (NFRs) Added

Functional requirements say what the system does. NFRs say how well it does it. Make them measurable.

Performance

p95 < 300 ms at 500 TPS

Availability

99.95% monthly, excluding planned maintenance

Scalability

Handle 3× peak with auto-scale

Recoverability

RPO 5 min, RTO 1 h

Security

OAuth2, TLS 1.2+, encryption at rest, OWASP

Compliance

Privacy Act, APRA CPS 234/230, PCI DSS

Observability

Traces, dashboards, alerts on SLOs

Maintainability & cost

Deployment frequency, cost per transaction

❌ "The system should be fast." ✅ "95% of balance enquiries respond within 300 ms at 1,000 req/s."

14.12 Runbook vs SOP vs Playbook Added

SOP

Routine, planned tasks. The "how we always do X" procedure.

Runbook

Specific operational or incident steps for one system or alert ("if the DLQ depth is over 100, do…"). Often automated.

Playbook

Broader response strategy across teams for a scenario (cyber incident, regional outage, major release).

14.13 TOGAF & Well-Architected frameworks Added

Two widely used frameworks: TOGAF for running enterprise architecture, and Well-Architected for reviewing cloud workloads.

TOGAF ADM (enterprise architecture method)

Preliminary → A. Vision → B. Business → C. Information Systems (data + application) → D. Technology → E. Opportunities & Solutions → F. Migration Planning → G. Implementation Governance → H. Change Management, with Requirements Management at the centre.

Well-Architected (Azure / AWS)

Azure pillars: Reliability, Security, Cost Optimisation, Operational Excellence, Performance Efficiency. AWS adds Sustainability. Use them as a design review checklist.

⚡ Quick-fire Q&A

HLD vs LLD?

HLD covers what components exist and how they interact (system view). LLD covers how each component is built: contracts, schemas, logic, error handling (developer view).

When do you write an ADR?

For any decision that is significant, costly to reverse, or likely to be questioned later: technology choice, integration pattern, data store, security approach.

What makes a good architecture document?

Clear purpose and audience, diagrams first, measurable NFRs, explicit trade-offs and decisions, linked ADRs, owner and version, and kept up to date.

24.1 Design principles Added

A handful of rules of thumb that keep code easy to change. Each one is good in moderation and harmful when pushed to the extreme.

🔁 DRY

Don't repeat yourself. Each piece of knowledge (a rule, a formula) lives in one place.

💡 KISS

Keep it simple. The simplest design that meets today's needs wins.

✋ YAGNI

You aren't gonna need it. Don't build for a future that may never come.

🧱 Separation of concerns

UI, business rules and data access live in different places, so each can change alone.

🧲 High cohesion, low coupling

Things that change together stay together. Modules know as little about each other as possible.

🧩 Composition over inheritance

Build behaviour by combining small objects, not by deep class trees.

🗣 Law of Demeter

Talk to your direct friends only. Avoid a.B.C.D.Do() train wrecks.

📣 Tell, don't ask

Tell an object what to do. Don't pull its data out and decide for it.

🚨 Fail fast

Reject bad input at the edge, loudly, before it spreads and corrupts data.

When each one is over-applied

PrincipleOver-applied looks likeBalance
DRYTwo services share a "common" helper and can no longer change aloneDuplicate code is fine if the reasons differ. Rule of three
KISSNo error handling, no tests, "simple" copy-pasteSimple ≠ easy. Simple means few moving parts
YAGNIIgnoring known needs: security, audit, idempotencySkip speculative features, not known non-functionals
Separation of concernsSeven layers to save one rowSeparate by change rate. Vertical slices are fine
Low couplingInterfaces and events everywhere; nobody can follow a callDecouple across boundaries, not inside one module
CompositionTwenty tiny objects for one ruleShallow inheritance (one level) is still fine
Law of DemeterWrapper methods that just forward every callApplies to behaviour, not to DTOs and fluent APIs
Fail fastOne bad record stops a 1-million-row batchFail fast on requests; isolate and park bad records in batches
  • All principles serve one goal: cheap, safe change. Use that to settle arguments.
  • DRY is about knowledge, not text. Two identical lines with different reasons to change are not duplication.
  • YAGNI never applies to security, observability or data integrity.

{
    public void Pay(decimal total, string reference)
    {

Every design principle is right… until you push it too far ⚖️

🔁 DRY: share knowledge, not text. A "common" library can couple two teams forever

✋ YAGNI: skip speculative features, never skip security or audit

🧲 Low coupling: decouple across boundaries, not inside one small module

📣 Tell, don't ask: order.Pay(total) beats order.Customer.Wallet.Balance -= total

🚨 Fail fast on requests, but park bad rows in a batch instead of stopping it

24.2 SOLID Added

Five object-oriented principles that keep classes small, swappable and testable, so a change in one place doesn't ripple everywhere.

PrincipleSmell it preventsIn ASP.NET Core
S · Single responsibilityGod classes, merge conflicts, huge test setupsThin endpoints; one handler or service per use case
O · Open/closedGrowing switch statements, risky editsRegister many IFeeRules; inject IEnumerable<T> or keyed services
L · Liskov substitutionNotSupportedException overrides, type checksAny registered implementation must work in every consumer
I · Interface segregationFat interfaces, fake methods in mocksIOptions<T> per feature, small service interfaces
D · Dependency inversionnew of infrastructure inside business codeConstructor injection via the built-in container

S · Single responsibility

// ❌ data, fees, PDF and email together
class StatementService
{
    void Load() { }   void CalcFees() { }
    void ToPdf() { }  void Email() { }
}
// ✅ one reason to change each
class FeeCalculator { }
class StatementPdf { }
class StatementMailer { }

O · Open/closed

// ❌ edit for every new rail
decimal Fee(Payment p) => p.Rail switch
{
    "NPP" => 0m, "BPAY" => 0.50m,
    _ => throw new NotSupportedException()
};
// ✅ add a class, edit nothing
interface IFeeRule { decimal Fee(Payment p); }
sealed class NppFee : IFeeRule
{
    public decimal Fee(Payment p) => 0m;
}

L · Liskov substitution

// ❌ subtype breaks the base promise
class ReadOnlyAccount : Account
{
    public override void Deposit(decimal a)
        => throw new NotSupportedException();
}
// ✅ split the abstraction
interface IReadableAccount
{
    decimal Balance { get; }
}
interface IDepositable { void Deposit(decimal a); }

I · Interface segregation

// ❌ report job must "implement" Pay()
interface IAccountService
{
    Account Get(int id); void Pay(Payment p);
    void Close(int id);  Report Export();
}
// ✅ small, client-shaped interfaces
interface IAccountReader { Account Get(int id); }
interface IPaymentSender { void Pay(Payment p); }

D · Dependency inversion

// ❌ business code news up the detail
class TransferService
{
    readonly SqlAccountRepo repo = new();
}
// ✅ depend on an abstraction
class TransferService(IAccountRepository repo)
{
}
  • DIP is the principle; DI (the container) is just one way to apply it.
  • Add interfaces at seams: I/O, external systems, things you swap or fake in tests. Not for every class.
  • LSP violations show up as type checks and NotSupportedException. Fix the hierarchy, not the callers.

SOLID in one line each, with the smell it kills 🧱

🅢 Single responsibility: one reason to change. Kills god classes

🅞 Open/closed: add a class, don't edit the switch. Kills risky edits

🅛 Liskov: subtypes keep promises. Kills NotSupportedException overrides

🅘 Interface segregation: small interfaces. Kills fake methods in mocks

🅓 Dependency inversion: depend on abstractions. Kills new SqlRepo() in business code

24.3 Creational patterns Added

Patterns that control how objects get created, so callers don't depend on concrete classes or complex setup steps.

PatternProblem it solvesWhere .NET uses it
Factory methodCaller shouldn't pick the concrete classILoggerFactory.CreateLogger, IHttpClientFactory.CreateClient
Abstract factoryCreate a family of related objects that must matchDbProviderFactory (connection + command + parameter)
BuilderMany optional steps; readable setupWebApplication.CreateBuilder, StringBuilder, UriBuilder, DbContextOptionsBuilder
SingletonExactly one shared instanceAddSingleton, ArrayPool<T>.Shared, TimeProvider.System
PrototypeCopy an existing object, then tweak itRecord with expressions

❌ Static singleton

  • static readonly Instance: hidden global dependency.
  • Can't swap it in tests; state leaks between tests.
  • Hand-rolled thread safety (Lazy<T>, locks).

✅ DI singleton

  • AddSingleton<IFxCache, FxCache>(): visible in the constructor.
  • Swap for a fake in tests; one line to change lifetime.
  • The container handles thread-safe creation and disposal.
  • In ASP.NET Core the DI container is your main factory. Write your own factory only when the choice depends on runtime data.
  • A singleton must be thread-safe and must never hold a scoped service (e.g. a DbContext).
  • Builders shine for test data: new PaymentBuilder().WithAmount(250m).Build().

24.4 Structural patterns Added

Patterns that wrap or combine objects to change an interface, add behaviour, or hide complexity, without editing the original class.

🔌 Adapter

Makes an existing class fit the interface you need. Wrap a vendor SDK behind IFraudScorer.

🎁 Decorator

Same interface, extra behaviour: caching, logging, retries. Stack them like layers.

🏛 Facade

One simple entry point over many subsystems. OnboardingService calls KYC, core banking and email.

🛡 Proxy

Same interface, controls access: lazy loading, remote calls, permission checks.

🌳 Composite

Treat a tree of items like one item. A product bundle's price is the sum of its parts.

PatternInterfaceUse when.NET example
AdapterChanges itThird-party or legacy API doesn't match yoursStreamReader over a Stream
DecoratorSame, adds behaviourCross-cutting concerns without touching the classDelegatingHandler, GZipStream, DelegatingChatClient
ProxySame, controls accessLazy load, remote call, security checkEF Core lazy-loading proxies, gRPC client, DispatchProxy
FacadeNew, simplerCallers need one task, not ten subsystemsFile.ReadAllTextAsync, HttpClient
CompositeSame for leaf and groupTree structures: menus, bundles, rulesCompositeFileProvider, configuration sections
  • Decorator vs proxy: same shape. A decorator adds behaviour; a proxy controls access to the real object.
  • Put an adapter around every vendor SDK. Swapping vendors then touches one class (an anti-corruption layer in DDD terms).
  • Order matters when stacking decorators: cache outside retry, or retry outside cache? Decide on purpose.

🎁 Decorator: same interface, adds behaviour (cache, log, retry)

🛡 Proxy: same interface, controls access (lazy load, remote, auth)

🔌 Adapter: changes the interface to fit yours (wrap that vendor SDK!)

🏛 Facade: one simple door into many subsystems

24.6 Anti-patterns & code smells Added

Warning signs that code will be hard and risky to change, and the small, safe refactoring moves that fix them.

SmellSymptomRefactoring move
God class3,000-line PaymentService, 20 dependenciesExtract class per responsibility
Anaemic domain modelEntities are bags of setters; rules live in servicesMove behaviour into the entity (account.Debit())
Primitive obsessionstring bsb, string acct, decimal amt everywhereValue objects: Bsb, Money
Shotgun surgeryOne change edits ten filesMove related code together (cohesion)
Feature envyA method uses another class's data more than its ownMove method to that class

🩸 Anaemic model: a smell when…

  • Rules (overdraft limits, state changes) are spread across services.
  • Anyone can set Balance directly and break invariants.

👍 Anaemic model: fine when…

  • It's CRUD, reporting or a simple data API with no real rules.
  • Records are DTOs crossing a boundary, not domain objects.
  • Refactor in small, behaviour-preserving steps with tests green after each one.
  • Value objects kill primitive obsession and make invalid data unrepresentable.
  • Over-engineering is a smell too. Patterns should remove pain you already have.

24.7 Clean code & code review Added

Code is read far more often than it is written. Clean code makes intent obvious, and a good review checks more than style.

🏷 Naming

Names say intent and domain: settlementDate, not d2. Booleans read as questions: isOverdrawn.

✂️ Small functions

One level of abstraction per method. If you need "and" to describe it, split it.

🚪 Guard clauses

Return or throw early. Keep the happy path un-nested at the left margin.

🧊 Immutability

record, init, required. C# 14's field keyword lets a property validate without a manual backing field.

❔ Nullability

Turn on nullable reference types. Treat warnings as errors in new projects.

💬 Comments explain why

The code says what. Comments say why: a regulation, a workaround, a trade-off.

Errors: exceptions or Result?

SituationUseWhy
Expected business outcome (insufficient funds, invalid BSB)Result typePart of the normal flow; caller must handle it; cheap
Bug or broken invariantExceptionShould never happen; fail fast and loudly
Infrastructure failure (DB down, timeout)Exception (+ retry policy)Let resilience and the global handler deal with it
At the HTTP edgeProblemDetails (RFC 9457)One consistent error shape for every client
  • Automate style (formatters, analyzers) so humans review design, correctness and risk.
  • Use a Result type for expected outcomes, exceptions for the unexpected. Don't use exceptions for control flow.
  • Small PRs (under ~400 lines) get better reviews than big ones.

public ErrorOr<Transfer> Create(Account from, decimal amount)
{
    if (amount <= 0) return Error.Validation("amount", "Amount must be positive");
    if (from.Balance < amount) return Error.Conflict("funds", "Insufficient funds");
    return new Transfer(Guid.NewGuid(), from.Id, amount);   // happy path last
}

    svc.Create(accounts.Get(req.FromId), req.Amount).Match<IResult>(
        t => TypedResults.Created($"/transfers/{t.Id}", t),
        errors => TypedResults.Problem(errors[0].Description,

My 7-point code review checklist ✅

🎯 Correctness: edge cases like empty, zero, duplicates, time zones

🔐 Security: authorisation on every endpoint, no PII in logs

⚡ Performance: no N+1 queries, no sync-over-async

📖 Readability: names that explain intent, small methods

🧪 Tests and 🔭 observability: would we know if it broke in prod?

A 5-step approach for live coding

  • Say the brute force and its Big-O first, then improve. Silence is the most common reason people fail.
  • "Longest substring", "k largest", "shortest path" are cues: sliding window, heap, BFS.
  • Use the built-in collections confidently: PriorityQueue, HashSet, Queue.

// Sliding window: longest substring with no repeated chars. O(n)
static int LongestDistinct(string s)
{
    var last = new Dictionary<char, int>();
    int best = 0, start = 0;
    for (int i = 0; i < s.Length; i++)
    {
        if (last.TryGetValue(s[i], out int seen) && seen >= start) start = seen + 1;
        last[s[i]] = i;
        best = Math.Max(best, i - start + 1);
    }
    return best;
}

// Top-k largest: keep a min-heap of size k. O(n log k)
static int[] TopK(int[] nums, int k)
{
    var heap = new PriorityQueue<int, int>();
    foreach (int n in nums)
    {
        heap.Enqueue(n, n);
        if (heap.Count > k) heap.Dequeue();   // drop the smallest
    }
    return [.. heap.UnorderedItems.Select(x => x.Element)];
}

Live coding is pattern matching, not genius 🧠

🪟 "Longest substring that…" → sliding window, O(n)

🗂 "Duplicates / two sum / anagram" → hash map, O(n)

🏔 "k largest / k closest" → heap, O(n log k)

🌊 "Shortest path in a grid" → BFS, O(V + E)

🗣 And always: clarify → examples → brute force → optimise → test edge cases

⚡ Quick-fire Q&A

When is duplicated code acceptable?

When the two copies have different reasons to change. DRY is about knowledge, not text. Merging two "similar" fee calculations owned by different products couples them forever. A common rule: wait for the third copy before abstracting.

What's the difference between dependency inversion and dependency injection?

Dependency inversion is the principle: high-level code depends on abstractions, not on details. Dependency injection is a technique: dependencies are passed in (usually via the constructor) instead of created inside. The ASP.NET Core container automates DI, which makes DIP easy to apply.

Why is a DI singleton better than a static singleton?

It's visible in the constructor, easy to replace with a fake in tests, and its lifetime is one line of config. The container also handles thread-safe creation and disposal. A static singleton is a hidden global that leaks state between tests.

Decorator, proxy or adapter?

Adapter changes the interface to the one you need. Decorator keeps the interface and adds behaviour (caching, logging). Proxy keeps the interface and controls access to the real object (lazy loading, remote calls, permission checks).

Should a new .NET project use MediatR?

Check the licence first: MediatR v13+ needs a paid commercial licence unless you qualify for the free Community tier (under US$5M revenue, plus other criteria). Free options are the source-generated Mediator (MIT), Wolverine, or simply injecting handler classes directly, which is often the clearest choice.

Is an anaemic domain model always bad?

No. For CRUD, reporting or thin data APIs with few rules, plain data classes plus services are simpler. It becomes a problem when real business rules and invariants (overdraft limits, state changes) are scattered across services and anyone can set fields directly.

Exceptions or the Result pattern?

Use a Result type (e.g. ErrorOr, FluentResults) for expected business outcomes like insufficient funds. Use exceptions for bugs, broken invariants and infrastructure failures, and turn them into ProblemDetails in a global handler. Don't use exceptions for normal control flow.

Why can a Dictionary lookup be slower than O(1)?

O(1) is the average case. Many keys with the same hash code (a poor GetHashCode) fall into the same bucket and lookups degrade towards O(n). Mutating a key after inserting it can make the entry impossible to find. Use immutable keys such as records or strings.

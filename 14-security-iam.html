14.2 IAM: Identity & Access Management

The policies, processes and tools that make sure the right identities get the right access to the right resources, at the right time, for the right reasons.

User / app
→login
Identity provider (IdP)Entra ID · Okta · Ping
→token (claims, roles)
Applications / APIs / cloudenforce access

👤 Identities

  • Human: employees, customers (CIAM), partners (B2B)
  • Non-human: service principals, managed identities, workload identities, API clients

🔑 Authentication

  • Passwords + MFA
  • Passwordless: FIDO2, passkeys, Windows Hello
  • Certificates, federated tokens
  • Conditional access (device, location, risk)

🛂 Authorization models

  • RBAC: roles (Reader, Contributor)
  • ABAC: attributes (dept=Finance AND region=AU)
  • PBAC: central policy engine (OPA)
  • ReBAC: relationships (owner of the doc)
  • ACLs on resources

🔄 Lifecycle & governance (IGA)

  • Joiner-Mover-Leaver process
  • Automated provisioning (SCIM)
  • Access reviews / recertification
  • Segregation of duties (SoD)

👑 Privileged access (PAM / PIM)

  • Just-in-time elevation with approval
  • Time-bound admin roles
  • Session recording, break-glass accounts
  • CyberArk, Entra PIM

🌐 Federation & SSO

  • One login, many apps
  • Trust between organisations' IdPs
  • SAML, OIDC, WS-Fed
  • Principle of least privilege: give the minimum access, for the minimum time.
  • Prefer managed identities over secrets for service-to-service access in the cloud.
  • Leavers must be de-provisioned immediately. Orphaned accounts are a top audit finding.
  • Cloud IAM scope hierarchy (Azure): Management group → Subscription → Resource group → Resource. Assign roles at the lowest scope that works.

IAM in 4 words: right access, right time ⏰🔑

👤 Who are you? (authentication + MFA)

🛂 What can you do? (RBAC / ABAC)

⏳ For how long? (just-in-time, access reviews)

🚪 What happens when you leave? (automated de-provisioning)

Most breaches aren't hacks. They're logins with too much access.

14.4 Symmetric vs Asymmetric keys

Symmetric: one shared secret key locks and unlocks. Asymmetric: a key pair. What the public key locks, only the private key can unlock.

Symmetric

Cipher text
↓ decrypt with the SAME 🔑 K
Plain text
Asymmetric
Plain text
↓ encrypt with Bob's 🔓 public key
Cipher text
↓ decrypt with Bob's 🔐 private key
Plain text
SymmetricAsymmetric
Keys1 shared secretPublic + private pair
SpeedVery fast (bulk data)Slow (100–1000× slower)
Key sizesAES-128 / AES-256RSA 2048–4096, ECC P-256 (≈ RSA 3072)
AlgorithmsAES-GCM, ChaCha20-Poly1305RSA, ECDSA, ECDH, Ed25519
Big problemHow to share the key safely?Performance. Need to trust that a public key really is theirs (PKI)
Used forData at rest, bulk encryption, TLS session dataKey exchange, digital signatures, certificates, JWT RS256

Digital signatures: asymmetric in reverse

Encrypt → use the RECEIVER's public key  |  Sign → use the SENDER's private key

Hybrid encryption (how TLS actually works)

Asymmetric (ECDHE)securely agree a session key
→
Symmetric (AES-GCM)encrypt all the data fast
  • Best of both: asymmetric to exchange keys and sign, symmetric to encrypt the data.
  • JWT: HS256 = symmetric (shared secret). RS256 / ES256 = asymmetric (the API only needs the public key, which is better).
  • Post-quantum crypto (e.g. ML-KEM) is coming, and that work is mostly about asymmetric algorithms.

// Symmetric: AES-256-GCM
byte[] key   = RandomNumberGenerator.GetBytes(32);
byte[] nonce = RandomNumberGenerator.GetBytes(12);   // unique per message, never reuse with the same key
byte[] plain = "pay 100 to Bob"u8.ToArray();
byte[] cipher = new byte[plain.Length];
byte[] tag    = new byte[16];
using (var aes = new AesGcm(key, tagSizeInBytes: 16))
    aes.Encrypt(nonce, plain, cipher, tag);          // store nonce + cipher + tag
// aes.Decrypt(nonce, cipher, tag, output) throws if anything was changed

// Asymmetric: sign with the private key, verify with the public key
using var ecdsa = ECDsa.Create(ECCurve.NamedCurves.nistP256);
byte[] signature = ecdsa.SignData(plain, HashAlgorithmName.SHA256);
bool valid = ecdsa.VerifyData(plain, signature, HashAlgorithmName.SHA256);

Symmetric vs Asymmetric encryption, using padlocks 🔐

Symmetric: you and I have copies of the same key. Fast, but how do I get you the key safely?

Asymmetric: I hand out open padlocks (public key). Anyone can lock a box for me, but only my private key opens it.

TLS uses both: padlocks to swap a shared key, then the shared key for speed.

TLS encrypts data in transit and proves the server's identity with a certificate. mTLS makes the client prove its identity too.

builder.WebHost.ConfigureKestrel(k => k.ConfigureHttpsDefaults(h =>
{
    h.SslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13;

{

    handler.SslOptions.ClientCertificates = new X509CertificateCollection { cert };
    return handler;
});

Behind a load balancer or App Service, TLS often ends before your app. The client cert then arrives in a header; use AddCertificateForwarding to read it.

14.7 Secrets & key management Added

Never hard-code secrets. Store them in a vault, access them by identity, rotate them, and audit every use.

  • HSM: tamper-resistant hardware. Keys never leave it (FIPS 140-2/3).
  • Customer-managed keys (CMK / BYOK) for regulatory control.

14.8 Zero Trust Added

"Never trust, always verify." Being inside the network doesn't make you trusted.

1. Verify explicitly

Authenticate and authorise every request using identity, device health, location and risk.

2. Least privilege

Just-in-time and just-enough access. Time-bound.

3. Assume breach

Micro-segmentation, encrypt everything, monitor, limit the blast radius.

14.10 DevSecOps & software supply chain security Added

Build security checks into every step of delivery, and be able to prove that what runs in production is exactly what you built, from parts you trust.

The scanners and what they find

🔍 SAST

Static analysis of your source code for bugs like SQL injection or weak crypto. Runs on every PR. Tools: CodeQL, SonarQube, .NET analyzers.

🎯 DAST

Attacks the running app from the outside, like a hacker would. Finds config and runtime issues. Tools: OWASP ZAP, Burp Suite.

📦 SCA (dependency scanning)

Known CVEs and licence problems in third-party packages, including transitive ones. Tools: NuGet Audit, Dependabot, Snyk.

🔑 Secret scanning

Keys, tokens and passwords in code and git history. Use push protection to stop them before they land. Tools: GitHub secret scanning, Gitleaks.

🏗️ IaC scanning

Misconfigured Terraform, Bicep or Kubernetes YAML: public storage, open ports, no encryption. Tools: Checkov, Trivy.

🐳 Container image scanning

CVEs in the base image and OS packages. Rebuild often on a small, patched base image. Tools: Trivy, Grype, Defender for Cloud.

⚡ Quick-fire Q&A

Why not encrypt passwords instead of hashing?

Encrypted passwords can be decrypted if the key leaks. Slow, salted hashes (bcrypt/Argon2) can't be reversed, and they make brute force expensive.

RBAC vs ABAC?

RBAC grants access by role and is simple, but leads to role explosion. ABAC uses attributes and context, which is flexible and fine-grained but more complex to govern.

What does a managed identity solve?

It removes credentials from code and config. The cloud platform issues and rotates tokens for the workload automatically.

What is an SBOM, and why does it matter?

A software bill of materials: a machine-readable list of every component and version in a build, in SPDX or CycloneDX format. When a new vulnerability is published, you can search your SBOMs and know in minutes which systems are affected. Regulators and customers increasingly ask for it too.

What is dependency confusion, and how do you prevent it in .NET?

An attacker publishes a public package with the same name as an internal one, and the build pulls the public version. In .NET, use NuGet package source mapping so internal prefixes only resolve from the internal feed, commit lock files and restore with --locked-mode in CI, and reserve your package ID prefix on nuget.org.

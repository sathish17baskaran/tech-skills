6.1 SQL vs NoSQL Added

SQL: tables, fixed schema, joins, strong transactions. NoSQL: flexible models built for scale and specific access patterns.

Relational (SQL)

SQL Server, PostgreSQL, Oracle, Azure SQL

Transactions, ledgers, complex queries

Key-value

Redis, DynamoDB

Sessions, cache, lookups by key

Document

MongoDB, Cosmos DB

JSON aggregates, catalogues, profiles

Wide-column

Cassandra, HBase

Massive writes, time-ordered data

Graph

Neo4j, Cosmos Gremlin

Relationships, fraud rings, recommendations

Time-series / Vector / Search

InfluxDB · pgvector, Pinecone · Elasticsearch

Metrics · AI similarity · full-text

  • Model NoSQL around access patterns (queries first). Model SQL around entities (normalise first).

6.3 Indexing Added

An index is like a book's index: it finds rows without scanning the whole table. Reads get faster, writes get slower.

  • B-tree (default): equality and range queries, sorting.
  • Hash: equality only.
  • Clustered: the table is physically sorted by this key (one per table). Non-clustered: a separate structure pointing to rows.
  • Composite (customer_id, created_at): follows the leftmost-prefix rule. It helps a filter on customer_id, but not a filter on created_at alone.
  • Covering index: contains every column the query needs, so the table is never touched.
  • Index columns used in WHERE, JOIN and ORDER BY. Check the execution plan. Too many indexes slow down inserts and updates.

6.4 Unique ID generation Added

Every record needs an ID that is unique everywhere, ideally sortable by time and friendly to indexes, and created without a central bottleneck.

🔢 Auto-increment

IDENTITY / SERIAL: 1, 2, 3…

  • Simple, small, perfectly ordered
  • ✗ One database hands them out, so it doesn't work across shards or regions without coordination
  • ✗ Leaks business data: order 10,500 today and 10,900 tomorrow = 400 orders a day. IDs are guessable

🎲 UUID v4

128 bits, random.

  • Create anywhere, no coordination, unguessable
  • ✗ Random order: each insert lands on a random index page, so page splits and fragmentation

⏱ UUID v7

128 bits: 48-bit Unix millisecond timestamp first, then random bits (RFC 9562, 2024).

  • Create anywhere, and new IDs sort after old ones
  • Inserts go to the end of the index, like auto-increment

🔤 ULID

128 bits: 48-bit timestamp + 80 random bits, written as 26 Base32 characters (01JA2X…).

  • Sortable as text, URL-friendly
  • A community spec, not an RFC. UUID v7 is now the standard choice

❄ Snowflake ID

64 bits: timestamp + machine ID + sequence (from Twitter, 2010).

  • Fits a BIGINT: half the size of a UUID
  • Each node generates its own, roughly time-ordered
  • ✗ Needs unique machine IDs and sane clocks

🗂 Sequences & Hi/Lo

A DB sequence hands out numbers independent of any table. Hi/Lo: the app reserves a block (e.g. 10 IDs) per round trip and assigns them in memory.

  • Fewer round trips; IDs known before insert
  • Gaps when a block isn't used up (that's fine)

Snowflake ID: 64 bits

Choosing a clustered index key

  • A good clustered key is narrow, unique, never changes and always increases. BIGINT (identity, sequence or Snowflake) is the classic choice.
  • Need IDs created outside the database (offline clients, many services, merge later)? Use UUID v7 or Snowflake, not v4.
  • Keep the internal key and the public ID separate if counts or order are sensitive: expose a random or opaque ID in URLs.
  • Random UUID v4 as a clustered key = page splits and fragmentation. Time-ordered IDs append to the end of the index.
  • Distributed systems and sharding (see 6.7) need IDs that don't depend on one database: UUID v7 or Snowflake.
  • Sequential IDs in public URLs let anyone count your customers or guess other records. Always check authorisation anyway.

Your primary key choice can quietly slow down every insert 🐢

🔢 Auto-increment: fast and ordered, but one DB owns it, and it tells competitors how many orders you take

🎲 UUID v4: unique anywhere, but random, so inserts land all over the index

⏱ UUID v7: unique anywhere AND time-ordered. Inserts append to the end

❄ Snowflake: 64 bits = timestamp + machine + sequence. Fits a BIGINT

Rule of thumb: time-ordered IDs for keys, opaque IDs in public URLs. What does your team use?

6.5 Search systems Added

A search engine builds an inverted index (word → documents) so it can find and rank matching text in milliseconds, with stemming, typo tolerance and facets.

✗ Why not LIKE '%card%'?

  • A leading wildcard can't use a B-tree index, so every row is scanned
  • No ranking: which result is most relevant?
  • No stemming ("payments" doesn't match "payment"), no synonyms, no typo tolerance
  • No facets ("Cards (12) · Loans (4)")

✓ What a search engine adds

  • Inverted index: like the index at the back of a book
  • Analysers: lowercase, split, remove stop words, stem
  • Relevance scoring (BM25)
  • Fuzzy matching, autocomplete, highlighting, facets, filters

Key ideas

🔤 Analysers

Character filters → tokenizer → token filters (lowercase, stop words, stemming, synonyms, accent folding). Use the same analyser at index and query time, or matches fail.

📐 Relevance: TF-IDF → BM25

TF-IDF: a term counts more if it's frequent in this document and rare across all documents. BM25 improves it: repeated words give diminishing returns, and long documents don't win just by being long. BM25 is the default in Lucene, Elasticsearch, OpenSearch and Azure AI Search.

🔎 Typo tolerance

Fuzzy queries match within an edit distance ("platnum" → "platinum"). N-grams and edge n-grams power autocomplete.

🧮 Facets & filters

Counts per category, price band or date, computed alongside the results. Filters narrow results without changing the score.

Keeping the index fresh

6.6 Geospatial indexing Added

A spatial index turns 2D locations into something a database can search fast, so "find the nearest ATMs within 1 km" doesn't scan every row.

Why it's needed: a normal index on latitude helps one range, but "near me" is a 2D question. Spatial indexes split the map into cells or boxes so only nearby candidates are checked.

🔠 Geohash

Interleaves latitude and longitude bits into a short string. Shared prefix = same area: r3gx2 is a cell in Sydney's CBD. Longer = smaller cell. Works with a normal B-tree (LIKE 'r3gx2%').

🌳 Quadtree

Split the map into 4 squares; keep splitting any square with too many points. Dense cities get small cells, the outback gets big ones. Popular for in-memory indexes.

📦 R-tree

Groups nearby shapes into bounding rectangles inside a balanced tree. Handles points, lines and polygons. Used by PostGIS (GiST indexes), SQLite and Oracle.

⬡ S2 and H3

S2 (Google) maps the sphere onto cube faces with 64-bit cell IDs. H3 (Uber) uses hexagons, so all neighbours are about the same distance away. Good for aggregating ("rides per hexagon").

  • Use geography (round earth, metres) for real-world distances; SRID 4326 = WGS 84, the GPS coordinate system.
  • GeoJSON, NetTopologySuite and Redis take longitude first, then latitude. Mixing them up puts Sydney in Antarctica.

6.7 Database scaling

Climb the ladder: try the cheap, simple steps first, and only move to sharding when you must.

6.8 Storage types: block vs file vs object Added

Block storage is a raw disk for one machine, file storage is a shared folder, and object storage is a huge, cheap bucket of files you reach over HTTP.

💽 Block

A virtual hard disk split into fixed-size blocks. Attached to one VM, which formats it with a file system.

  • Lowest latency, high IOPS, in-place updates
  • Databases, VM OS disks, anything needing a "real" disk
  • Azure Managed Disks, AWS EBS

📁 File

Folders and files shared over the network (SMB or NFS) by many machines at once.

  • Familiar paths, file locking, shared access
  • Lift-and-shift apps, shared config, team drives, content for several servers
  • Azure Files, Azure NetApp Files, AWS EFS, FSx

🪣 Object

A flat namespace of objects (data + metadata + key), read and written through an HTTP API.

  • Practically unlimited scale, cheapest per GB, very high durability
  • Documents, images, backups, logs, data lakes, static websites
  • Azure Blob Storage, Amazon S3

Object storage tiers and lifecycle

  • Cool, Cold and Archive have minimum storage periods (30, 90 and 180 days). Moving or deleting earlier costs an early-deletion fee.
  • AWS S3 has the same idea: Standard, Standard-IA, Glacier Instant / Flexible Retrieval and Glacier Deep Archive, plus Intelligent-Tiering, which moves objects for you.

🔒 Immutability (WORM)

Write once, read many. Nobody, not even an admin, can change or delete the object until the retention period ends.

  • Azure: immutable blob storage with time-based retention or legal hold
  • AWS: S3 Object Lock (governance or compliance mode)
  • Used for records retention and ransomware-proof backups (see 6.9)

🔗 SAS and presigned URLs

A short-lived URL that lets a client read or upload one object directly, without passing the file through your API.

  • Azure: SAS; prefer a user delegation SAS (signed with Entra ID, not the account key)
  • AWS: S3 presigned URL
  • Keep expiry short (minutes), scope to one object and the least permission

Block vs file vs object storage, in one minute 🗄

💽 Block: a raw disk for one machine. Fast. Databases live here

📁 File: a shared folder over SMB/NFS. Many servers, one path

🪣 Object: a bucket over HTTP. Massive scale, cheapest per GB. Documents, backups, data lakes

💸 Then let lifecycle rules move old objects Hot → Cool → Cold → Archive, and lock records with WORM

Bonus: never stream big files through your API. Give the client a 15-minute SAS or presigned URL.

6.9 Database backup strategies

Backups are insurance against deletion, corruption, ransomware and disasters. A backup only counts if you've tested the restore.

Full: every backup = everything. Incremental: Δ since the LAST backup of any type. Differential: Δ since the LAST FULL, so it grows every day.

TypeBackup timeStorageRestore speed
FullSlowestMostFastest (one set)
IncrementalFastestLeastSlowest (whole chain)
DifferentialMedium (grows)MediumMedium (full + latest diff)

📜 Transaction log backups → PITR

Log backups every few minutes let you restore to any point in time, like "just before the bad DELETE at 10:42".

📸 Snapshots

Storage- or volume-level copies, near-instant. Make sure they're application-consistent.

🔤 Logical vs physical

Logical = SQL dump (portable, slow). Physical = data files (fast, same engine).

🔥 Hot vs cold

Hot = DB online during backup. Cold = DB offline (consistent, but downtime).

🌏 Geo-redundant

Copy to another region (GRS) for disaster recovery.

🔒 Immutable / air-gapped

WORM storage that can't be deleted or encrypted by ransomware.

  • 3-2-1 rule: 3 copies of data, on 2 different media, 1 offsite. Modern version: 3-2-1-1-0 = plus 1 immutable or air-gapped copy, and 0 errors after restore verification.
  • Retention: GFS (Grandfather-Father-Son), e.g. daily for 30 days, monthly for 12 months, yearly for 7 years (compliance).
  • Encrypt backups. Protect and back up the keys separately.
  • Backup frequency sets your RPO. Restore speed sets your RTO.

Your backup strategy is only as good as your last successful restore 🔁

✅ 3 copies ✅ 2 media ✅ 1 offsite ✅ 1 immutable ✅ 0 errors on restore test

That's the 3-2-1-1-0 rule. Ransomware goes after your backups first. Make one copy it can't touch.

6.10 Data migration strategies

Moving data from a source to a target system without losing it, corrupting it, or stopping the business.

Lifecycle

→

→
3. Extract & transformcleanse

→
5. Validate & reconcilecounts, checksums

6. Cutovergo / no-go
→

💥 Big bang

Move everything in one cutover window (e.g. a weekend).

  • ➕ Simple. No dual running.
  • ➖ High risk, downtime, hard to roll back.

💧 Trickle / phased

Migrate in waves (by product, region or customer segment) while old and new run side by side.

  • ➕ Low risk, learn as you go.
  • ➖ Longer, needs sync between systems.

🔄 CDC replication

Bulk-load history, then stream ongoing changes (CDC) until cutover. Near-zero downtime.

🪞 Parallel run

Run old and new together and compare outputs before switching. Common in banking.

✍️ Dual write

The app writes to both systems. Risky (partial failures). Prefer CDC or outbox.

🧩 Expand → migrate → contract

For schema changes: add the new column, backfill, switch reads, then drop the old one. Zero downtime.

Cloud migration: the 7 Rs

Rehost (lift & shift) · Relocate · Replatform (lift & reshape) · Refactor (re-architect) · Repurchase (move to SaaS) · Retire · Retain

  • Data quality issues show up during migration. Profile early and agree on cleansing rules with the business.
  • Reconcile: row counts, sums of amounts, hash totals, sample record checks.
  • Always have a rollback plan and a rehearsed cutover runbook.

⚡ Quick-fire Q&A

Read replicas or sharding?

Replicas scale reads, and they're simple. Sharding scales writes and storage, and it's complex. Most systems are read-heavy, so start with replicas and caching.

How do you achieve near-zero-downtime migration?

Bulk-copy history, keep it in sync with CDC, validate continuously, then do a short cutover (switch the connection or DNS) with a rollback path.

Incremental vs differential restore?

Incremental needs the full backup plus every incremental since. Differential needs the full backup plus only the latest differential.

UUID v4 or UUID v7 for a primary key?

UUID v7. Both can be created anywhere, but v7 starts with a millisecond timestamp, so new keys append to the end of the index instead of landing on random pages. On SQL Server, mind its GUID sort order (EF Core's sequential GUIDs or BIGINT may suit better).

How would you add product search to an app backed by SQL?

Keep SQL as the source of truth and push changes (CDC or outbox events) into a search engine such as Azure AI Search or Elasticsearch. It gives an inverted index, BM25 ranking, fuzzy matching and facets, about a second behind the database. LIKE '%x%' scans the table and can't rank.

Design "find the nearest 5 ATMs".

Store locations with a spatial index (PostGIS, SQL Server geography, Redis GEO or a geohash column). Coarse filter: your geohash cell plus its 8 neighbours (or ST_DWithin). Then compute exact distances on the candidates, sort and take 5. Cache results per cell because ATM locations rarely change.

When would you choose block, file or object storage?

Block for a database or VM disk (low latency, one machine). File for a folder shared by several servers or a legacy app that needs paths. Object for documents, images, backups and data lakes at scale, with lifecycle tiers and SAS / presigned URLs for direct client access.

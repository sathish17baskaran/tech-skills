22.1 Flash-sale order & inventory without overselling Added

Thousands of people press "Buy" in the same second for a few thousand items. Take the stock in one atomic step, answer fast, and do the slow work (payment, order rows) in the background.

Problem statement

A retailer (or a bank's rewards store) sells 5,000 limited items at 12:00 sharp. About 200,000 shoppers arrive in the first minute. A normal "read stock, then write stock" flow sells the same last item to many people, and the database melts under the spike.

Functional

  • Show remaining stock (can be a few seconds old)
  • Reserve and place an order; pay within 10 minutes
  • Limit: 2 items per customer
  • Release stock if payment fails or times out
  • A double-click or retry must not buy twice

Non-functional

  • Peak: 50,000 requests/s on "Buy" for about 2 minutes
  • Latency: reserve answer p99 < 200 ms
  • Correctness: 0 oversold items, ever
  • Availability: 99.95% during the sale window
  • Durability: no accepted order is lost

Constraints & assumptions: one Azure region; SQL Server holds the real stock and orders; Redis is available; the payment provider is external and slow (1–3 s); the sale time is known in advance, so you can pre-scale.

Solution

Key decisionTrade-off
Gate in Redis, truth in SQL. A Lua script checks and decrements stock in one atomic step in memory.Very fast, but Redis and SQL can drift, so SQL keeps a final WHERE Stock >= @qty guard and a job reconciles.
Reserve now, write later. The API answers 202 and a queue absorbs the spike.The shopper sees "pending" for a moment, and you need a timeout to release unpaid stock.
Idempotency key per checkout. Retries return the first result.One extra Redis key per order (kept 24 h).
Admission control. Rate limit or a waiting room in front of "Buy".Some shoppers wait or get 429, but the system stays up.
Pre-scale before 12:00. Set minimum replicas ahead of time.You pay for idle capacity for a few minutes; autoscale reacts too slowly for a 2-minute spike.

Steps to implement in .NET 10

  1. Set up: dotnet new webapi (minimal APIs) plus an Aspire 13 AppHost with Aspire.Hosting.Redis, Aspire.Hosting.SqlServer and Aspire.Hosting.Azure.ServiceBus, so Redis, SQL and the Service Bus emulator start locally with one command.
  2. Model: EF Core 10 (Microsoft.EntityFrameworkCore.SqlServer) with Product (Id, Stock, [Timestamp] byte[] RowVersion), Order (PK = orderId) and an outbox table. RowVersion makes admin edits (price, stock top-ups) fail with DbUpdateConcurrencyException instead of silently overwriting.
  3. Load stock into Redis before the sale: StringSetAsync("stock:{sku}", 5000) with StackExchange.Redis.
  4. Reserve endpoint: run the Lua script with IDatabase.ScriptEvaluateAsync (core trick 1). It also adds the order to a sorted set scored by its expiry time, so the sweeper can find unpaid reservations.
  5. Idempotency: require an Idempotency-Key header (an IETF draft name, widely used). Check it inside the same Lua script, so "seen before?" and "take stock" can't race.
  6. Publish OrderReserved with Azure.Messaging.ServiceBus. Set MessageId = orderId and turn on duplicate detection on the queue.
  7. Order worker: a BackgroundService with ServiceBusProcessor writes the order using the SQL guard (core trick 2), in one transaction with the outbox row.
  8. Admission control: built-in Microsoft.AspNetCore.RateLimiting (AddRateLimiter, token bucket per client, 429 + Retry-After), plus Azure Front Door WAF rate rules at the edge.
  9. Release expired reservations: a BackgroundService using new PeriodicTimer(TimeSpan.FromSeconds(15), timeProvider) reads expired entries (SortedSetRangeByScoreAsync up to "now"), returns their stock and removes them. Inject TimeProvider so tests can fake time.
  10. Deploy & observe: Azure Container Apps with min replicas raised before the sale, Azure Managed Redis, Azure.Monitor.OpenTelemetry.AspNetCore for traces and metrics (reserved, sold out, released). Run the load test a day before.

Core trick 1: atomic reserve + idempotency in one Lua script

const string ReserveLua = """
    -- KEYS: 1 stock, 2 customer count, 3 idempotency key, 4 reservations (sorted set)
    if redis.call('EXISTS', KEYS[3]) == 1 then return -2 end            -- seen before
    local qty, limit = tonumber(ARGV[1]), tonumber(ARGV[2])
    local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
    if stock < qty then return -1 end                                     -- sold out
    if tonumber(redis.call('GET', KEYS[2]) or '0') + qty > limit then return -3 end
    redis.call('DECRBY', KEYS[1], qty)
    redis.call('INCRBY', KEYS[2], qty)
    redis.call('SET', KEYS[3], ARGV[3], 'EX', 86400)                      -- remember orderId 24 h
    redis.call('ZADD', KEYS[4], ARGV[4], ARGV[3])                        -- score = expiry time
    return stock - qty
    """;

var tag = "{sku-123}";            // hash tag: all keys land on the same cluster slot
var left = (long)await db.ScriptEvaluateAsync(ReserveLua,
    [$"stock:{tag}", $"cust:{tag}:{customerId}", $"idem:{tag}:{idemKey}", $"resv:{tag}"],
    [qty, 2, orderId.ToString(), clock.GetUtcNow().AddMinutes(10).ToUnixTimeSeconds()]);
return left switch
{
    -1 => Results.Conflict("Sold out"),
    -2 => Results.Accepted($"/orders/{await db.StringGetAsync($"idem:{tag}:{idemKey}")}"),
    -3 => Results.UnprocessableEntity("Limit is 2 per customer"),
    _  => Results.Accepted($"/orders/{orderId}")
};

Never "read stock, then write stock" in two calls. Whatever store you use, the check and the decrement must be one atomic operation.

  • Check-and-decrement in one atomic step: a Redis Lua script or UPDATE ... WHERE Stock >= @qty.
  • Answer 202 fast; a queue and a worker do the slow part.
  • Idempotency key + reservation expiry turn retries and abandoned carts into non-events.
  • Prove it with a Task.WhenAll race test, not with hope.

22.2 Seat / appointment booking with temporary holds Added

Let a user hold a seat or time slot for a few minutes while they pay, block everyone else, and release it automatically if they walk away.

Problem statement

Concert tickets, flight seats and branch appointments all have the same shape: a limited set of named slots. Users need a short, exclusive hold while they fill in details or pay. Without holds, two people pay for the same seat; with holds that never expire, seats look "sold out" when they are not.

Functional

  • See free, held and booked seats/slots
  • Hold 1–6 seats for 10 minutes, all or nothing
  • Confirm (after payment) or cancel a hold
  • Holds release by themselves when time runs out
  • Show a countdown; other screens update live

Non-functional

  • Peak: 2,000 hold requests/s at a big on-sale (appointments: ~50/s)
  • Latency: hold p99 < 300 ms; seat map p95 < 100 ms
  • Correctness: zero double bookings
  • Availability: 99.9%
  • Freshness: seat map may be 2–3 s stale; hold/confirm never

Constraints & assumptions: SQL Server is the source of truth; up to 60,000 seats per event; app servers are NTP-synced (seconds of skew don't matter for a 10-minute hold); all times are stored in UTC (DateTimeOffset).

Solution

Key decisionTrade-off
Hold columns on the seat row + a conditional UPDATE. WHERE BookedBy IS NULL AND (HoldExpiresAt IS NULL OR HoldExpiresAt <= @now).One source of truth and transactional with booking; SQL row locks become the bottleneck at very big on-sales.
Lazy expiry. An expired hold counts as free in every query; no exact-time job is needed.Expired values stay in the row until a sweeper or the next hold overwrites them.
All-or-nothing multi-seat holds in one transaction.One taken seat fails the whole request; the UI must suggest alternatives.
Redis SET NX PX in front for huge on-sales (plus a waiting room).Much faster, but now two stores must agree; SQL still does the final confirm.
10-minute hold, one extension.Longer holds mean fewer failed payments but more "fake sold out" seats.

Steps to implement in .NET 10

  1. Set up: minimal API + Aspire AppHost (Aspire.Hosting.SqlServer); EF Core 10 with Microsoft.EntityFrameworkCore.SqlServer.
  2. Model: Seat (Id, EventId, HeldBy, HoldExpiresAt as DateTimeOffset?, BookedBy, [Timestamp] RowVersion), index on (EventId, Id). A Booking row per confirmed payment with a unique PaymentId.
  3. Time: register builder.Services.AddSingleton(TimeProvider.System) and never call DateTime.UtcNow directly. Tests swap in FakeTimeProvider.
  4. Hold endpoint: one ExecuteUpdateAsync inside a transaction; if fewer rows changed than seats asked for, roll back (core trick 1). Reject duplicate seat IDs and more than 6 seats up front (400).
  5. Confirm endpoint: UPDATE ... SET BookedBy = @me WHERE HeldBy = @me AND HoldExpiresAt > @now, idempotent on PaymentId. If the hold expired but the seat is still free, book it; if someone else has it, trigger an automatic refund.
  6. Seat map reads: HybridCache (Microsoft.Extensions.Caching.Hybrid) with a 2 s expiry and a tag per event; call RemoveByTagAsync after holds change.
  7. Live updates: ASP.NET Core SignalR (built-in), one group per event: push "held", "booked", "free again". Use Azure SignalR Service (Microsoft.Azure.SignalR) to scale out.
  8. Sweeper: BackgroundService with new PeriodicTimer(TimeSpan.FromSeconds(30), timeProvider) clears expired holds and pushes "free again" events.
  9. Big on-sale mode: Redis hold first with StringSetAsync(key, user, TimeSpan.FromMinutes(10), When.NotExists) (core trick 2), plus a queue-based waiting room; SQL confirm stays the final check.
  10. Deploy: App Service or Container Apps, Azure SQL (read replica for seat-map reads if needed), OpenTelemetry metrics for holds created, expired and confirmed.

Core trick 1: all-or-nothing hold with a conditional UPDATE

app.MapPost("/events/{eventId:int}/holds", async (int eventId, HoldRequest req, BookingDb db,
    TimeProvider clock, ClaimsPrincipal user, CancellationToken ct) =>
{
    var now = clock.GetUtcNow();
    var me = user.FindFirstValue(ClaimTypes.NameIdentifier)!;
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var held = await db.Seats
        .Where(s => s.EventId == eventId && req.SeatIds.Contains(s.Id) && s.BookedBy == null
                 && (s.HoldExpiresAt == null || s.HoldExpiresAt <= now))      // free or expired
        .ExecuteUpdateAsync(s => s
            .SetProperty(x => x.HeldBy, me)
            .SetProperty(x => x.HoldExpiresAt, now.AddMinutes(10)), ct);

    if (held != req.SeatIds.Length)                    // someone else got at least one seat
    {
        await tx.RollbackAsync(ct);                    // all or nothing
        return Results.Conflict("One or more seats are no longer free");
    }
    await tx.CommitAsync(ct);
    return Results.Ok(new { expiresAt = now.AddMinutes(10) });
});

22.3 Search autocomplete (typeahead) Added

Suggest the best 5–10 completions while the user types. Precompute the answers per prefix, cache hard, and send fewer requests from the client.

Problem statement

A large store or banking app has a search box: products, merchants, help articles. Every keystroke could be a request, so a naive "LIKE 'hom%'" query on the main database is slow and expensive. Users expect suggestions to appear as fast as they type.

Functional

  • Top 10 suggestions for a prefix, most popular first
  • Case- and accent-insensitive ("Café" = "cafe")
  • New trending terms show up within ~15 minutes
  • Never suggest blocked or offensive terms
  • Nice to have: typo tolerance, personal history

Non-functional

  • Traffic: 10M daily users × 5 searches × ~6 requests (after debounce) ≈ 300M/day ≈ 3,500/s, peak ~15,000/s
  • Latency: server p99 < 20 ms; end to end < 100 ms
  • Availability: 99.9% (if it fails, search still works)
  • Freshness: minutes are fine

Constraints & assumptions: ~5M distinct terms from search logs; English first; prefixes capped at 10 characters for the precomputed lists; Azure hosting with a CDN in front.

Solution

Key decisionTrade-off
Precompute top 10 per prefix (a trie flattened into one Redis sorted set per prefix).Reads are one call and already ranked; costs memory (a few GB) and a rebuild job.
Client debounce (200–300 ms) + cancel stale calls.Cuts requests several times over; adds a small delay before the first suggestion.
Cache short prefixes at the edge (60 s). One- and two-letter prefixes are the hottest.Suggestions can be up to a minute old.
Batch rebuild from logs, written to a new version and switched with one pointer key.Trending terms appear after the next batch, not instantly; readers never see half-built data.
Managed search (Azure AI Search suggester) when you need typo tolerance and filters.Less code, fuzzy matching built in; higher cost and latency than a Redis lookup.

Steps to implement in .NET 10

  1. Set up: minimal API; Redis via Aspire.StackExchange.Redis (client integration) or plain StackExchange.Redis.
  2. Log searches: send each final query as an event to Event Hubs (Azure.Messaging.EventHubs). Never log personal data in the term.
  3. Aggregate: a timer job (Azure Functions timer trigger, or a BackgroundService) counts term frequency with time decay, and drops blocked terms.
  4. Build the index: for each term and each prefix up to 10 chars, SortedSetAddAsync then trim with SortedSetRemoveRangeByRankAsync(key, 0, -11) to keep the top 10 (core trick 1). Use batching/pipelining; write to ac:v43:*, then set ac:current = v43.
  5. Normalise once, everywhere: Trim(), ToLowerInvariant(), remove accents (string.Normalize(NormalizationForm.FormD) and drop non-spacing marks). Same function in the indexer and the API.
  6. Suggest endpoint: validate 1–50 chars, read SortedSetRangeByRankAsync(key, 0, 9, Order.Descending). For prefixes longer than 10 chars, read the 10-char list and filter with StartsWith.
  7. Cache: built-in output caching (AddOutputCache, .CacheOutput(p => p.Expire(...).SetVaryByQuery("q"))) and a Cache-Control: public, max-age=60 header for the CDN (Azure Front Door).
  8. Protect: built-in rate limiter per IP; if Redis fails, return an empty list (200), not an error.
  9. Client: debounce 250 ms and cancel the previous request (AbortController in JS, a new CancellationTokenSource per keystroke in Blazor/MAUI).
  10. Optional managed option: Azure AI Search (Azure.Search.Documents) with a SearchSuggester on the index and SearchClient.AutocompleteAsync / SuggestAsync with UseFuzzyMatching = true (core trick 2).

Core trick 1: top 10 per prefix in Redis sorted sets

// Indexer: put a term into the top-10 list of each of its prefixes
async Task IndexTermAsync(IDatabase db, string version, string term, double score)
{
    var t = Normalise(term);
    for (int len = 1; len <= Math.Min(10, t.Length); len++)
    {
        var key = $"ac:{version}:{t[..len]}";
        await db.SortedSetAddAsync(key, t, score);
        await db.SortedSetRemoveRangeByRankAsync(key, 0, -11);      // keep only the top 10
    }
}

// API: one Redis call per uncached keystroke
app.MapGet("/suggest", async (string q, IConnectionMultiplexer mux) =>
{
    var norm = Normalise(q);
    if (norm.Length is 0 or > 50) return Results.BadRequest();
    var db = mux.GetDatabase();
    var version = await db.StringGetAsync("ac:current");             // switched after each rebuild
    var hits = await db.SortedSetRangeByRankAsync($"ac:{version}:{norm[..Math.Min(10, norm.Length)]}",
                                                  0, 9, Order.Descending);
    return Results.Ok(hits.Select(h => h.ToString()).Where(h => h.StartsWith(norm)));
}).CacheOutput(p => p.Expire(TimeSpan.FromSeconds(60)).SetVaryByQuery("q"));

22.4 Proximity service: find nearby ATMs, branches or drivers Added

"What is near me?" Static places (ATMs, branches) live in a spatial database; fast-moving things (drivers, couriers) live in an in-memory geo index that is updated every few seconds.

Problem statement

A banking app needs "nearest ATM or branch" with filters. A delivery or ride app needs "available drivers within 3 km", where every driver moves and reports a new location every few seconds. Scanning every row and computing distances is too slow, and moving objects create a heavy write load.

Functional

  • Nearest N ATMs/branches within a radius, with filters (deposits, open now, accessible)
  • Drivers report location every ~4 s
  • Find available drivers within 3 km, nearest first
  • Hide drivers that stopped reporting

Non-functional

  • Places: ~20k locations, 2,000 queries/s, p95 < 100 ms
  • Drivers: 200k online × 1 update / 4 s = 50,000 writes/s; 5,000 searches/s, p99 < 50 ms
  • Freshness: driver location at most ~10 s old
  • Availability: 99.95%

Constraints & assumptions: WGS84 latitude/longitude (SRID 4326); distances in metres; the customer's location is never stored or logged in full; driver history is not kept in the hot store.

Solution

Key decisionTrade-off
Two stores for two problems. Places in SQL (geography + spatial index); drivers in Redis GEO (in memory).Each fits its load (rich filters vs 50k writes/s), but you run two technologies.
Shard drivers by city/region key (drivers:syd, drivers:mel).Small sets and spread load; a rider near a boundary must query two keys.
Heartbeat key with a TTL per driver. GEO members can't expire on their own.One extra key and an MGET per search; a cleanup job removes stale members.
Client-side throttling: send only if moved > 50 m or 4 s passed.Far fewer writes; position can be ~50 m off.
Cache place searches by rounded location (e.g. 3 decimals ≈ 110 m).High hit rate in busy areas; recompute exact distances for display.

Steps to implement in .NET 10

  1. Set up: minimal API; Microsoft.EntityFrameworkCore.SqlServer.NetTopologySuite (or Npgsql.EntityFrameworkCore.PostgreSQL.NetTopologySuite for PostGIS); StackExchange.Redis.
  2. Model places: Atm with NetTopologySuite.Geometries.Point Location mapped to SQL Server geography; register with UseSqlServer(cs, x => x.UseNetTopologySuite()).
  3. Spatial index: add CREATE SPATIAL INDEX with migrationBuilder.Sql(...) in a migration (create it in SQL; don't rely on HasIndex for spatial indexes).
  4. Nearest places query: IsWithinDistance + OrderBy(Distance) + Take(10) (core trick 1). Validate lat −90..90, lon −180..180, radius capped at 50 km.
  5. Driver updates: GeoAddAsync("drivers:{city}", lon, lat, driverId) plus StringSetAsync($"hb:{driverId}", 1, TimeSpan.FromSeconds(15)).
  6. Nearby drivers: GeoSearchAsync(key, lon, lat, new GeoSearchCircle(3, GeoUnit.Kilometers), count: 20, order: Order.Ascending, options: GeoRadiusOptions.WithDistance), then drop members with no heartbeat (core trick 2).
  7. Cleanup: BackgroundService removes stale members with GeoRemoveAsync every 30 s.
  8. Live tracking: after a match, stream the driver's position to the rider through a SignalR group (Azure SignalR Service to scale).
  9. Cache place results: HybridCache keyed by rounded lat/lon + filters, 5-minute expiry (places rarely change).
  10. Deploy & protect privacy: Container Apps autoscaling on HTTP load; round coordinates in logs and traces; OpenTelemetry for write rate and search latency.

22.5 Large file upload & processing (chunked, resumable, scanned) Added

Let clients upload big files straight to blob storage in chunks they can resume, keep the bytes away from your API servers, and process a file only after a malware scan says it is clean.

Problem statement

Customers upload loan documents, statements, photos and videos, some of them several GB, often from a phone on a weak network. A single HTTP POST through the API ties up servers, fails at 90% and starts again from zero, and lets untrusted files reach back-office systems.

Functional

  • Upload files up to 5 GB with a progress bar
  • Resume after a network drop without starting over
  • Check type and size; scan for malware
  • Process clean files (OCR, thumbnails), then notify the user
  • Delete abandoned uploads automatically

Non-functional

  • Volume: 200k uploads/day, average 10 MB ≈ 2 TB/day; ~20 uploads/s at peak
  • Resume: a drop loses at most one 8 MiB block
  • Speed: 95% of files scanned and processed within 5 minutes
  • Availability: 99.9%; zone-redundant storage
  • Security: nothing is opened before a clean scan

Constraints & assumptions: Azure Blob Storage; browser and mobile clients; files are untrusted until scanned; managed identities everywhere (no storage keys in code); retention rules apply to stored documents.

Solution

Key decisionTrade-off
Direct to blob with a short, write-only SAS. The API never touches the bytes.Scales without app servers; you must validate size and type after upload and keep the SAS tight (one blob, 1 h, no read).
Block blobs as resumable chunks: Put Block, then Put Block List.Free resume (uncommitted blocks are kept for up to a week); the client must track block IDs.
tus protocol (tusdotnet) instead when you need a standard resumable protocol, ready clients (tus-js-client, Uppy) or non-Azure storage.Mature and open, but the bytes flow through your servers.
Scan before use: Defender for Storage on-upload scanning + Event Grid; only "No threats found" files move to the clean container.Per-GB cost and a short delay; blob index tags alone aren't tamper-proof, so act on events.

Steps to implement in .NET 10

  1. Storage: containers incoming (untrusted) and clean. Enable Defender for Storage on-upload malware scanning and send results to an Event Grid custom topic. Add a lifecycle rule that deletes old blobs in incoming.
  2. Packages: Azure.Storage.Blobs, Azure.Identity (DefaultAzureCredential / managed identity), Microsoft.Extensions.Azure (AddAzureClients).
  3. Start an upload: validate name, declared size (≤ 5 GB) and allowed types; save an Upload row as Pending; return a user delegation SAS for one blob with Create + Write only, valid 1 hour (core trick 1).
  4. Client upload: browsers use @azure/storage-blob; .NET clients (MAUI, desktop, workers) use BlockBlobClient.StageBlockAsync per 8 MiB block and CommitBlockListAsync at the end, saving progress after each block (core trick 2).
  5. Alternative: tusdotnet with app.MapTus("/files", ...) and the community Azure store Xtensible.TusDotNet.Azure; raise Kestrel's MaxRequestBodySize (default ~30 MB) for the tus route.
  6. Scan result handler: Azure Functions isolated worker with Microsoft.Azure.Functions.Worker.Extensions.EventGrid ([EventGridTrigger]).   7. Validate content: check the real size and the file's magic bytes (a renamed .exe is not a PDF) before processing.
  8. Process: send a Service Bus message (Azure.Messaging.ServiceBus) per clean file; the worker does OCR (Azure AI Document Intelligence) or thumbnails, idempotent by upload id, with a dead-letter queue.
  9. Notify & status: GET /uploads/{id} plus a SignalR or push notification when Ready or Rejected.

22.7 Web crawler Added

"Design a crawler that fetches a billion public pages a month, politely, without fetching the same page twice." A giant queue (the frontier) plus three rules: obey robots.txt, limit each host, remember what you've seen.

Problem statement

A search or knowledge product needs fresh copies of public web pages. The crawler starts from seed URLs, follows links, and keeps pages up to date, without overloading any website or getting stuck in endless link loops.

Functional

  • Start from seeds; fetch HTML; extract links and text
  • Follow links within allowed domains; obey robots.txt and Crawl-delay
  • Recrawl pages that change; skip unchanged ones
  • Store raw HTML and extracted text for indexing

Non-functional

  • 1B pages/month ≈ 400 pages/s average, 1,000/s peak
  • Default 1 request/s per host
  • 100 KB average page ≈ 100 TB/month raw (≈25 TB compressed)
  • Seen set of 10B URLs: a Bloom filter at 1% false positives ≈ 12 GB

Constraints & assumptions:

  • Public pages only, no logins. Identify the bot with a User-Agent and a contact URL.
  • robots.txt follows RFC 9309. Cache it per host for up to 24 hours.
  • No JavaScript rendering in v1 (a headless browser only for an allow-list of sites).

Solution

FrontierKafka topic keyed by host, so one worker owns each host; per-host Channel<T> queues inside the workerPoliteness stays local and simple; very big hosts make partitions uneven
PolitenessPartitionedRateLimiter keyed by host (token bucket 1/s, or the site's Crawl-delay)Safe for websites; big sites take longer to crawl
Seen URLsNormalise the URL, then a Redis Bloom filter12 GB instead of hundreds of GB; ~1% of new URLs are wrongly skipped

Steps to implement in .NET 10

  1. Create a Worker Service. Register a named HttpClient with IHttpClientFactory, AddStandardResilienceHandler() (Microsoft.Extensions.Http.Resilience), automatic decompression, a 10 s timeout and a User-Agent with a contact URL.
  2. Build the frontier: a Kafka topic urls keyed by host (Confluent.Kafka); inside each worker, bounded System.Threading.Channels per host.
  3. robots.txt: fetch once per host, cache with HybridCache, and parse with TurnerSoftware.RobotsExclusionTools (or a small RFC 9309 parser of your own).
  4. Politeness: a PartitionedRateLimiter<Uri> keyed by host, plus a cap of 1–2 concurrent requests per host.
  5. Parse with AngleSharp: a[href] links, canonical link, meta robots (noindex, nofollow) and body text. Resolve relative links with new Uri(baseUri, href) and normalise them.
  6. Seen set: StackExchange.Redis sending BF.ADD / BF.EXISTS (Redis 8 includes Bloom filters; on managed Redis, check your tier supports them).
  7. Store compressed HTML in Blob Storage (Azure.Storage.Blobs) keyed by URL hash, and per-URL metadata (ETag, last crawl, content hash, next due) in Cosmos DB or Table Storage.
  8. Emit OpenTelemetry metrics (pages/s, errors per host, queue depth). Run N workers on AKS with KEDA scaling on Kafka consumer lag.

async Task CrawlAsync(Uri url, HttpClient http, CancellationToken ct)
{
    using RateLimitLease lease = await perHost.AcquireAsync(url, 1, ct);
    if (!lease.IsAcquired) { await frontier.RequeueLaterAsync(url, ct); return; }

    using var response = await http.GetAsync(url, HttpCompletionOption.ResponseHeadersRead, ct);
    if (!response.IsSuccessStatusCode || response.Content.Headers.ContentType?.MediaType != "text/html") return;

    var doc = await new HtmlParser().ParseDocumentAsync(await response.Content.ReadAsStreamAsync(ct), ct);
    foreach (var href in doc.QuerySelectorAll("a[href]").Select(a => a.GetAttribute("href")))
        if (Uri.TryCreate(url, href, out var link) && link.Scheme is "http" or "https")
            await frontier.OfferAsync(Normalise(link), ct);      // Bloom filter check inside
}

22.8 Real-time fraud detection Added

"Score every payment for fraud in under 100 ms, block the obvious ones, and send the doubtful ones to analysts." A fast inline decision, backed by a payment stream that keeps the features fresh.

Problem statement

A bank processes card and real-time account-to-account payments. Real-time payments can't be pulled back once they settle, so the fraud decision must happen before the money moves, without making checkout feel slow.

Functional

  • Score each payment: approve, step-up (extra check), decline, or approve + review
  • Rules (velocity, new payee, impossible travel, known mule accounts) + an ML model
  • Analysts work cases; their outcomes become training labels
  • Change rules and thresholds without a deploy

Non-functional

  • Decision p99 under 100 ms; 3,000 payments/s at peak (500 average)
  • 99.99% available; a safe fallback if scoring fails
  • Every decision audited with rule and model versions
  • Few false declines: a wrong decline costs a customer

Constraints & assumptions:

  • PCI DSS: the fraud store holds card tokens, never full card numbers.
  • The model is trained offline (ML.NET, or Python exported to ONNX) and served in .NET.
  • The payment switch calls the fraud service synchronously; everything else can be async.

Solution

Inline vs streamSynchronous gRPC decision; a stream consumer computes long-window features and casesLatency stays bounded; stream features can lag a few seconds (hot counters are updated inline)
Rules + modelHard rules override (sanctions, known mule); model score bands map to actionsExplainable and safe; two things to tune and govern
FeaturesRedis: INCR + expiry for fixed windows, sorted sets for sliding windowsSub-millisecond reads; memory cost, so every key needs a TTL

Failure mode80 ms budget, then a rules-only fallback decisionPayments keep flowing in an outage; a little more fraud risk while degraded

Steps to implement in .NET 10

  1. Create an ASP.NET Core gRPC service (Grpc.AspNetCore) with a Score(PaymentRequest) contract agreed with the payment switch.
  2. Features with StackExchange.Redis: velocity counters via StringIncrementAsync + KeyExpireAsync in one transaction; sliding windows via SortedSetAddAsync, SortedSetRemoveRangeByScoreAsync, SortedSetLengthAsync.
  3. Rules as plain C# classes, with thresholds in IOptionsMonitor<FraudRules> fed by Azure App Configuration, so changes apply without a deploy.
  4. Train offline (ML.NET with Microsoft.ML.LightGbm, or Python to ONNX). Serve with Microsoft.Extensions.ML: AddPredictionEnginePool<TxnFeatures, FraudScore>().FromFile("fraud", path, watchForChanges: true), or Microsoft.ML.OnnxRuntime.
  5. Publish every decision to Event Hubs (Azure.Messaging.EventHubs) or Kafka, partition key = card token. An EventProcessorClient consumer updates long-window features and opens cases.
  6. Case management: review-band decisions create a case; the analyst's outcome (fraud / genuine) is stored as a label for retraining.
  7. Wrap scoring in a Microsoft.Extensions.Resilience pipeline: 80 ms timeout + fallback to rules-only. Record latency histograms, decision mix and model version with OpenTelemetry.
  8. Deploy across zones (min 3 replicas, zone-redundant Redis). Run a new model in shadow mode (score, don't act) before switching it on.
public sealed class FraudScorer(
    IDatabase redis, PredictionEnginePool<TxnFeatures, FraudScore> model, RuleSet rules)
{
    public async Task<Decision> ScoreAsync(Payment p)
    {
        string key = $"vel:{p.CardToken}:10m";
        ITransaction tx = redis.CreateTransaction();
        Task<long> count10m = tx.StringIncrementAsync(key);
        _ = tx.KeyExpireAsync(key, TimeSpan.FromMinutes(10), ExpireWhen.HasNoExpiry);
        await tx.ExecuteAsync();

        var f = new TxnFeatures { Amount = (float)p.Amount, Count10m = await count10m,
                                  NewPayee = p.IsNewPayee, MerchantRisk = p.MerchantRisk };

        if (rules.HardBlock(p, f) is { } reason) return Decision.Decline(reason);   // e.g. known mule account

        float score = model.Predict("fraud", f).Probability;
        return score switch
        {
            >= 0.90f => Decision.Decline("model"),
            >= 0.60f => Decision.ApproveAndReview(score),     // async case for an analyst
            _        => Decision.Approve(score)
        };
    }
}

22.9 Customer onboarding (KYC) workflow Added

"Design digital onboarding: verify a new customer's identity, screen them, ask a human when needed, open the account, and prove every step later." A long-running workflow that may take three minutes or three weeks.

Problem statement

Customers open an account in the app. Under Australia's AML/CTF Act (reformed obligations from 31 March 2026), a bank must complete initial customer due diligence before it provides the service, and keep the records for 7 years after the relationship ends. Functional

  • Capture details, an ID document photo and a selfie

  • 80% of applicants auto-decided in under 3 minutes
  • 10,000 applications a day; peak 50 starts a minute
  • Workflows survive restarts and can wait up to 30 days
  • Every step in an append-only audit trail, kept 7 years after the relationship ends
  • PII encrypted; documents stored in an Australian region

Constraints & assumptions:

  • Identity, liveness and screening are external vendor APIs with rate limits and outages.
  • Analysts work business hours; every decision must be explainable.

public sealed class KycOrchestrator : TaskOrchestrator<Application, KycOutcome>
{
    public override async Task<KycOutcome> RunAsync(TaskOrchestrationContext ctx, Application app)
    {
        var retry = TaskOptions.FromRetryPolicy(new RetryPolicy(5, TimeSpan.FromSeconds(10), backoffCoefficient: 2));
        IdResult id = await ctx.CallActivityAsync<IdResult>("VerifyIdentity", app, retry);
        Risk risk   = await ctx.CallActivityAsync<Risk>("ScreenAndRate", new ScreenInput(app, id), retry);
        if (risk.Level != RiskLevel.Low)
        {
            using var cts = new CancellationTokenSource();
            Task timeout = ctx.CreateTimer(ctx.CurrentUtcDateTime.AddDays(5), cts.Token);
            Task<ReviewDecision> review = ctx.WaitForExternalEvent<ReviewDecision>("ReviewDecision");
            if (await Task.WhenAny(review, timeout) == timeout) return KycOutcome.Expired();
            cts.Cancel();   if (!review.Result.Approved) return KycOutcome.Declined(review.Result.Reason);
        }
        string accountId = await ctx.CallActivityAsync<string>("OpenAccount", app, retry);
        try { await ctx.CallActivityAsync("IssueCard", accountId, retry); }
        catch (TaskFailedException)
        {
            await ctx.CallActivityAsync("CloseAccount", accountId, retry);      // compensate
            return KycOutcome.Failed("card");
        }
        return KycOutcome.Approved(accountId);
    }
}

22.10 Enterprise RAG assistant Added

"Let staff ask questions over policies, procedures and wikis, get grounded answers with citations, and never see a document they aren't allowed to open." RAG at enterprise scale: the hard parts are permissions, freshness and proving quality.

Problem statement

A company has 2 million documents across SharePoint, Confluence and file shares, and 20,000 staff. People waste time hunting for the right policy. The assistant must answer from these documents only, show its sources, and respect each document's permissions.

Functional

  • Ingest new, changed and deleted documents, and permission changes
  • Chunk, enrich and embed; hybrid retrieval trimmed to the user's groups
  • Answers with clickable citations; "I don't know" when nothing fits
  • Thumbs up/down feedback; an evaluation dashboard for the owners

Non-functional

  • 2M docs ≈ 20M chunks; at 1,536 dimensions × 4 bytes ≈ 120 GB of vectors (before quantisation)
  • Peak 20 questions/s; first token under 2 s; p95 full answer under 8 s
  • Permission removals reflected within 15 minutes; content changes within 1 hour
  • Groundedness at least 4/5 on the golden set; data stays in region

Constraints & assumptions:

  • Models run in an Azure region you approve; staff sign in with Microsoft Entra ID.
  • Documents can contain prompt-injection text; treat retrieved text as data, never as instructions.
  • Restricted-label content is excluded at ingestion (see 7.2).

Steps to implement in .NET 10

  1. Create an ASP.NET Core API with Entra ID auth (Microsoft.Identity.Web). Register IChatClient and IEmbeddingGenerator from Microsoft.Extensions.AI, using Azure.AI.OpenAI + Microsoft.Extensions.AI.OpenAI (AsIChatClient()).
  2. Design the Azure AI Search index (Azure.Search.Documents): content, contentVector (HNSW), title, url, headingPath, lastModified, and group_ids as a filterable, non-retrievable string collection; add a semantic configuration and a vectorizer.
  3. Build the ingestion worker: source change feeds (e.g. Microsoft Graph delta for SharePoint); Azure.AI.DocumentIntelligence layout to Markdown; chunk with Microsoft.Extensions.DataIngestion preview or your own splitter; embed; MergeOrUpload and delete.
  4. Query path: read the user's group ids from the token (use Microsoft Graph when the token has too many groups), build the search.in filter, run hybrid + semantic search.
  5. Prompt: system rules ("answer only from the sources, cite [n], say you don't know"), numbered sources; stream with GetStreamingResponseAsync; validate citations before showing them.
  6. Guardrails: Azure.AI.ContentSafety on output, Prompt Shields (REST) on the question and documents, per-user rate limits (Microsoft.AspNetCore.RateLimiting), no prompts or PII in logs.
  7. Evaluation: a golden Q&A set run as xUnit tests with Microsoft.Extensions.AI.Evaluation.Quality, cached and reported with Microsoft.Extensions.AI.Evaluation.Reporting; fail the PR if scores drop.
  8. Deploy with private endpoints for Search and the model; trace tokens, latency and "I don't know" rate with OpenTelemetry; review low-rated answers weekly.
app.MapPost("/ask", async (AskRequest req, ClaimsPrincipal user, SearchClient search,
                           IChatClient chat, CancellationToken ct) =>
{
    string groups = string.Join(",", user.FindAll("groups").Select(c => c.Value));   // Graph on overage
    var options = new SearchOptions
    {
        Size = 8,
        Filter = $"group_ids/any(g: search.in(g, '{groups}', ','))",            // security trimming
        QueryType = SearchQueryType.Semantic,
        SemanticSearch = new() { SemanticConfigurationName = "default" },
        VectorSearch = new() { Queries = { new VectorizableTextQuery(req.Question)
            { KNearestNeighborsCount = 50, Fields = { "contentVector" } } } }
    };
    var hits = new List<Chunk>();
    await foreach (var r in (await search.SearchAsync<Chunk>(req.Question, options, ct)).Value.GetResultsAsync())
        hits.Add(r.Document);
    if (hits.Count == 0) return Results.Ok(Answer.DontKnow);
    string sources = string.Join("\n", hits.Select((h, i) => $"[{i + 1}] {h.Title}: {h.Content}"));
    ChatResponse reply = await chat.GetResponseAsync(
        [new(ChatRole.System, Prompts.GroundedAnswer),
         new(ChatRole.User, $"Sources:\n{sources}\n\nQuestion: {req.Question}")],
        cancellationToken: ct);
    return Results.Ok(Answer.WithValidatedCitations(reply.Text, hits));   // drop or retry unknown [n]
});

⚡ Quick-fire Q&A

Flash sale: how do you guarantee you never oversell?

Make "check stock and take stock" one atomic operation: a Redis Lua script, or SQL UPDATE ... SET Stock = Stock - @qty WHERE Stock >= @qty and check the rows affected. Add idempotency keys so retries don't buy twice, and prove it with a parallel test (Task.WhenAll) against a real Redis or SQL container.

Booking: how do temporary holds expire without a timer per seat?

Store an expiry time on the hold and treat any hold with HoldExpiresAt <= now as free in every query (lazy expiry). A periodic sweeper only tidies up and pushes "free again" events. In Redis, SET key value NX PX 600000 gives the same thing in one command. Test it with FakeTimeProvider.Advance.

Autocomplete: why not run LIKE 'abc%' on the database?

At thousands of requests per second it is too slow and it can't rank by popularity cheaply. Precompute the top 10 per prefix (Redis sorted sets or a trie) from search logs, cache short prefixes at the edge, and debounce on the client. Use Azure AI Search suggesters if you need typo tolerance.

Proximity: why use two different stores for ATMs and drivers?

ATMs rarely change and need rich filters, so a SQL/PostGIS spatial index fits. Drivers move every few seconds (tens of thousands of writes per second), so an in-memory Redis GEO index fits, with a heartbeat TTL to hide drivers who went offline.

File upload: how do you make a 5 GB upload resumable and safe?

Give the client a short, write-only SAS for one blob, upload 8 MiB blocks (Put Block) and commit the list at the end (Put Block List), so a drop only re-sends one block. Scan with Defender for Storage, react to the Event Grid result, and process only files marked "No threats found".

Job scheduler: how do you stop two nodes running the same job?

Let one shared store decide. Clustered Quartz.NET takes a database row lock when it acquires a trigger, so only one node fires each firing. Because a crashed node's job is recovered and may run again, also make every job idempotent with a key such as job name + scheduled fire time.

Web crawler: how do you stay polite and avoid re-fetching pages?

Shard the frontier by host so one worker owns each site, and rate-limit per host (about 1 request/s, or the site's Crawl-delay) after checking robots.txt. Normalise URLs and check a Bloom filter before enqueueing, and use conditional GET (ETag / Last-Modified) on recrawls.

Fraud detection: how do you decide in under 100 ms?

Keep the inline path tiny: read and update velocity counters in Redis, run hard rules, then score with an in-process model (ML.NET or ONNX Runtime). Publish the decision to a stream and do everything else (long-window features, cases, retraining labels) asynchronously. If scoring times out, fall back to rules only.

KYC onboarding: how do you model a human approval that can take days?

Use a durable workflow (Durable Functions / Durable Task, or Temporal). The orchestrator waits for an external "ReviewDecision" event racing a durable timer, so it costs nothing while it waits and expires cleanly. Side effects like opening an account use saga compensations, and every step writes to an append-only audit store.

Enterprise RAG: how do you stop the assistant leaking documents?

Trim at retrieval. Store the allowed group ids on every chunk, read the user's groups from their validated Entra token, and filter every search with them (e.g. search.in in Azure AI Search). Unauthorised text never reaches the prompt, and permission changes are synced into the index quickly.

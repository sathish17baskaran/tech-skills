4.1 Why distributed is hard: fallacies & partial failure Added

On one machine, things either work or crash. Across a network, some parts fail while others keep going, and you often can't tell which.

The 8 fallacies of distributed computing

False assumptions that engineers new to distributed systems make (L. Peter Deutsch and others at Sun Microsystems, 1990s).

FallacyRealityWhat you do
1. The network is reliablePackets drop, connections reset, cables and switches failTimeouts, retries with backoff, idempotency
2. Latency is zeroCross-region calls take tens to hundreds of msFewer, coarser calls; caching; async
3. Bandwidth is infiniteBig payloads clog links and cost moneyPaging, compression, claim check
4. The network is secureAnything on the wire can be read or changedTLS / mTLS, zero trust
5. Topology doesn't changePods, IPs and routes change all the timeService discovery, DNS, health checks
6. There is one administratorMany teams, vendors and clouds own parts of the pathClear contracts, observability, runbooks
7. Transport cost is zeroSerialisation, egress and hops cost CPU and moneyEfficient formats (gRPC/Protobuf), co-location
8. The network is homogeneousMixed hardware, OSs, protocols and versionsOpen standards, versioned APIs

💥 Partial failure

One node, link or dependency fails while the rest keep running. A timeout tells you nothing about whether the work happened.

✂ Network partition

Nodes are alive but can't reach each other. Each side may think the other is dead. This is the "P" in CAP (see 3.11).

🪖 Two generals problem

Two generals must attack together but can only send messengers who may be captured. No finite number of messages makes both certain. Lesson: over an unreliable network you can't get guaranteed agreement, only good-enough protocols.

🐢 Slow = dead?

A GC pause, a busy disk or a noisy neighbour looks exactly like a crash from outside. Failure detection is always a guess based on timeouts.

  • A timeout means "I don't know", not "it failed". Design every remote write to be safe to retry (idempotency, see 8.7).
  • Assume every network call can be slow, fail, or succeed without you hearing about it.
  • The more services in a request path, the more likely one is down. Availabilities multiply.

4.2 Replication models Added

Keep copies of the same data on several nodes for availability, durability and read scale. The big choices: who accepts writes, and whether to wait for copies.

Single-leaderMulti-leaderLeaderless
Who takes writesOne leader. Followers copy its logSeveral leaders (often one per region) that sync with each otherAny replica. The client writes to several at once
ProsSimple. No write conflictsLocal writes in every region. Survives a region lossNo failover needed. Very high availability
ConsLeader is a bottleneck. Failover takes time and can lose async writesWrite conflicts need resolving (last-write-wins, merge, CRDTs)Weaker consistency. Needs quorums and read repair
ExamplesSQL Server Always On, PostgreSQL streaming replication, MongoDB replica sets, a Kafka partitionCosmos DB multi-region writes, CouchDB, active-active databasesCassandra, ScyllaDB, Riak (Amazon Dynamo paper style)

⏳ Synchronous replication

  • Leader waits for the follower to confirm before saying "done"
  • No data loss on failover (RPO = 0)
  • Slower writes. A slow or dead follower can block writes
  • Common middle ground: wait for one follower (semi-sync), the rest async

⚡ Asynchronous replication

  • Leader confirms right away and ships changes later
  • Fast writes, followers can be far away (other regions)
  • Recent writes can be lost on failover
  • Followers lag behind, so reads can be stale

Replication-lag anomalies (and fixes)

  • Read-your-writes: you don't see your own update. Fix: read from the leader after a write, or use session tokens.
  • Monotonic reads: you see new data, refresh, then see older data (two different followers). Fix: pin a user to one replica.
  • Consistent prefix: you see an answer before the question. Fix: keep related writes in the same partition.
  • These map to the consistency models in 3.12.
  • Single-leader is the default. Pick multi-leader or leaderless only when you need multi-region writes or extreme availability, and have a conflict plan.
  • Async replication means RPO > 0 and stale reads. Say so explicitly in a design.
  • Route reads that must be fresh (balance after a payment) to the primary. Send reports and search to replicas.

4.3 Quorum: N, W, R Added

With N replicas, a write must reach W of them and a read must ask R of them. If R + W > N, every read overlaps at least one replica that has the latest write.

N: replicas

How many copies of each item exist (Cassandra calls it the replication factor). Typical: 3.

W: write quorum

How many replicas must confirm a write before it counts as done.

R: read quorum

How many replicas a read asks. The newest version among the answers wins.

N / W / RR + W > N?BehaviourTolerates
3 / 2 / 2✅ 4 > 3Balanced default. Fresh reads1 node down for both reads and writes
3 / 3 / 1✅ 4 > 3Fast reads, slow and fragile writesWrites fail if any node is down
3 / 1 / 3✅ 4 > 3Fast writes, slow readsReads fail if any node is down
3 / 1 / 1❌ 2 ≤ 3Fastest, eventually consistent2 nodes down

Sloppy quorum & hinted handoff

  • If some home replicas are unreachable, a sloppy quorum accepts the write on other nodes so writes stay available.
  • The stand-in node keeps a hint and hands the data back when the home replica returns (hinted handoff).
  • Trade-off: during that window, R + W > N no longer guarantees a fresh read.
  • Described in Amazon's Dynamo paper. Cassandra does hinted handoff, but hints don't count towards the consistency level (except ANY).

In real products

  • Cassandra / ScyllaDB: N = replication factor per keyspace. Pick W and R per query: ONE, QUORUM, LOCAL_QUORUM (majority in your data centre), ALL.
  • Cosmos DB: you don't set N, W or R. Each partition has a 4-replica set; writes commit to a local majority (3 of 4), Strong and Bounded Staleness read from 2 replicas, the other levels read from 1. You choose a consistency level instead (3.12).
  • Raft / Paxos systems (etcd, ZooKeeper) use majority quorums too (4.4).
  • R + W > N → read and write sets overlap. Majority both ways (W = R = ⌊N/2⌋ + 1) is the usual choice.
  • Quorums alone aren't full linearizability: sloppy quorums, concurrent writes and half-failed writes can still surprise you.
  • Use odd N (3, 5) so a majority survives one or two failures.

One inequality explains how Cassandra-style databases stay consistent: R + W > N 🧮

📦 N = copies of the data (say 3)

✍️ W = copies that must confirm a write (2)

👀 R = copies you ask on a read (2)

🔗 2 + 2 > 3, so every read touches at least one fresh copy

Drop to W = 1, R = 1 and you trade freshness for speed. Which way does your system lean?

4.4 Consensus & leader election (Raft) Added

Consensus gets a group of nodes to agree on one value, or one ordered log, even when some nodes crash or messages are lost, as long as a majority is up.

🎯 What it solves

  • Who is the leader right now?
  • What's the agreed order of writes?
  • Is this config change committed?

🔢 Majority rule

2f + 1 nodes survive f failures. 3 nodes survive 1, 5 survive 2. 4 nodes still survive only 1, so use odd numbers.

📜 Paxos in one line

Lamport's original consensus algorithm: proven correct, famously hard to understand and implement (used in Google Chubby and Spanner).

Raft in five ideas

  • Roles: every node is a follower, candidate or leader. Only the leader accepts writes.
  • Terms: time is split into numbered terms. At most one leader per term. A higher term always wins.
  • Election: followers expect heartbeats. If a randomised timeout passes with none, a follower becomes a candidate, bumps the term and asks for votes. A majority of votes makes it leader.
  • Log replication: the leader appends each write to its log and sends it to followers (AppendEntries). Once a majority has stored it, the entry is committed.
  • Safety: a node only votes for a candidate whose log is at least as up to date as its own, so committed entries are never lost.

🧠🧠 Split brain

Two nodes both believe they are leader, usually after a partition or a too-short timeout, and both accept writes. Data diverges.

  • Needs a majority to lead, so only one side can win
  • Odd node counts, or a tie-breaker witness (e.g. a cloud witness for a 2-node cluster)

🎫 Fencing tokens

Every new leader or lock holder gets a number that only goes up (Raft term, ZooKeeper zxid, etcd revision). Storage rejects any request with a lower number than it has already seen, so an old leader that wakes up can't do damage. More in 4.5.

  • Don't write your own consensus. Borrow it: use a lease from etcd/Kubernetes, ZooKeeper, Consul or a cloud lock (Azure Blob lease).
  • Consensus needs a majority, so a 3-node cluster with 2 nodes down stops accepting writes. That's the CP choice by design.
  • Leader election is only half the job. The resource the leader writes to must also check a fencing token.

If a renew fails, stop working immediately: another instance may already be leader. Pair the lease with a fencing check on the data you write.

How does Kubernetes know which etcd node is in charge? Raft 🗳️

💓 The leader sends heartbeats. Silence for too long → a follower runs for election.

🔢 Every election bumps the "term". Higher term always wins.

🏆 A majority of votes makes you leader. 5 nodes survive 2 failures.

📜 A write is committed once a majority has it in their log.

🧟 An old leader that wakes up sees a higher term and steps down.

Rule of thumb: never build your own consensus. Borrow it from etcd, ZooKeeper or a cloud lease.

4.5 Distributed locks Added

A lock shared across machines so that only one worker does something at a time, such as running the nightly statement job or refreshing a shared token.

⏲ Lease, not a lock

Every distributed lock needs a TTL. If the holder crashes, the lock frees itself. The holder must renew before it expires.

🧟 The zombie problem

The holder pauses (GC, VM freeze, slow network) longer than the TTL. The lock expires, someone else takes it, the first one wakes up and still thinks it holds it. Two writers.

🎫 Fencing token

The lock service hands out a number that goes up with every grant. The storage rejects writes carrying an older number.

⚖️ Efficiency vs correctness

Ask "what happens if two workers run at once?" If the answer is "some wasted work", Redis is fine. If it's "a customer is charged twice", you need fencing or, better, no lock at all.

✅ Prefer idempotency over locks

  • A unique constraint on a business key (payment ID)
  • Conditional update / optimistic concurrency (rowversion, ETag)
  • One consumer per key (Service Bus sessions, Kafka partitions)
  • Idempotent handlers (8.7)
  • Every distributed lock is really a lease. Assume it can expire while you're still working.
  • Use fencing tokens, or a conditional write, wherever two holders would corrupt data.
  • lock / SemaphoreSlim only work inside one process. They do nothing across pods.

Your distributed lock is lying to you. It's really a lease 🔒⏲

😴 Worker 1 takes the lock, then freezes in a long GC pause.

⌛ The lease expires. Worker 2 takes it and writes.

🧟 Worker 1 wakes up, still "holding" the lock, and writes too.

🎫 Fix: fencing tokens. Storage rejects any write with an older token.

✅ Better fix: make the operation idempotent so you don't need the lock.

4.6 Distributed transactions: 2PC vs Saga Added

Two-phase commit (2PC) makes several databases commit or roll back together. It's atomic, but blocking and fragile, so microservices usually use a saga instead.

  • Phase 1, prepare: each participant writes everything durably, holds its locks and votes yes or no.
  • Phase 2, commit: if all voted yes, the coordinator says commit; otherwise roll back.
  • Blocking problem: a participant that voted yes can't commit or abort on its own. If the coordinator is down, it waits with rows locked.
  • XA is the standard 2PC interface between a transaction manager and resources. On Windows, MSDTC plays the coordinator role.

LocksHeld across all participants until commitShort, local onlyReservation, not a DB lock

Why microservices avoid 2PC

  • Brokers, NoSQL stores and HTTP APIs usually don't support XA at all.
  • Locks held across services kill throughput and couple teams' availability together.
  • The coordinator is a single point of failure.
  • Instead: a saga (11.6) for the business flow, plus the transactional outbox (10.5) so each step's DB write and event publish stay atomic.
  • 2PC gives atomicity at the cost of availability: it's CP, and it blocks.
  • Saga = a chain of local transactions + compensations. Accept intermediate states ("pending") and design them in.
  • TCC is a saga where the first step is an explicit reservation that expires if not confirmed.

🔁 The alternative: a saga. Local transactions plus compensating "undo" steps.

4.7 Time & ordering: clocks, Lamport, vector clocks Added

Every machine's clock is slightly wrong, so timestamps can't reliably order events across machines. Logical clocks order events by cause and effect instead.

🕰 Clock skew

Two servers' clocks disagree, often by milliseconds, sometimes by seconds after a bad NTP sync or VM pause.

⏪ Clocks jump

NTP can step a clock backwards. Leap seconds and VM migrations add surprises. "Later" can get a smaller timestamp.

⏱ Two kinds of clock

Wall clock (UTC) for display and logs. Monotonic clock for durations and timeouts: it never goes backwards.

⚠️ Last-write-wins (LWW) loses data silently

Two replicas accept updates to the same address. Node B's clock runs 2 s fast, so its older update gets the bigger timestamp and wins. The newer change disappears without any error. Cassandra, and Cosmos DB multi-region writes, resolve conflicts with LWW by default, so use it only where losing a concurrent update is acceptable.

🔢 Lamport timestamps

One counter per node. Tick on every event; on receive, take max(local, received) + 1. Gives a total order consistent with causality (break ties by node ID). Can't tell whether two events were concurrent.

🧮 Vector clocks

Each node keeps a counter for every node. Compare vectors to see "happened before" or concurrent (a real conflict). Used in Amazon's Dynamo paper and Riak. Size grows with the number of nodes.

🔀 Hybrid logical clocks (HLC)

Physical time plus a small logical counter. Stays close to wall-clock time but still respects causality. Used by CockroachDB, YugabyteDB and MongoDB cluster time.

🛰 TrueTime (Spanner)

GPS and atomic clocks give a time interval with bounded uncertainty; Spanner waits out the uncertainty before committing, so timestamps order transactions globally.

CRDTs: merge without conflicts

  • Conflict-free replicated data types are data structures that any replica can update, and that always merge to the same result in any order.
  • Examples: G-Counter (grow-only counter), PN-Counter (up and down), OR-Set (add/remove set), LWW-Register.
  • Used in Redis Active-Active geo-replication, Riak, and collaborative editors (Automerge, Yjs).
  • Great for counters, likes, carts and presence. Not for balances that must never go below zero: that needs coordination.
  • Never order cross-machine events by wall-clock timestamps alone. Use a sequence from one leader, a version number, or a logical clock.
  • Measure durations and timeouts with a monotonic clock (Stopwatch), not DateTime.Now.
  • Store and send times as UTC with an offset (DateTimeOffset). Keep NTP healthy and alert on skew.

// A thread-safe Lamport clock
public sealed class LamportClock
{
    private long _time;

    // Local event or just before sending a message
    public long Tick() => Interlocked.Increment(ref _time);

    // On receiving a message stamped with the sender's time
    public long Receive(long remote)
    {
        while (true)
        {
            long current = Interlocked.Read(ref _time);
            long next = Math.Max(current, remote) + 1;
            if (Interlocked.CompareExchange(ref _time, next, current) == current)
                return next;
        }
    }
}

Your servers don't agree on what time it is. And that can silently delete data 🕰️

⏩ Clocks drift and NTP can jump them backwards.

🗑 Last-write-wins + a fast clock = an older update beats a newer one, with no error.

🔢 Lamport clocks order events by cause and effect, not by wall time.

🧮 Vector clocks go further and detect true conflicts.

⏱ For timeouts, use a monotonic clock, never DateTime.Now.

⚡ Quick-fire Q&A

How many nodes should a consensus cluster (etcd, ZooKeeper) have?

An odd number, usually 3 or 5. 2f + 1 nodes survive f failures: 3 survive 1, 5 survive 2. Adding a 4th node adds cost without adding fault tolerance.

Does R + W > N guarantee strong consistency?

It guarantees that read and write sets overlap, so a read normally sees the latest acknowledged write. Sloppy quorums, concurrent writes and partially failed writes can still give anomalies, so it's not full linearizability.

Is a Redis SET NX lock safe?

For efficiency (avoid duplicate work), yes, with a TTL and a release that checks the value. For correctness, no: a paused holder can outlive its lease. Add a fencing token checked by the storage, or make the operation idempotent.

Why not use 2PC across microservices?

It blocks when the coordinator fails, holds locks across services, needs every participant to support XA, and lowers availability. Use a saga with compensations plus the transactional outbox.

Why can't you order events from different servers by timestamp?

Clocks skew and can jump backwards, so a later event can get an earlier timestamp. Use a single sequencer, version numbers, or logical clocks (Lamport, vector, HLC).

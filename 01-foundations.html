Foundations: how programs run & wait

1.1 Process vs Thread

A process is a running program with its own memory. A thread is a worker inside a process that shares that memory.

Visual

How it works

  • The OS gives each process an isolated address space. One process can't read another's memory.
  • Threads in the same process share heap, globals and file handles. Each thread has its own stack and registers.
  • The OS scheduler switches threads on CPU cores (a context switch). Switching between processes costs more because memory mappings change.
  • Threads talk through shared memory, which needs locks. Processes talk through IPC: pipes, sockets, message queues, shared memory.
ProcessThread
MemoryIsolatedShared within process
Creation costHeavyLight
CommunicationIPC (slower, safer)Shared variables (fast, needs locks)
Crash impactOnly that process diesOne bad thread can crash the whole process
ExampleEach Chrome tab, each containerWeb server thread pool handling requests
  • Shared memory brings race conditions, deadlocks and starvation. Use locks, mutexes, semaphores or immutable data.
  • Thread pools reuse threads, so you don't pay the cost of creating one per request.
  • Python's GIL lets only one thread run Python code at a time. For CPU-bound work, use multiple processes.
  • Node.js runs your JavaScript on one thread with an event loop and uses a background pool for I/O.
  • Lightweight "green" threads exist too: Go goroutines, Java 21 virtual threads, .NET async tasks. You can run millions of them.
  • A container is just an isolated process, not a VM.

{
    private readonly Lock _gate = new();   // .NET 9+ dedicated lock type
    private decimal _balance;
    private long _requests;

    public void Deposit(decimal amount)
    {
        Interlocked.Increment(ref _requests);   // lock-free counter
        lock (_gate) { _balance += amount; }    // one thread at a time
    }
}

1.2 Concurrency vs Parallelism Added

Concurrency means juggling many tasks by switching between them. Parallelism means doing many tasks at the same instant on multiple cores.

Visual

"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once." (Rob Pike)

  • You can have concurrency without parallelism (a single-core event loop) and parallelism without much concurrency (a GPU running the same math on many items).
  • I/O-bound work (waiting on network or DB) gains most from concurrency and async.
  • CPU-bound work (encryption, image processing) gains from parallelism across cores.
  • Amdahl's law: the part of the job that can't run in parallel limits the total speed-up.

    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (id, token) => await client.RefreshBalanceAsync(id, token));

// Parallelism (CPU-bound): spread the work across cores

    .GroupBy(t => t.AccountId)
    .Select(g => (Account: g.Key, Total: g.Sum(t => t.Amount)))
    .ToList();

Don't wrap I/O calls in Task.Run or PLINQ to "make them parallel". Async I/O is already concurrent; extra threads only add overhead.

1.3 Sync vs Async

Synchronous: the caller waits for the answer before moving on. Asynchronous: the caller moves on and gets the result later.

Two levels, same idea

In code

  • Blocking I/O: the thread sits idle while waiting for the DB.
  • Non-blocking / async-await: the thread is released while waiting, then picks up again when data arrives.
  • Result: one thread can serve many requests.

Between systems

  • Sync: HTTP request/response. The client waits for 200 OK.
  • Async: send a message to a queue or event bus, return immediately. A consumer processes it later.
  • Result: services are decoupled in time.

  • Always carry a correlation ID so you can trace a message end to end.
  • Async consumers must be idempotent because messages can arrive twice.
  • Calling sync services in a chain multiplies latency and failure: A→B→C means each call adds risk.
  • Interview answer: "Use sync when the user needs the answer to continue. Use async when the work can finish later or fan out."

Sync vs Async explained with coffee ☕

Sync: you stand at the counter until your coffee is ready.

Async: you get a buzzer (202 Accepted), sit down, and it buzzes when ready (webhook).

Same coffee, but the café serves 5x more people. That's async: better throughput, not faster coffee.

1.4 Latency vs Throughput vs Bandwidth Added

Latency = how long one request takes. Throughput = how many requests finish per second. Bandwidth = the maximum the pipe can carry.

⏱ Latency

Time for one trip, in ms. Like how long one car takes on the highway.

🚚 Throughput

Work done per unit of time (req/s, TPS, MB/s). Like cars arriving per hour.

🛣 Bandwidth

The theoretical max capacity. Like the number of lanes.

  • Report percentiles, not averages: p50 (typical), p95, p99 (tail). One slow dependency hurts p99.
  • Little's Law: L = λ × W. Requests in the system = arrival rate × time each spends. Example: 200 req/s × 0.5 s = 100 requests in flight, so you need about 100 concurrent workers.
  • Batching raises throughput but can add latency. That trade-off shows up everywhere.

1.6 Race conditions, locks and deadlocks Added

A race condition is a bug where the result depends on which thread gets there first. Locks make a critical section run one at a time; deadlock is when locked threads wait for each other forever.

Visual: the lost update

How it works

  • Critical section: code that touches shared state and must not interleave. Atomic = it happens all at once or not at all.
  • Two classic races: read-modify-write (count++ is read, add, write) and check-then-act (if (!exists) add).
  • Atomic operations use one CPU instruction. Compare-and-swap (CAS): "set to X only if it is still Y", else re-read and retry. Lock-free, best for one variable.
  • Basics of thread safety were in 1.1. Across machines you need a distributed lock or a fencing token.
PrimitiveLets inUse for
Mutex / lock1 threadProtect a small critical section
SemaphoreN at onceCap concurrency (e.g. 10 DB calls)
Reader-writer lockMany readers or 1 writerRead-mostly data, like a cache
Atomic / CASNo lockCounters, flags, swapping a reference

Optimistic vs pessimistic concurrency

Optimistic: check at write

  • Read a row version or ETag, then UPDATE … WHERE version = @v.
  • 0 rows changed = someone won: reload and retry, or return 409 / 412.
  • Best when conflicts are rare. No locks held.

Pessimistic: lock at read

  • SELECT … FOR UPDATE (SQL Server: UPDLOCK) inside a transaction.
  • Others wait until you commit.
  • Best when conflicts are frequent and retries are costly. Keep it short.

See transactions in 6.2 and ETag + If-Match on APIs in 8.2.

Deadlock: four conditions, break one

Coffman conditionMeansBreak it with
Mutual exclusionOnly one holderImmutable data, lock-free ops
Hold and waitHold one, wait for moreTake all locks at once, or smaller lock scope
No preemptionLocks can't be taken awayTimeouts, release and retry
Circular waitA waits B waits AGlobal lock order (e.g. by account ID)

Livelock

Threads keep backing off for each other and retrying, so nothing finishes. Fix: random jitter on retries.

Starvation

One thread never gets the lock, e.g. a writer behind endless readers. Fix: fair queues, short hold times.

Avoid locks

Immutable objects need no lock. Thread-safe collections do the locking for you.

  • count++ is not atomic: it is read, add, write.
  • Keep locks small and short. Never do I/O or call unknown code while holding one.
  • Prevent deadlock with a fixed lock order plus timeouts. Databases detect deadlocks and kill a victim: retry it.
  • Optimistic for rare conflicts, pessimistic for hot rows.
  • An in-process lock does nothing across two servers. Use the database or a distributed lock.

🔒 Fix in memory: a lock, an atomic op or compare-and-swap.

🗄️ Fix in the database: a row version (optimistic) or SELECT FOR UPDATE (pessimistic).

1.7 Concurrency models: threads, event loop, actors, channels Added

A concurrency model is the rule for how concurrent work shares state: shared memory with locks, one event loop, actors passing messages, channels between tasks, or data split across cores.

Visual: five ways to share work

Compare the models

ModelUse whenFailure modeExamples
Shared memory + locksSmall hot state in one processRaces, deadlocks, contentionJava, C#, C++ threads
Event loopMany I/O waits, little CPUOne CPU-heavy or blocking call freezes everyoneNode.js, Python asyncio
ActorsMany independent entities with stateMailbox overflow, A→B→A call deadlock, hot actorErlang, Akka.NET, Orleans
CSP / channelsPipelines, producer/consumerBlocked sends, leaked consumers, unbounded buffersGo, .NET Channels
Data parallelismCPU work on big dataOverhead on small jobs, races in the loop bodyParallel.For, PLINQ, SIMD, GPU

Key ideas

  • Event loop: async I/O lets one thread juggle thousands of waits (1.3). Node.js moves CPU work to worker_threads. .NET async uses the same idea on a thread pool, so it gets both.
  • Actors: no shared memory and no locks. Erlang and Akka.NET add supervisors ("let it crash"). Orleans adds virtual actors that the runtime places and activates for you (22.10).
  • CSP: "Don't communicate by sharing memory; share memory by communicating" (Go proverb).
  • Data parallelism is parallelism, not concurrency (1.2). Amdahl's law still caps the speed-up.

How to answer "which model?"

  • Most real systems mix models: async I/O at the edge, channels inside, locks for a few hot fields.
  • Never block an event loop or an actor: it stalls everything queued behind it.
  • Every queue needs a bound (back-pressure), or memory grows until the process dies.
  • Actors and channels remove locks, not ordering, retry and overload problems.
  • Shared memory within one process; messages between processes and machines.

// An actor in miniature: one mailbox, one reader, private state, no locks
public sealed class AccountActor
{
    private readonly Channel<decimal> _mailbox = Channel.CreateBounded<decimal>(
        new BoundedChannelOptions(1_000) { SingleReader = true, FullMode = BoundedChannelFullMode.Wait });
    private decimal _balance;   // only RunAsync touches it

    public ValueTask PostAsync(decimal amount, CancellationToken ct) =>
        _mailbox.Writer.WriteAsync(amount, ct);   // waits when full: back-pressure

    public async Task RunAsync(CancellationToken ct)   // start once, e.g. from a BackgroundService
    {
        await foreach (var amount in _mailbox.Reader.ReadAllAsync(ct))
            _balance += amount;   // one message at a time
    }
}

Orleans grains are non-reentrant by default: if grain A awaits B and B calls back into A, they deadlock until the request times out. Avoid call cycles, or allow reentrancy on purpose (RequestContext.AllowCallChainReentrancy(), [AlwaysInterleave] or [Reentrant]).

Five ways to run work at the same time, and how each one breaks. 🧠

🔒 Threads + locks: fast, until races and deadlocks.

🔁 Event loop: one thread, thousands of I/O waits. One CPU-heavy call freezes everyone.

📬 Actors: own your state, one message at a time. Watch for full mailboxes and call cycles.

🚰 Channels: share a pipe, not memory. Always bound the pipe.

⚡ Data parallel: split the data across cores. Amdahl still wins.

Real systems mix them. Which one runs your hot path?

  • Many concurrent, mostly idle connections: APIs, gateways, WebSockets.
  • Memory and thread count stay flat as connections grow.

  • Simplicity matters more than scale: batch jobs, CLIs.

  • Async scales because a waiting request holds a kernel registration, not a thread.
  • Low CPU + high latency = threads blocked, not busy. See 22.4.

1.9 Memory and storage hierarchy Added

Storage is a ladder: each step down is bigger, cheaper per GB and much slower. Fast systems keep hot data high on the ladder and turn random access into sequential access.

The numbers to quote are in the 1.4 and 1.5 latency ladder. Rule of thumb: each step is roughly 10–1,000× slower than the one above.

Locality: why arrays beat linked lists

How it works

  • Temporal locality: data used now is likely used again soon (so cache it). Spatial locality: its neighbours are likely next (so read whole lines and pages).
  • Sequential beats random, on every device. That's why append-only logs (WAL, Kafka) and LSM trees (RocksDB, Cassandra) exist: they turn random writes into sequential ones.
  • Page cache: a write() lands in OS memory and reaches the disk later. Reads of hot files are served from RAM.
  • Durable means it survives a power cut: only after fsync (or write-through) returns. Databases fsync the WAL on commit and batch commits to share one fsync (group commit).
  • Row vs columnar: rows keep a record together; columns keep each field together, so scans read less and compress better.

  • Caches exist to hide the gap between rungs. Hit rate decides speed.

  • write() returning is not durable. fsync is; in a cluster, durable usually also means "on N replicas".

  • OLTP on rows, analytics on columns. Don't run big reports on the OLTP primary.

Why is an array faster than a linked list when both are O(n)? 🧠

📏 The CPU reads memory in 64-byte cache lines. Arrays use every byte; linked lists jump around and miss

💾 Disks love sequential I/O. That's why Kafka, WALs and LSM trees append instead of updating in place

⚠️ write() returning isn't durable. The data sits in the OS page cache until fsync

📊 OLTP wants rows, analytics wants columns. That's the whole case for Parquet

// Top-K largest payments: keep a min-heap of size K, O(n log K)
static List<Payment> TopK(IEnumerable<Payment> all, int k)
{
    var heap = new PriorityQueue<Payment, decimal>(k);
    foreach (var p in all)
    {
        if (heap.Count < k) heap.Enqueue(p, p.Amount);
        else if (p.Amount > heap.Peek().Amount) heap.EnqueueDequeue(p, p.Amount);
    }
    return heap.UnorderedItems.Select(x => x.Element)
               .OrderByDescending(p => p.Amount).ToList();
}

1.11 What happens when you type a URL Added

The classic opener: walk one request from the address bar to DNS, TCP/QUIC, TLS, the edge, your backend and back to pixels on screen.

How it works, step by step

  • HSTS: a host on the HSTS list is upgraded to https before anything is sent.
  • Caches first: a fresh HTTP cache entry skips the network; a cached DNS answer skips the lookup.
  • DNS: the recursive resolver walks root → TLD → authoritative. The answer is often a CNAME to a CDN, cached for the TTL.
  • Connect: TCP handshake, then TLS 1.3 (SNI, ALPN, certificate, keys). QUIC does both in one round trip.
  • Response: compressed (br/gzip) with Cache-Control and ETag, so the next visit is cheaper.
  • Render: sub-resources reuse the connection; render-blocking JS delays first paint.

Trade-offs you tune at each layer

LayerKnobTrade-off
DNSTTLLong = fewer lookups, slow failover
TLSCert lifetimeShort = safer, must automate renewal
CDNCache TTLHigher hit ratio vs stale content
Load balancerSticky sessionsSimple state vs uneven load
ResponseCompressionFewer bytes vs CPU

🎤 How to answer in an interview

1. Breadth first: walk the whole path in about 60-90 s, one line per layer.
2. Ask: "Which layer shall I go deep on?"
3. Go deep with numbers: RTTs, TTLs, cache hit ratio.
4. Close with failures and how you'd observe them (traces, p99).

⚠️ Common slips

Skipping caches, HSTS or the certificate check. Stopping at the server and forgetting rendering.

  • Breadth first, then depth: let the interviewer choose the layer.
  • DNS: resolver → root → TLD → authoritative, cached for the TTL.
  • TLS 1.3 = 1 RTT; QUIC folds TCP + TLS into 1 RTT.
  • Edge order: CDN/WAF → LB → gateway → app → cache → DB.
  • Render: DOM + CSSOM → render tree → layout → paint.

⚡ Quick-fire Q&A

Why are threads cheaper than processes?

They share the parent's memory and resources, so creating and switching them needs no new address space.

Is async always better?

No. It adds complexity (ordering, retries, eventual consistency). Use it when decoupling, spike absorption or long-running work justify it.

Why does p99 latency matter more than average?

If one page calls 10 services, most users hit at least one tail-latency call. The average hides the pain.

How do you prevent deadlocks?

Break one Coffman condition: take locks in one global order (no circular wait), use timeouts and release on failure, keep lock scope small, and avoid locks with immutable data or atomic operations. Databases detect deadlocks and kill a victim, so retry it.

Optimistic or pessimistic concurrency?

Optimistic (row version / ETag, retry on conflict) when conflicts are rare; pessimistic (SELECT ... FOR UPDATE in a short transaction) when the row is hot and retries are costly.

Actors or shared memory with locks?

Actors when you have many independent stateful entities (accounts, devices, sessions): each owns its state and handles one message at a time, so no locks. Shared memory with locks for a few hot fields inside one process, where message passing would only add overhead.

What breaks an event loop?

Any CPU-heavy or blocking call on the loop thread: every other request waits behind it. Move CPU work to worker threads and keep I/O async.

Why did our container get OOM-killed when the app never threw OutOfMemoryException?

The container hit its cgroup memory limit, so the kernel killed the process with SIGKILL (exit code 137, OOMKilled). Nothing in the app gets a chance to run. Compare the limit with working set, look for unbounded caches or queues, and capture a dump with dotnet-dump while memory climbs.

Why can an async server handle 10,000 connections on a handful of threads?

Waiting sockets are registered with the kernel (epoll, kqueue, IOCP, io_uring) instead of each holding a blocked thread. The kernel reports which ones are ready or done, and a few threads run just those. Threads only cost something when there's work to do.

When is a write actually durable?

When it's on stable storage, not just in the OS page cache: after fsync (or a write-through write) returns. Databases fsync the write-ahead log on commit and group commits to share one fsync. In a replicated system, durable usually also means acknowledged by N replicas.

Why do analytics systems store data by column?

Reports scan a few columns over millions of rows. Columnar formats like Parquet read only those columns, compress similar values well, and skip row groups using min/max stats. Row stores suit OLTP, where you fetch or update whole records.

Why do write-heavy stores like Cassandra use an LSM tree instead of a B+tree?

An LSM tree turns writes into sequential appends (WAL + memtable, flushed to SSTables), so ingest is fast. The cost is reads across several files and background compaction; Bloom filters keep those reads cheap.

Which structure would you use for a real-time leaderboard?

A Redis sorted set (a skip list plus a hash): O(log n) score updates, rank lookup and top-N range queries.

What happens when you type a URL? (the short version)

URL parse + HSTS, caches, DNS (resolver → root → TLD → authoritative), TCP + TLS 1.3 (or QUIC), HTTP request through CDN/WAF, load balancer, gateway, app, cache, DB, then a compressed, cacheable response the browser turns into DOM + CSSOM → layout → paint. Go breadth first, then ask which layer to go deep on.

Why is HTTP/3 faster to connect than HTTP/2?

HTTP/2 needs a TCP handshake and then a TLS 1.3 handshake (2 round trips). HTTP/3 runs over QUIC, which combines transport and TLS into 1 round trip, or 0 on a resumed connection.

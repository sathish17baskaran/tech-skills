Section 06

APIs: styles, design, auth, performance & rate limiting

APIs are the contracts between systems. This section covers which API style to use, how to design them well, how to secure them, how to make them fast, and how to protect them.

REST vs GraphQL vs gRPC: stop asking "which is best". Ask "who is the consumer?" 🎯

🌍 External partners → REST (universal, cacheable)

📱 Rich front-end needing flexible data → GraphQL

⚙️ Service-to-service, low latency → gRPC

🔔 "Tell me when it happens" → Webhooks / events

6.2 REST design best practices Added

Nouns for resources, HTTP verbs for actions, status codes for outcomes, and a contract you never break silently.

Methods

VerbUseSafeIdempotent
GETRead✅✅
POSTCreate / action❌❌ (use an Idempotency-Key)
PUTReplace❌✅
PATCHPartial update❌Not guaranteed
DELETERemove❌✅

URL examples

  • ✅ GET /customers/42/accounts
  • ✅ POST /payments
  • ❌ POST /getCustomerAccounts

Status codes cheat sheet

200 OK · 201 Created · 202 Accepted · 204 No Content
304 Not Modified
400 Bad Request · 401 Unauthenticated · 403 Forbidden · 404 Not Found
409 Conflict · 412 Precondition Failed · 422 Unprocessable · 429 Too Many Requests
500 Server Error · 502 Bad Gateway · 503 Unavailable · 504 Gateway Timeout

Versioning

URI /v1/ (most common), header api-version, query ?api-version=, or media type. Only breaking changes need a new major version.

Pagination

Offset ?page=3&size=50 is simple but slow and drifts on deep pages. Cursor / keyset ?after=abc is stable and fast.

Filter / sort / fields

?status=active&sort=-createdAt&fields=id,name

Errors

Use a consistent body such as RFC 9457 Problem Details: type, title, status, detail, traceId.

Concurrency

ETag + If-Match for optimistic locking. Return 412 on conflict.

HATEOAS

Responses include links to next actions. Rarely used in full.

  • Backward-compatible changes: adding optional fields or new endpoints. Breaking changes: removing or renaming fields, changing types, making a field required.
  • Consumers should be tolerant readers (ignore unknown fields).
  • Publish a deprecation policy (e.g. Sunset header, 6–12 months' notice).

6.3 API authentication & authorization

Authentication = who are you? Authorization = what are you allowed to do? (Fail authN → 401. Fail authZ → 403.)

MethodHow it worksGood forCaution
Basic authBase64(user:password) in a headerInternal or legacy onlyCredentials sent every call. TLS is mandatory
API keyStatic key in a headerIdentifying apps, metering, simple partner accessIdentifies an app, not a user. Easy to leak. Rotate
OAuth 2.0 bearer tokenShort-lived access token from an authorization serverDelegated access, user and M2M APIsValidate signature, audience, expiry and scopes
OIDCIdentity layer on OAuth2 (ID token)User login and SSOID token ≠ access token
JWTSelf-contained signed tokenStateless validation at the gatewayCan't revoke easily. Keep expiry short
mTLSBoth sides present X.509 certificatesB2B, service-to-service, open bankingCertificate lifecycle management
HMAC signatureRequest signed with a shared secret + timestampWebhooks, payment APIs (AWS SigV4)Secret distribution, clock skew

Authorization models

  • Scopes (OAuth): what the client app may do, e.g. accounts.read.
  • RBAC: permissions by role. ABAC: by attributes (department, region, time). ReBAC: by relationship (owner of the account).
  • Always check object-level access: can this user see account 42? This is OWASP API #1 (BOLA).

public sealed class AccountOwner : IAuthorizationRequirement;

public sealed class AccountOwnerHandler : AuthorizationHandler<AccountOwner, Account>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext ctx, AccountOwner req, Account account)
    {
        if (account.OwnerId == ctx.User.FindFirst("oid")?.Value) ctx.Succeed(req);
        return Task.CompletedTask;
    }
}

{
    var account = await db.Accounts.FindAsync(id);
    if (account is null) return Results.NotFound();
    var check = await auth.AuthorizeAsync(user, account, new AccountOwner());  // can THIS user see THIS account?
    return check.Succeeded ? Results.Ok(account) : Results.Forbid();          // 403
}).RequireAuthorization();                                                     // 401 if not signed in

6.4 OAuth 2.0, OIDC & JWT deep dive Added

OAuth 2.0 lets an app get limited access to an API on behalf of a user or itself, without ever seeing the user's password.

Four roles

Resource ownerthe user
Clientapp wanting access
Authorization serverEntra ID, Okta, Ping
Resource serveryour API

Authorization Code + PKCE (user-facing apps, SPAs, mobile)

Grant typeUse when
Authorization Code + PKCEAny app acting for a user (web, SPA, mobile)
Client CredentialsMachine-to-machine. No user (batch job, backend service)
Device CodeDevices without a browser (TV, CLI)
Refresh TokenGet a new access token without logging in again
On-Behalf-Of / Token ExchangeAPI A calls API B while keeping the user's identity
Implicit, Password (ROPC)Deprecated in OAuth 2.1 / security best practice

JWT anatomy

  • OAuth = authorization (access token). OIDC = authentication (ID token + userinfo).
  • Never put secrets or sensitive PII in a JWT. It's only encoded.
  • Validate: signature (via JWKS kid), iss, aud, exp/nbf, scopes and roles. Keep access tokens short (5–60 min).
  • SPAs: prefer the BFF pattern (tokens kept server-side) over storing tokens in localStorage.
  • Banking: FAPI (Financial-grade API) profile tightens OAuth with mTLS or private_key_jwt, PAR and JARM. Australia's Consumer Data Right (CDR) uses it.

    .WithCertificate(certificate)
    .WithAuthority($"https://login.microsoftonline.com/{tenantId}")
    .Build();
var result = await msal.AcquireTokenForClient(["api://payments/.default"]).ExecuteAsync();

Login without passwords: ASP.NET Core Identity in .NET 10 supports passkeys (WebAuthn / FIDO2).

OAuth 2.0 explained with a hotel key card 🏨

You (resource owner) show ID at reception (authorization server). You get a key card (access token) that opens only your room (scope) until checkout (expiry).

The door (API) doesn't need your passport. It just checks that the card is valid.

OAuth = what you can access. OIDC = who you are.

6.5 API performance

Measure first (p95/p99 latency, throughput, error rate), find the slowest hop, then fix that hop.

Where the time goes

🗃 Caching

HTTP cache headers, CDN, gateway response cache, Redis.

📄 Pagination & field selection

Never return 10,000 rows. Use cursors and sparse fields.

🗜 Compression

gzip / Brotli for JSON payloads over ~1 KB.

🔌 Connection pooling & keep-alive

Reuse DB and HTTP connections. Avoid a new TLS handshake per call.

⚡ Async processing

Return 202 for long work. Push to a queue.

🧮 Fix the N+1 problem

Batch DB queries (JOIN, IN, DataLoader) instead of one query per item.

📦 Smaller payloads

Protobuf/gRPC internally. Trim unused fields.

🔀 Parallelise calls

Fan out independent downstream calls together, not one after another.

📈 Scale & protect

Auto-scale, load balance, rate limit, timeouts, circuit breakers.

  • Load-test tools: JMeter, k6, Gatling, Azure Load Testing. Monitor with App Insights / APM and distributed tracing.
  • Set a latency budget per hop (e.g. gateway 20 ms, service 50 ms, DB 30 ms).
  • Index DB queries. Slow APIs are usually slow queries.

        .OrderBy(p => p.Id)
        .Take(50)
        .Select(p => new PaymentDto(p.Id, p.Amount, p.Status))   // only the columns needed
        .ToListAsync(ct));

// Fan out independent downstream calls together, not one after another

await Task.WhenAll(customerTask, accountsTask);

Measure with OpenTelemetry traces, dotnet-counters and a load test before tuning. Response compression over HTTPS is off by default because of BREACH-style attacks on secrets in responses.

6.6 Rate limit algorithms

Rate limiting caps how many requests a client can make in a time window. It protects backends, ensures fairness and blocks abuse.

🪣 Token bucket ⭐ most popular

  • Allows bursts up to B, then a steady rate r.
  • ➕ Simple, memory-light, allows bursts. Used by AWS and Stripe.
  • ➖ Two parameters to tune.

💧 Leaky bucket

  • Smooths traffic to a constant output rate.
  • ➕ Steady load on the backend.
  • ➖ Bursts get queued or dropped. Adds latency.

🪟 Fixed window counter

  • Count per calendar window (e.g. per minute).
  • ➕ Simplest (Redis INCR + EXPIRE).
  • ➖ Boundary burst problem.

📜 Sliding window log

  • ➕ Exact, no boundary problem.
  • ➖ Memory-heavy (one entry per request).

🧮 Sliding window counter

  • Blends the current and previous fixed windows.
  • ➕ Accurate enough, low memory. Popular at scale (used by Cloudflare).
  • ➖ An approximation.
AlgorithmBurstsAccuracyMemoryTypical use
Token bucketAllowed (up to B)GoodLowAPI gateways, public APIs
Leaky bucketSmoothedGoodLowTraffic shaping, protecting fragile backends
Fixed window2× at edgesWeakLowestSimple quotas
Sliding logNoExactHighLow-volume, strict limits
Sliding counterMinimalVery goodLowHigh-scale distributed limits

How to apply it

  • Where: at the edge (API gateway / APIM / WAF) first, then inside services for fine-grained limits.
  • Key by: API key, user, client ID, IP, tenant, endpoint.
  • Respond: 429 Too Many Requests + Retry-After, plus RateLimit-Limit / Remaining / Reset headers.
  • Distributed: keep counters in Redis (atomic Lua scripts) so all gateway nodes share them.
  • Rate limit (short term, e.g. 100/s) vs quota (long term, e.g. 1M/month) vs throttling (slowing down rather than rejecting).
  • Clients should back off with exponential backoff and jitter when they get a 429.
  • Tiered limits per product or plan (Free / Gold / Partner) is a classic APIM setup.

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.AddPolicy("per-api-key", http => RateLimitPartition.GetTokenBucketLimiter(
        partitionKey: http.Request.Headers["X-Api-Key"].ToString() is { Length: > 0 } key
            ? key : $"ip:{http.Connection.RemoteIpAddress}",
        factory: _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 100,                              // bucket size B (max burst)
            TokensPerPeriod = 10,                          // refill r ...
            ReplenishmentPeriod = TimeSpan.FromSeconds(1), // ... per second
            QueueLimit = 0                                 // reject at once, don't queue
        }));
    o.OnRejected = (ctx, ct) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter))
            ctx.HttpContext.Response.Headers.RetryAfter = ((int)Math.Ceiling(retryAfter.TotalSeconds)).ToString();
        return ValueTask.CompletedTask;
    };
});

var app = builder.Build();
app.UseRateLimiter();
app.MapPost("/payments", CreatePayment).RequireRateLimiting("per-api-key");

Built-in limiters count per instance (10 nodes = 10× the limit). Authenticate the key before using it as a partition, or callers can invent keys to get fresh buckets. On the client side, Microsoft.Extensions.Http.Resilience retries honour Retry-After.

5 rate-limiting algorithms in one post 🚦

🪣 Token bucket: allows bursts, then a steady rate

💧 Leaky bucket: smooth, constant output

🪟 Fixed window: simple, but 2× bursts at the edges

📜 Sliding log: exact, memory hungry

🧮 Sliding counter: the practical sweet spot

Rule of thumb: token bucket at the gateway, return 429 + Retry-After, and let clients back off.

6.7 Idempotency Added

An operation is idempotent if doing it once or many times has the same effect. Essential when networks retry.

  • Payments, transfers and order creation must be idempotent.
  • Store keys with a TTL (e.g. 24 h). Scope them per client. Reject the same key sent with a different payload.
  • Message consumers: deduplicate by message ID (the idempotent receiver pattern).
.NET 10 How to implement it
PieceLibrary / API
Read the keybuilt-in IEndpointFilter on the POST endpoints (there's no built-in idempotency middleware)
Store the responseIDistributedCache on Redis (Microsoft.Extensions.Caching.StackExchangeRedis) or a SQL table, with a 24 h TTL
Hard guaranteeA unique index on (ClientId, IdempotencyKey) (EF Core HasIndex(…).IsUnique()), written in the same transaction as the payment
Message consumersIdempotent receiver: insert the message ID into a processed-messages table with a unique key, in the same transaction as the business change
ClientsMicrosoft.Extensions.Http.Resilience retries: send the same Idempotency-Key on every retry
public sealed class IdempotencyFilter(IDistributedCache cache) : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var http = ctx.HttpContext;
        string? key = http.Request.Headers["Idempotency-Key"];
        if (string.IsNullOrWhiteSpace(key))
            return TypedResults.Problem("Idempotency-Key header is required", statusCode: 400);

        var cacheKey = $"idem:{http.User.FindFirst("azp")?.Value}:{key}";   // scope keys per client
        if (await cache.GetStringAsync(cacheKey) is { } saved)
            return TypedResults.Text(saved, "application/json");          // replay, don't charge twice

        var result = await next(ctx);
        if (result is IValueHttpResult { Value: { } value })
            await cache.SetStringAsync(cacheKey, JsonSerializer.Serialize(value, JsonSerializerOptions.Web),
                new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(24) });
        return result;
    }
}
// app.MapPost("/payments", CreatePayment).AddEndpointFilter<IdempotencyFilter>();

This sketch has a race: two identical requests arriving together both run. Claim the key first (Redis SET NX or the unique index), store a hash of the body to reject the same key with a different payload (422), and replay the original status code too.

⚡ Quick-fire Q&A

API key vs OAuth token?

An API key identifies the calling app and never expires unless rotated. An OAuth token is short-lived, scoped, can represent a user, and is issued by a trusted authorization server.

Which grant type for a nightly batch job calling an API?

Client Credentials, ideally with a certificate or private_key_jwt, or a managed identity, instead of a client secret.

How do you rate limit across 10 gateway nodes?

Use a shared counter store (Redis) with atomic operations, or a gateway feature with synchronised counters. Accept slight approximation for speed.

401 vs 403?

401: we don't know who you are (missing or invalid token). 403: we know who you are, but you're not allowed.

Algorithms

Round robin

Bigger servers get more traffic. Also used for canary releases (90/10).

Send to the server with the fewest active connections. Good for long requests.

The same client goes to the same server. Session affinity.

Consistent hashing

Key-based routing that barely reshuffles when nodes change (caches, shards).

3.4 Consistent hashing Added

Place nodes and keys on a hash ring. Each key belongs to the next node clockwise, so adding a node only moves about 1/N of the keys.

Watch Node E join: only the keys between Node A and Node E (they used to belong to Node B) move to E. Every other key stays where it is. With hash(key) mod N, changing N from 4 to 5 sends almost every key to a different node. Virtual nodes = each server appears many times on the ring, which gives an even spread.

  • Used in Cassandra, DynamoDB, Redis Cluster (hash slots), CDNs and distributed caches.
.NET 10 How to implement it
Library / APIPackageUse it for
XxHash3 / XxHash64System.IO.HashingFast, stable hash for ring positions. Don't use string.GetHashCode(): it changes on every process start
Sorted array + BinarySearchbuilt-in SortedList, Array.BinarySearchFind the next node clockwise in O(log n). .NET has no built-in hash ring
Redis ClusterStackExchange.RedisRedis uses 16,384 hash slots instead of a ring; the client routes each key for you
Cosmos DB / Kafka partitionsMicrosoft.Azure.Cosmos, Confluent.KafkaPick a good partition key; the service does the hashing
public sealed class HashRing
{
    private readonly ulong[] _positions;   // sorted points on the ring
    private readonly string[] _nodes;      // node that owns each point

    public HashRing(IEnumerable<string> nodes, int virtualNodes = 100)
    {
        var ring = new SortedList<ulong, string>();
        foreach (var node in nodes)
            for (var i = 0; i < virtualNodes; i++)
                ring[Hash($"{node}#{i}")] = node;   // many points per node = even spread
        _positions = [.. ring.Keys];
        _nodes = [.. ring.Values];
    }

    public string GetNode(string key)
    {
        var i = Array.BinarySearch(_positions, Hash(key));
        if (i < 0) i = ~i;                                // first point clockwise
        return _nodes[i == _positions.Length ? 0 : i];    // wrap around the ring
    }

    private static ulong Hash(string s) => XxHash3.HashToUInt64(Encoding.UTF8.GetBytes(s));
}

3.5 Fault tolerance

The system keeps working, maybe in a reduced mode, when parts of it fail. Design assuming everything fails eventually.

High availability

Minimise downtime with redundancy and fast failover. A brief blip is OK.

Fault tolerance

No interruption at all when a component fails. Costs more.

Resilience

Absorb the failure, degrade gracefully and recover automatically.

How it's achieved

  • Remove single points of failure (SPOF): at least 2 of everything, across availability zones.
  • Redundancy models: active-active (all serve traffic) or active-passive (standby takes over). N+1 or N+2 capacity.
  • Replication of data: synchronous (no data loss, slower) or asynchronous (fast, may lose recent writes).
  • Failover: automatic detection (health checks, heartbeats) and switchover. Leader election (Raft/Paxos) for clusters.
  • Isolation: bulkheads and cells (see 3.14), so one failure doesn't sink everything.
  • Graceful degradation: serve cached or partial data, turn off non-critical features.
  • Chaos engineering: inject failures on purpose to prove resilience (Chaos Monkey, Azure Chaos Studio).

3.6 Resilience patterns: timeout, retry, circuit breaker, bulkhead Added

Code-level patterns that stop one slow or failing dependency from taking everything down with it.

⏱ Timeout

Never wait forever. Set connect and read timeouts below the caller's own timeout.

🔁 Retry + exponential backoff + jitter

Retry only transient errors (503, timeouts): 100 ms, 200 ms, 400 ms + random. Cap the attempts. Only retry idempotent operations.

🔌 Circuit breaker

After N failures, stop calling the dependency and fail fast. Probe again later.

🚢 Bulkhead

Give each dependency its own thread or connection pool, so one bad one can't use up all resources.

🪂 Fallback

Default value, cached response or friendly message.

🚦 Rate limit / load shedding

Reject extra load early (429/503) to protect the core.

Circuit breaker states

CLOSEDcalls flow, count failures
→failures ≥ threshold
OPENfail fast, no calls
→after cool-down
HALF-OPENlet a few test calls through
→success → CLOSED / fail → OPEN
  • Retries without backoff or jitter cause retry storms that make an outage worse.
  • Retry in one layer only. Retrying at every layer multiplies traffic (3 layers × 3 retries = 27×).
  • Libraries: Polly (.NET), Resilience4j (Java), and service mesh / APIM policies.
.NET 10 How to implement it
PatternLibrary / API
All-in-one for HttpClient ★Microsoft.Extensions.Http.Resilience: AddStandardResilienceHandler() = concurrency limit + total timeout + retry + circuit breaker + per-attempt timeout, with good defaults
Timeout / retry / circuit breakerPolly v8 (Polly.Core) ResiliencePipelineBuilder: AddTimeout, AddRetry (exponential backoff + jitter), AddCircuitBreaker
BulkheadPolly.RateLimiting (AddConcurrencyLimiter), or a SemaphoreSlim per dependency
HedgingAddStandardHedgingHandler(): send a second request if the first is slow
Non-HTTP callsMicrosoft.Extensions.Resilience: AddResiliencePipeline("name", ...) + ResiliencePipelineProvider<string>, with telemetry
// HttpClient: one line gives timeout, retry, circuit breaker and bulkhead
builder.Services.AddHttpClient<FxClient>(c => c.BaseAddress = new("https://fx.internal/"))
    .AddStandardResilienceHandler(o =>
    {
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
        o.Retry.MaxRetryAttempts = 3;               // backoff + jitter by default
    });

// Anything else (DB, SDK): a named Polly v8 pipeline. First added = outermost
builder.Services.AddResiliencePipeline("ledger", p => p
    .AddRetry(new() { MaxRetryAttempts = 3, BackoffType = DelayBackoffType.Exponential, UseJitter = true })
    .AddCircuitBreaker(new() { FailureRatio = 0.5, MinimumThroughput = 10, BreakDuration = TimeSpan.FromSeconds(30) })
    .AddTimeout(TimeSpan.FromSeconds(3)));

// Usage (inject ResiliencePipelineProvider<string> provider)
await provider.GetPipeline("ledger").ExecuteAsync(async t => await ledger.PostAsync(entry, t), ct);

Only retry idempotent operations, or send an idempotency key. Retrying a payment POST without one can charge the customer twice. The standard handler retries every method by default; call o.Retry.DisableForUnsafeHttpMethods() to stop that.

The circuit breaker pattern is literally your home fuse box ⚡

Too many failures → trip (OPEN) → stop calling the broken service → after a cool-down, try one call (HALF-OPEN) → healthy? Back to normal (CLOSED).

Fail fast > fail slow. A slow failure takes your threads, your users and your weekend.

3.7 Availability (HA & "the nines") Added

Availability is the percentage of time a system is up and working correctly for its users. High availability (HA) means designing it so failures cause little or no downtime.

How it's measured

⏱ Time-based

Availability = uptime ÷ (uptime + downtime)

= MTBF ÷ (MTBF + MTTR)

MTBF = mean time between failures. MTTR = mean time to recover.

📨 Request-based (preferred for APIs)

Availability = successful requests ÷ total valid requests

e.g. 999,000 good out of 1,000,000 = 99.9%. This reflects what users actually experienced.

Availability

Is it up and answering right now?

Reliability

Does it work correctly over time, without failing? (MTBF)

Durability

Is the data kept safe and never lost? (Storage: 11 nines of durability ≠ 11 nines of availability.)

Resilience

How well does it absorb failures and recover?

The nines

AvailabilityDowntime / yearDowntime / month
99% (two nines)3.65 days7.3 h
99.9%8.77 h43.8 min
99.95%4.38 h21.9 min
99.99%52.6 min4.4 min
99.999%5.26 min26 s

Composite availability

In series (A calls B): multiply.
99.9% × 99.9% = 99.8%. Each dependency lowers the total.

In parallel (redundant copies): 1 − (1 − a)ⁿ
Two 99% nodes → 1 − 0.01² = 99.99%.

Redundancy raises availability. Long dependency chains lower it.

Active-active

All sites serve traffic at the same time.

  • ➕ Near-zero failover time, capacity is already warm
  • ➖ Costly. Data consistency across sites is hard

Active-passive

A standby takes over when the primary fails (hot, warm or cold).

  • ➕ Simpler, cheaper
  • ➖ Failover takes time. The standby may be untested or stale
  • Two levers: fail less often (raise MTBF: redundancy, testing, change control) and recover faster (cut MTTR: detection, automated failover, rollback). Recovering faster is usually cheaper.
  • Changes cause most outages. Safe deployment practices protect availability as much as redundancy does.
  • Agree whether planned maintenance counts as downtime in the SLA.
  • Availability is only as high as your weakest required dependency, including DNS, the identity provider, certificates and third-party APIs.
  • Pick a target from the business impact. 99.99% costs far more than 99.9%. Don't over-engineer internal or batch systems.

3.8 Performance Added

Performance is how fast a system responds and how much work it can get through with the resources it has.

Key metrics

⏱ Latency / response time

Time for one request. Track p50, p95 and p99, not the average.

🚚 Throughput

Work per second: requests/s, TPS, messages/s, MB/s.

📊 Utilisation

How busy the resources are: CPU, memory, connections, threads, DB DTU.

❌ Error rate under load

Timeouts and 5xx often appear only when load rises.

Performance vs scalability

Performance problem

The system is slow even for one user. Fix the code, query, algorithm or network path.

Scalability problem

Fast for one user, but slows down as load grows. Fix capacity, contention or the architecture (scale out, cache, queue, partition).

Why things slow down under load: queueing

Response time = network + waiting in queue + service time. Waiting time explodes as utilisation approaches 100% (simple queue model: R = S ÷ (1 − U), where S is the service time and U the utilisation).

Where the time goes, and what to do about it

Is your system slow, or just busy? 🐢 vs 🚦

Slow for ONE user → a performance problem (code, query, network).

Fast for one, slow for MANY → a scalability problem (capacity, contention).

3.9 Capacity planning & cost (FinOps) Added

Capacity planning makes sure you have enough resources for the peak, with headroom. FinOps makes sure you don't pay for much more than that.

Capacity planning in 6 steps

1. Baselinetoday's load, p95, CPU per request
→
2. Forecastgrowth, seasonality, campaigns
→
3. Add headroomrun at 60–70%, N+1 for failures
→
4. Load testprove the per-instance limit
→
5. Set autoscale limitsmin, max, quotas, DB limits
→
6. Reviewmonthly, after big events
  • Find the peak, not the average: payday, end of month, Black Friday, end of financial year (30 June in Australia), a marketing push.
  • Find the bottleneck resource: often the database (DTU/vCores, connections), not the stateless web tier.
  • Check the limits you can't autoscale: subscription quotas, IP addresses in a subnet, DB connection limits, third-party API rate limits, licences.
  • Plan for losing a zone: if one of 3 zones goes down, the other 2 must carry the full peak.

Little's Law: how much concurrency do I need?

L = λ × W

L = average number of requests in the system (in flight)

λ (lambda) = arrival rate (requests per second)

W = average time each request spends in the system

Works for any stable system: APIs, queues, call centres, bank branches.

🧮 Example

Peak = 400 requests/s, average response = 0.25 s.

L = 400 × 0.25 = 100 requests in flight.

Load test shows one instance handles 25 concurrent requests at 65% CPU → 100 ÷ 25 = 4 instances, + 1 for a failure (N+1) = 5.

If a slow dependency doubles W to 0.5 s, L doubles to 200. Latency eats capacity.

📏 Unit economics

Track cost per transaction, per customer or per payment, not just the total bill. A rising bill with a falling unit cost is healthy growth.

📉 Right-sizing

Most VMs and DBs are over-provisioned. Use utilisation data (Azure Advisor, AWS Compute Optimizer) to step down a size. Turn off non-prod at night.

🤝 Commitments

Reservations and savings plans (1 or 3 years) cut the price of steady, always-on load. Commit to the baseline only, not the peak.

⚡ Spot / preemptible

Big discounts on spare capacity, but the cloud can take it back at short notice. Only for interruptible work: batch, CI, stateless workers.

🏷 Tagging

Tag every resource (app, env, owner, cost-centre) and enforce it with policy. No tags = no showback.

🔔 Budgets & alerts

Budgets per subscription or team, alerts at 50/80/100% and on anomalies. A forgotten GPU or log ingestion spike shows up in days, not at month end.

  • Little's Law: concurrency = throughput × latency. Cut latency and you need fewer instances.
  • Write cost as an NFR: "under $0.002 per payment at 500 TPS". Then it can be designed, tested and traded off like latency.
  • Commit (reserve) for the baseline, autoscale for the peak, spot for interruptible work.
  • Scaling has limits you can't buy your way past quickly: quotas, DB connections, downstream rate limits. Find them in the load test, not in production.

    }

One formula every architect should know: L = λ × W 🧮

📥 λ = how many requests arrive per second

⏱ W = how long each one takes

🔄 L = how many are in flight at once, which is the capacity you must provide

400 req/s × 0.25 s = 100 in flight. If a slow dependency doubles latency, you need double the capacity. Latency is a cost.

💸 Then FinOps: reserve the baseline, autoscale the peak, use spot for batch, and track cost per transaction, not just the bill.

3.10 SLA vs SLO vs SLI & error budgets Added

SLI is what you measure, SLO is the target you set, SLA is what you promise in a contract (with penalties).

SLI99.95% of requests < 300 ms (measured)
→
SLOinternal target: 99.9%
→
SLAcontract: 99.5%, or service credits
  • Set SLO stricter than SLA, so you get warned before you break the contract.
  • Error budget = 100% − SLO. At 99.9%, you get 43 min/month for incidents and risky releases. Budget used up → freeze features, fix reliability.
  • Good SLIs: availability (success rate), latency (p95/p99), freshness, correctness.

3.11 CAP theorem

When a network Partition splits a distributed data store, it must choose between Consistency (everyone sees the latest write) and Availability (every request gets an answer).

How it plays out

  • It's not "pick any 2 of 3". In a distributed system, partitions will happen, so P is a given. The real choice is C or A during a partition.
  • "C" in CAP means linearizability, which is different from the "C" in ACID (constraint validity).
  • Banking ledgers and payments usually choose CP. Social feeds, carts and catalogues often choose AP.
  • Many databases let you tune this per request (Cassandra consistency levels, Cosmos DB's 5 levels).
.NET 10 How to implement it

CAP theorem in 20 seconds ⏱

Network splits happen. When they do, your database must choose:

🔵 Consistency: "I'd rather say nothing than say something wrong." (payments, ledgers)

🟢 Availability: "I'll answer, even if it's a bit stale." (likes, product catalogue)

It's not "pick 2 of 3". It's "pick C or A when P happens".

3.12 PACELC & consistency models Added

PACELC extends CAP: if there's a Partition choose A or C; Else (normal operation) choose Latency or Consistency.

Examples

  • PA/EL: Cassandra, DynamoDB. Fast, eventually consistent.
  • PC/EC: traditional RDBMS clusters, Spanner. Always consistent.
  • PA/EC or tunable: MongoDB, Cosmos DB.

Consistency spectrum (strong → weak)

  • Strong / linearizable: reads always see the latest write
  • Bounded staleness: at most X seconds or versions behind
  • Session / read-your-writes: you always see your own updates
  • Causal: cause is seen before effect
  • Eventual: copies converge… eventually
  • Quorum rule: with N replicas, if writes go to W and reads to R where R + W > N, reads see the latest write. Example: N=3, W=2, R=2.

3.14 Cell-based architecture & multi-region active-active Added

Split the whole stack (app, data, cache, queues) into independent copies called cells, each serving a slice of customers, so one failure or bad deployment only hurts that slice.

🧱 Cell

A complete, self-contained copy of the service with its own database. Sized to a known maximum (e.g. 50,000 customers). Azure calls this the Deployment Stamps pattern.

🧭 Cell router

A thin, very simple layer that maps a cell key (tenant, customer or account ID) to a cell and forwards the request. It must be the most reliable part of the system.

💥 Blast radius

With 10 cells, a poison request, bad config or DB outage affects about 10% of customers, not 100%.

📈 Scale by adding cells

Instead of growing one giant cluster, add a new cell when existing cells are full. Each cell stays a size you've tested.

Across regions: active-active vs active-passive vs pilot light

ModelSecond regionFailoverCost and complexity
Active-activeServes live traffic all the timeNear zero: shift trafficHighest. Each region needs headroom to take everything, and data conflicts must be handled
Active-passive (warm standby)Running, scaled down, not servingMinutes: scale up, switch trafficMedium. Simpler data (one writer)
Pilot lightOnly data is replicated; compute is off or minimalTens of minutes or more: deploy and start computeLow. Needs good automation (IaC)

These are the same strategies as the DR table in 3.13, seen from the traffic side.

Data replication and conflicts

  • Single writer per record (simplest): each customer has a home region for writes; any region can serve reads. No write conflicts. Common for ledgers and account balances.
  • Multi-region writes: any region accepts writes for any record, so two regions can change the same record at once. You need a conflict policy:
    • Last writer wins (by timestamp): simple, but silently drops one update. Fine for profiles, wrong for balances.
    • Custom merge: app or stored procedure decides. CRDTs: data types that merge automatically (counters, sets).
    • Avoid the conflict: route all writes for one account to one region.
  • Cross-region replication is usually asynchronous (hundreds of km means milliseconds of extra latency per write), so RPO is above zero unless you pay for synchronous writes.

✓ Worth it when

  • The availability target is 99.99% or higher, or a region outage is unacceptable to the business or regulator
  • Large multi-tenant platforms where one noisy or broken tenant must not hurt the rest
  • You need to deploy safely in waves at scale

✗ Probably not when

  • Single-region with zones already meets the SLO
  • The team can't yet automate deployments and failover
  • Data must be strongly consistent across regions on every write and the latency cost is unacceptable
  • Cells shrink the blast radius; multi-region protects against region loss. Big platforms combine them: several cells per region.
  • Keep the cell router dumb and static (a lookup table), and cache the mapping. A complex router becomes the new single point of failure.
  • Active-active only works if each region can take the full load, and you've decided how write conflicts are avoided or resolved.
  • Test failover regularly. Traffic shifting is easy; data and capacity are where it breaks.

Don't build one giant system. Build many small identical ones 🧱

That's cell-based architecture:

🧭 A thin router maps each customer to a cell

🧱 Each cell has its own app, database and cache

💥 A bad deploy or DB outage hits one cell (say 10% of customers), not everyone

📈 Need more capacity? Add a cell. Never run a size you haven't tested

Add multi-region active-active on top, and the hard part is no longer routing. It's capacity headroom and write conflicts.

⚡ Quick-fire Q&A

Your service has 3 dependencies at 99.9% each. What's your max availability?

About 99.7% (0.999³). To do better, add redundancy, caching or async decoupling.

When would you choose AP over CP?

When stale data is acceptable and downtime isn't: product catalogues, social feeds, recommendations, shopping carts.

Difference between HA and DR?

HA handles local failures (node or zone) automatically with little or no downtime. DR recovers from a large-scale disaster (region loss, ransomware) within the agreed RPO/RTO.

Peak is 600 requests/s and the average response time is 200 ms. How many requests are in flight?

Little's Law: L = λ × W = 600 × 0.2 = 120. If one instance handles 30 concurrently at a safe utilisation, you need 4, plus at least 1 spare for failures or a lost zone.

What is a cell-based architecture, and why use it?

Many independent copies of the whole stack, each serving a fixed slice of customers, behind a thin router. A failure or bad deployment only affects one cell's customers (smaller blast radius), and you scale by adding cells of a tested size.

Active-active across regions: what's the hardest part?

Not routing. It's data (async replication means possible loss or write conflicts, so pick a home region per record or a conflict policy) and capacity (each region must be able to take 100% of traffic after a failover).

11.1 Different types of architecture patterns

An architecture style is the overall shape of a system: how it's split into parts and how those parts talk.

🧱 Monolith

One deployable unit. Simple to build, test and deploy at first. Grows into a "big ball of mud".

🍰 Layered / N-tier

Presentation → Business → Data. Classic enterprise style. Watch out for "sinkhole" layers that only pass calls through.

📦 Modular monolith

One deployable, with strict module boundaries inside. A great default before microservices.

🔗 SOA

Coarse-grained shared services, often through an ESB. The predecessor of microservices.

🧩 Microservices

Small, independently deployable services, each owning one business capability and its data.

⚡ Event-driven

Components communicate through events (broker or mediator topology). Highly decoupled.

☁️ Serverless

Functions and managed services. No servers to manage, pay per use.

⬡ Hexagonal / Clean / Onion

Domain at the centre. Ports and adapters isolate it from DBs, UIs and frameworks. Very testable. More in 11.2.

🔌 Microkernel (plug-in)

Core system + plug-ins (IDEs, rules engines, browsers).

🌌 Space-based

In-memory data grid and processing units, for extreme, spiky scale.

🖼 Micro-frontends

The UI split by domain, each part owned by its own team.

🧫 Cell-based

Copies of the full stack ("cells"), each serving a slice of users, so one failure has a limited blast radius.

11.2 Hexagonal, Clean & Onion architecture Added

Put the business rules in the middle and make every dependency point inwards. The database, UI and frameworks become replaceable plug-ins at the edge.

The ports-and-adapters diagram is in 11.1. This section covers the rule behind it, how the three names differ, and when the pattern is overkill.

🔌 Port

An interface the core owns. Inbound (driving) port: a use case the outside calls, like TransferFunds. Outbound (driven) port: something the core needs, like IAccountStore.

🧩 Adapter

The code at the edge that plugs into a port: an API endpoint or queue listener (inbound), an EF Core repository or HTTP client (outbound).

➡️ Dependency rule

Outer code may use inner code, never the reverse. The core declares an interface. Infrastructure implements it (dependency inversion).

Hexagonal (ports & adapters)OnionClean

Mostly the same idea with different names: domain in the middle, dependencies pointing inwards, I/O at the edge.

✅ Benefits

  • Test business rules in milliseconds, with fakes and no database
  • Swap a database, broker or vendor API without touching the rules
  • Framework upgrades stay at the edge
  • Clear places for code to live

⚠️ Overkill risks

  • Simple CRUD drowning in mappers and pass-through layers
  • An interface for every class "just in case"
  • A repository wrapping EF Core, which is already a repository
  • Many projects and ceremony that slow small teams down

The alternative: vertical slice architecture

  • Organise by feature, not by technical layer: one folder per use case holds the endpoint, request, handler and data access.
  • Each slice picks the simplest approach it needs. A report can query SQL directly; a complex payment flow can use a rich domain model.
  • Change one feature in one place. Fewer shared abstractions to break.
  • They mix well: vertical slices on the outside, a clean domain core for the complex parts.
  • Explain it with one test: "Does my domain project reference EF Core or ASP.NET Core?" If yes, it isn't clean, whatever the folders are called.
  • Use it for complex, long-lived domains (payments, lending rules). For simple CRUD, vertical slices or a plain layered app is often better.
  • Enforce the rule with architecture tests in CI (example in 11.1).

// Application (inner): owns the port. No EF Core, no HTTP.
public interface IAccountStore                              // outbound port
{
    Task<Account?> FindAsync(Guid id, CancellationToken ct);
    Task SaveAsync(CancellationToken ct);                   // one unit of work
}

public sealed class TransferFunds(IAccountStore store)      // use case (inbound port)
{
    public async Task Handle(Guid from, Guid to, decimal amount, CancellationToken ct)
    {
        var source = await store.FindAsync(from, ct) ?? throw new KeyNotFoundException();
        var target = await store.FindAsync(to, ct) ?? throw new KeyNotFoundException();
        source.Withdraw(amount);                            // the rules live in the domain
        target.Deposit(amount);
        await store.SaveAsync(ct);
    }
}

// Infrastructure (outer): the adapter depends on the port, not the other way round
public sealed class EfAccountStore(BankDbContext db) : IAccountStore
{
    public Task<Account?> FindAsync(Guid id, CancellationToken ct) =>
        db.Accounts.FindAsync([id], ct).AsTask();
    public Task SaveAsync(CancellationToken ct) => db.SaveChangesAsync(ct);
}

// Api (outermost): wire it up
builder.Services.AddScoped<IAccountStore, EfAccountStore>();
builder.Services.AddScoped<TransferFunds>();

Clean, Onion, Hexagonal: three names, one rule 🧅

🎯 Business rules sit in the middle.

➡️ Every dependency points inwards. The core never names EF Core, ASP.NET Core or Kafka.

🔌 Ports are interfaces the core owns. Adapters are the DB, API and broker code at the edge.

🧪 You can test the core in milliseconds, with no database.

⚠️ For simple CRUD it's ceremony. Try vertical slices instead.

Quick check: does your Domain project reference EF Core? Then it isn't clean, whatever the folders say.

Microservices don't remove complexity. They move it 🚚

From: tangled code in one app

To: network calls, retries, sagas, tracing, 40 pipelines and eventual consistency

Worth it when you have many teams, different scaling needs and clear domain boundaries. Otherwise, a modular monolith wins.

11.5 Microservice API patterns Added

How clients reach many services through one front door, and how services call each other without turning into a distributed monolith.

  • Edge patterns decide how clients get in: gateway, BFF, composition.
  • Service-to-service patterns decide how services talk: sync, async, events.
  • Contract patterns decide how APIs change without breaking anyone: versioning, tolerant reader, contract tests.

API composition with a slow service

1. Edge patterns: how clients get in

PatternWhat it doesUse whenWatch out
API gateway (routing + offloading)One entry point. Routes by path and handles TLS, token validation, rate limits and CORSYou expose more than a couple of servicesKeep business logic out. A "smart gateway" becomes the new monolith
Gateway aggregationThe gateway merges several backend calls into one responseSimple, read-only mergesLogic creeps in. Use a BFF for anything screen-specific
Backend for Frontend (BFF)One API per client type (mobile, web, partner), owned by that client's teamClients need very different shapes, or a SPA needs secure cookie authDon't copy domain rules into each BFF. Keep them in the services
API compositionA composer calls several services and joins the results in memoryRead queries that span servicesBig joins, sorting and paging get slow. Use a CQRS read model instead

2. Service-to-service: how services talk

PatternWhat it doesUse whenWatch out
Sync request/response (REST, gRPC)The caller waits for the answerThe caller needs the answer to continue, e.g. "is the balance enough?"Temporal coupling: if B is down, A fails. Always set a timeout

Scatter-gather (branch)Fan out in parallel, then combine the answersQuotes or search across several providersSet a total deadline and return partial results

5. Message and payload patterns

Small decisions inside each API, from the book Patterns for API Design (Zimmermann et al.):

📄 Pagination

  • Cursor paging for big or changing lists
  • Offset paging only for small, stable lists

🎯 Wish list

  • Let callers pick fields: ?fields=id,balance
  • Smaller payloads for mobile

📦 Request bundle

  • Send many items in one call
  • Return a result per item

🔁 Conditional request

  • ETag + If-None-Match returns 304
  • If-Match stops lost updates

🔗 Embed or link

  • Embed small related data
  • Link to large or rarely used data

🛡 Safe retries and errors

  • Idempotency-Key on POST
  • Errors as Problem Details (RFC 9457)
  • 429 + Retry-After for rate limits

Smells to call out in a design review: chatty APIs (many calls per screen), synchronous chains of 4+ services, two services sharing one database, CRUD-per-table services, business rules in the gateway, breaking changes without a version, and retries on calls that aren't idempotent.

  • Design APIs around business capabilities and tasks, not database tables.
  • Use sync for answers you need now, and async for side effects.
  • Every remote call needs a timeout, retries only if it is idempotent, and a fallback.
  • Pass a deadline and a trace ID (W3C traceparent) through every hop.
  • Adding fields is free. A breaking change costs a version and a migration plan.
  • Prefer fewer, coarser calls across the network. Chatty is the enemy.

    .AddStandardResilienceHandler(o => o.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(800));

app.MapGet("/dashboard", async (ClaimsPrincipal user,
    AccountsClient accounts, CardsClient cards, CancellationToken ct) =>
{
    var id = user.FindFirstValue(ClaimTypes.NameIdentifier)!;
    var balancesTask = accounts.GetAsync(id, ct);       // required
    var cardsTask    = Try(cards.GetAsync(id, ct));     // optional tile, runs in parallel

    var balances = await balancesTask;                  // let a required call fail
    var myCards  = await cardsTask;
    return TypedResults.Ok(new DashboardView(balances, myCards, Degraded: myCards is null));
}).RequireAuthorization();

app.Run();

static async Task<T?> Try<T>(Task<T> call) where T : class
{
    try { return await call; }
    catch (Exception ex) when (ex is HttpRequestException
        or TimeoutRejectedException or BrokenCircuitException)
    { return null; }                                    // degrade, don't fail the page
}

Task.WhenAll on its own fails the whole response when one call fails. Decide per call: required calls may fail the request, optional calls degrade.

Most microservice pain shows up at the API layer, not in the code 🔌

5 API patterns I check in every design review:

1️⃣ Gateway: one front door. Routing, auth, rate limits. Zero business logic.
2️⃣ BFF: one API per client type. Mobile shouldn't pay for web's payload.
3️⃣ Composition: fan out in parallel, and return partial data when a tile is slow.
4️⃣ Async request-reply: 202 + a status URL for anything slower than a few seconds.
5️⃣ Events: publish what happened, and let others subscribe.

One smell to watch: if a request crosses 4 services synchronously, you've built a distributed monolith.

11.6 Saga pattern Added

A long business transaction split into local transactions. If one step fails, compensating actions undo the earlier steps.

  • Choreography saga: each service listens for events and emits the next one.
  • Orchestration saga: a central orchestrator calls each step and triggers compensation.
  • Sagas give eventual consistency, not ACID isolation. Use semantic locks or "pending" states.
.NET 10 How to implement it
Library / APIPackageUse it for
Durable FunctionsMicrosoft.Azure.Functions.Worker.Extensions.DurableTaskOrchestration sagas as plain C#: try the steps, compensate in catch

Wolverine sagasWolverineFxMessage-driven sagas with state stored in Marten or EF Core
MassTransit state machinesMassTransit commercial licence (v9+)Event-driven saga state machines with many persistence options
NServiceBus sagasNServiceBus commercial licenceLong-running processes with timeouts and strong tooling
[Function(nameof(PaymentSaga))]
public static async Task PaymentSaga([OrchestrationTrigger] TaskOrchestrationContext ctx)
{
    var payment = ctx.GetInput<Payment>()!;
    var undo = new Stack<string>();
    try
    {
        await ctx.CallActivityAsync("ReserveFunds", payment); undo.Push("ReleaseFunds");
        await ctx.CallActivityAsync("DebitAccount", payment); undo.Push("CreditBack");
        await ctx.CallActivityAsync("SendPayment", payment);
        await ctx.CallActivityAsync("Notify", payment);
    }
    catch (TaskFailedException)
    {
        while (undo.TryPop(out var step))       // compensate in reverse order
            await ctx.CallActivityAsync(step, payment);
        throw;
    }
}

Compensating activities must be idempotent and should not fail. Give them their own retry policy.

11.7 CQRS & Event Sourcing Added

CQRS: separate the write model (commands) from the read model (queries). Event sourcing: store every change as an event and rebuild state from them.

➕ Benefits

  • Read and write sides scale independently
  • Read models tuned for each screen
  • Full audit trail and time travel (event sourcing)

➖ Costs

  • Eventual consistency between write and read
  • More moving parts
  • Event versioning, snapshots needed for long streams
  • CQRS doesn't require event sourcing, and you shouldn't apply either to simple CRUD domains.

11.8 Strangler Fig pattern Added

Modernise a legacy system bit by bit: put a façade in front, route one feature at a time to new services, and retire the old system once it's empty.

  • Pairs well with CDC (to keep data in sync), an anti-corruption layer, and feature flags for routing.

   .Add(b => ((RouteEndpointBuilder)b).Order = int.MaxValue);

11.9 Sidecar & Service Mesh Added

A sidecar is a helper container that runs next to your service. A service mesh puts a sidecar proxy next to every service to handle networking concerns.

app.UseCloudEvents();

// Publish: the sidecar talks to the real broker (Service Bus, Kafka, Redis...)
app.MapPost("/payments", async (Payment p, DaprClient dapr) =>
{
    await dapr.PublishEventAsync("pubsub", "payments", p);
    return Results.Accepted();
});

// Subscribe: the sidecar delivers events here
app.MapPost("/on-payment", (Payment p) => Results.Ok())
   .WithTopic("pubsub", "payments");

If the mesh already retries, don't stack aggressive app-level retries on top. You'll multiply load during an outage.

11.10 Domain-Driven Design essentials Added

Model software around the business domain, and draw service boundaries where the business language changes.

Bounded context

A boundary inside which a model and its terms have one meaning. "Account" in Lending ≠ "Account" in Login.

Ubiquitous language

Business and tech use the same words in conversation and in code.

Subdomains

Core (your edge, so build it), supporting, generic (buy it).

Aggregate

A cluster of objects changed as one unit with one root (e.g. an Order and its OrderLines).

Entity vs value object

An entity has an identity (Customer #42). A value object is defined by its values (Money, Address).

Domain events & context map

Events link contexts. The context map shows relationships (ACL, shared kernel, customer/supplier).

11.11 Event storming Added

A fast sticky-note workshop (created by Alberto Brandolini) where business and tech people map a domain as a timeline of events, then find the boundaries in it.

The sticky-note legend

🟧 Domain event

Something that happened, in the past tense: "Payment settled". The backbone of the wall.

🟦 Command

An intent or decision that causes an event: "Submit payment".

🟨 Actor (small yellow)

The person or role who issues a command: "Customer", "Payments ops".

🟪 Policy (lilac)

A reaction rule: "Whenever fraud score is high, hold the payment".

🔗 External system (pink)

Something outside your control: a payment scheme, a credit bureau, a fraud engine.

🟩 Read model

The information someone looks at to make a decision: "Available balance".

🟨 Aggregate (large yellow)

The thing that accepts commands and enforces the rules: "Payment", "Account".

🟥 Hotspot

A question, conflict or risk, often on a magenta or red note.

Colours vary between facilitators and tools. Agree a legend at the start and keep it visible on the wall.

11.12 Serverless architecture

You write the code or configuration. The cloud runs, scales (even to zero) and bills it per execution. Servers still exist, you just don't manage them.

→

FaaS

Functions as a Service: Azure Functions, AWS Lambda, Google Cloud Functions.

BaaS / managed

Serverless DBs, queues, auth, storage (Cosmos DB serverless, DynamoDB, Entra ID).

Serverless containers & workflows

Azure Container Apps, Fargate, Cloud Run · Logic Apps, Durable Functions, Step Functions.

➕ Pros

  • No infrastructure to manage or patch
  • Automatic, fine-grained scaling
  • Pay per use. Cheap for spiky or low traffic
  • Fast to build event-driven glue

➖ Cons

  • Cold starts (latency on the first call)
  • Execution time and memory limits
  • Vendor lock-in
  • Harder local debugging and observability
  • Can overwhelm downstream DBs when it scales out
  • Costly at constant high load

Common serverless patterns

  • Event processing: blob uploaded → function → extract → store.
  • API backend: APIM → Functions → Cosmos DB.
  • Fan-out / fan-in: Durable Functions run steps in parallel, then aggregate.
  • Scheduled jobs: timer trigger replaces cron VMs.
  • Queue-based load levelling: Service Bus → function with a concurrency limit.
  • Cut cold starts with premium or provisioned plans, small packages and keeping functions warm.
  • Functions should be stateless, idempotent and short. Use Durable Functions or Logic Apps for long workflows.
  • Cap concurrency to protect downstream systems.

✅ Scales to zero ✅ Pay per execution ✅ No patching

⚠️ Cold starts ⚠️ Time limits ⚠️ Lock-in ⚠️ Can DDoS your own database when it scales out

Perfect for event-driven glue and spiky workloads. Think twice for steady, heavy traffic.

One system serves many customers (tenants). The key design question is how much they share: everything (pool), nothing (silo), or a mix (bridge).

🔐 Tenant isolation

Data: filters, row-level security, per-tenant encryption keys. Compute: dedicated pools or nodes for big tenants. Watch the noisy neighbour.

🧭 Tenant context

Resolve the tenant once at the edge (host name, token claim) and carry it everywhere: DB filter, logs, traces, message headers, cache keys.

🚦 Limits & quotas

Rate limits partitioned by tenant, and quotas per plan (requests, storage, users).

🗝️ Tenant-aware caching

Prefix every cache key with the tenant (t:42:account:7). One missing prefix leaks data across tenants.

🤖 Onboarding automation

One pipeline creates the database or schema, config, identity and DNS for a new tenant, and removes them on exit.

💰 Cost per tenant

Tag resources and meter usage per tenant, so you know which customers and plans are profitable.

  • Most platforms end up tiered: a pool for the long tail of small tenants, silos for the big or regulated ones.
  • The tenant ID comes from the authenticated token or host name, never from the request body.
  • Write tests that try to read tenant B's data as tenant A, and run them in CI.
  • Put the tenant ID in logs and traces. Only use it as a metric label if the number of tenants is small (cardinality).

{

Multi-tenant SaaS: how much do your customers share? 🏢

🏠 Silo: a stack per tenant. Safest, and the most expensive.

🏬 Pool: everything shared, with a TenantId on every row. Cheapest, but isolation lives in your code.

🌉 Bridge: shared app, a database per tenant. The common middle ground.

📢 Noisy neighbour? Per-tenant rate limits and quotas.

🔑 The tenant ID comes from the token, never the request body.

Most real platforms end up tiered: a pool for the long tail, silos for the big, regulated customers.

⚡ Quick-fire Q&A

How do you keep data consistent across microservices?

Sagas with compensating actions, the transactional outbox for reliable events, idempotent consumers, and accepting eventual consistency where the business allows it.

When would you NOT use microservices?

Small team, unclear domain boundaries, early-stage product, or no mature DevOps and observability. Use a modular monolith instead.

Serverless or containers?

Serverless for event-driven, spiky, short tasks. Containers for long-running, steady, latency-sensitive workloads or when you need full runtime control.

Hexagonal vs Clean vs Onion: what's the difference?

Very little. All three put the domain at the centre and make dependencies point inwards, with infrastructure at the edge. Hexagonal talks about ports and adapters; Onion and Clean draw concentric layers, and Clean names them (entities, use cases, interface adapters, frameworks). For simple CRUD, a vertical slice structure is often a better fit.

What do you get out of an event storming workshop?

A shared timeline of domain events, the commands, actors, policies and external systems around them, a list of hotspots (open questions and risks), and candidate bounded contexts where the language and ownership change. That feeds the DDD context map and the service boundaries.

How do you isolate tenants in a shared database?

Resolve the tenant from the token or host, never from the request body. Add a TenantId to every row and enforce it with an EF Core global query filter (named, so it's never switched off by accident) and ideally database row-level security as a second layer. Prefix cache keys with the tenant, rate limit per tenant, and test for cross-tenant leaks in CI. Move large or regulated tenants to their own database.

API gateway or BFF: which one?

Usually both. The gateway is the shared front door: routing, TLS, token validation and rate limits, with no business logic. A BFF sits behind it, one per client type, and shapes data for that client by calling several services. If one generic API keeps growing "mobile-only" or "web-only" fields, it is time for a BFF.

How do you query data owned by several microservices?

For simple reads, use API composition: call the owning services in parallel and merge the results, with a timeout per call and a partial response when an optional part is slow. For large joins, search, sorting or paging, build a CQRS read model fed by events. Never read another service's tables directly.
